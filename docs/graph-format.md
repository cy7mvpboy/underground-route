# 경로 탐색 그래프 형식 (`web\data\graph.json`)

- 만드는 스크립트: `scripts\build_graph.py` (프로젝트 폴더에서 `python -I scripts\build_graph.py`)
- 참조 탐색기: `scripts\route.py` (JavaScript로 옮길 원본)
- 점검 결과: `data\derived\graph_report.json` (통계, 부착 못 한 역, 서울 자료 대조 결과, 한강 횡단 간선 목록)
- 크기(2026-11-10 빌드): 3,227,492 byte, gzip 970,700 byte(파이썬 gzip 9단계). 전국을 파일 하나에 담는다.
  - 노선·선 이름과 정차 순서를 넣기 전에는 3,047,859 byte(gzip 953,091 byte)였다. 늘어난 것은 대부분 간선 `tn` 열과 `line_routes`다.
  - 역 깊이(`stations[].depth`)를 넣기 전에는 3,208,525 byte(gzip 967,433 byte)였다(+18,967 byte).

## 1. 그래프가 무엇을 나타내나

사람이 걸을 수 있는 길을 점(노드)과 선(간선)으로 나타낸다. 간선은 네 종류다.

| 종류(kind) | 뜻 | 길이 |
|---|---|---|
| `track` | 선로 한 구간. 끝점·분기점·구조 변화점(터널↔교량↔지상)·역 부착점에서 자른다. | 원래 OSM 좌표로 잰 길이 |
| `platform` | 선로 위 역 부착점 ↔ 그 역의 '승강장 허브' | 직선 거리 |
| `transfer` | 같은 역 안의 허브 ↔ 허브(환승) | 서울교통공사 값 또는 추정값 |
| `entrance` | 지상 출입구 ↔ 역 허브 | 직선 거리 |

### 승강장 허브
- 역(같은 이름 역들의 묶음)마다 **노선별로** 허브 노드를 하나 둔다. 노선은 그 부착점에 붙은 선로의 노선 이름 묶음이다.
- 상·하행 선로처럼 같은 노선의 부착점은 같은 허브에 이어진다. 그래서 같은 노선의 반대편 선로로 건너갈 때는 허브를 거친다.
- 환승은 허브끼리만 잇는다. 이렇게 하면 다른 노선을 거쳐 같은 노선의 반대 선로로 가는 '지름길'이 생기지 않는다.
- 탐색의 출발점·도착점은 역의 허브들이다.

### 지하·지상 판정
- 선로: `tunnel` 태그가 있고 값이 `no`가 아니면 `tunnel`, 아니면 `bridge` 태그로 `bridge`, 나머지는 `ground`.
  - `layer<0`만 있는 선로는 지상(`ground`)이다. 경부선 금정~수원이 `layer=-1`이지만 실제로는 지상이기 때문이다(`docs\data-check.md` 4.4절).
  - `covered=yes`(방음터널 등)도 지상이다.
- 역 부착점: 그 점에 붙은 본선 선로가 모두 터널이면 지하.
- 허브: 부착점 중 하나라도 지하면 지하.
- 승강장 간선: 부착점이 지하면 `underground`, 아니면 `ground`.
- 환승 간선: 양쪽 허브가 모두 지하면 `underground`, 아니면 `ground`.
- 출입구 간선: 지하 허브에 이으면 `entrance`, 지상 허브밖에 없으면 `ground`.

### 탐색 비용
- 비용 = 길이(m) × 가중치.
- 가중치: `tables.under_structs`(`tunnel`, `entrance`, `underground`)는 `weights.under`(1), 나머지(`bridge`, `ground`)는 `weights.exposed`(1000).
- 그래서 지상 1m는 지하 1km와 같은 비용이다. 지하로만 가는 길이 있으면 그 길이 뽑히고, 없으면 지상 노출이 가장 짧은 길이 뽑힌다.
- 막힌 간선은 간선 번호(배열 위치)로 지정하고, 탐색할 때 건너뛴다.

## 2. 최상위 구조

```json
{
  "format": "underground-route-graph", "version": 1,
  "attribution": ["...", "..."], "osm_base": "2026-11-10",
  "weights": {"under": 1, "exposed": 1000},
  "tables": {...}, "nodes": {...}, "edges": {...},
  "stations": [...], "entrances": {...}, "presets": {...}, "line_routes": [...]
}
```

- 기존 키의 뜻은 바꾸지 않고 새 키만 더한다. 2026-11-10에 `tables.line_short`, `tables.line_metro`, `tables.track_names`, `edges.tn`, `line_routes`를 더했고, `tables.lines`의 이름을 정식 노선 이름으로 바꿨다(3.1절). 같은 날 `stations[].depth`(6.1절)를 더했다. 이때 다른 키·노드·간선 번호는 바뀌지 않았다.

크기를 줄이려고 노드와 간선은 **열(column)별 배열**로 저장한다. 노드 i의 위도는 `nodes.lat[i]`, 간선 j의 시작 노드는 `edges.a[j]`이다. 노드 번호·간선 번호는 배열 위치(0부터)다.

## 3. `tables` (코드 → 이름 표)

| 키 | 내용 |
|---|---|
| `structs` | `["tunnel","bridge","ground","entrance","underground"]` — `edges.s`의 값 |
| `under_structs` | 가중치 1인 구조 이름 목록 |
| `kinds` | `["track","platform","transfer","entrance"]` — `edges.k`의 값 |
| `sources` | `["","seoul_metro","estimated"]` — `edges.src`의 값(환승 거리 출처) |
| `railways` | `["rail","subway","light_rail","monorail","narrow_gauge"]` — `edges.r`의 값(선로가 아니면 -1) |
| `services` | `["","yard","siding","spur","crossover"]` — `edges.svc`의 값(""=본선, 나머지=측선·차량기지) |
| `lines` | 정식 노선 이름 목록(263개, 가나다순). 예: `"5호선"`, `"수인분당선"`, `"부산 1호선"`, `"경부고속선"` |
| `line_short` | `lines`와 같은 순서의 짧은 이름(안내 화면용). 예: `"2호선 성수지선"` → `"2호선"`, `"동해선 광역전철"` → `"동해선"` |
| `line_metro` | `lines`와 같은 순서. 1 = 도시철도·광역전철 노선(3.1절 노선 이름표에 있는 노선), 0 = 선로 이름에서 온 이름(경부선, 기지선 등) |
| `line_sets` | 노선 번호 묶음 목록. `edges.ls`, `stations[].hub_ls`가 이 목록의 번호다. 0번은 빈 묶음 |
| `track_names` | 선 이름 목록(275개 + 0번 빈 문자열). `edges.tn`의 값. 예: `"일산선"`, `"과천선"`, `"경인선"`, `"인천국제공항선"` |
| `regions` | `[{"name": "서울특별시", "conf": "good"}, ...]` — `edges.rg`, `stations[].rg`의 값 |

- 지역 신뢰도 `conf`: `good`(서울·인천·경기·부산·대구·대전), `caveat`(전남광주통합특별시·울산·세종·강원·경북·경남), `unchecked`(충북·충남·전북). 제주는 그래프에서 뺐다. 화면에서 `caveat`·`unchecked` 지역 구간은 '신뢰도 낮음'으로 표시한다.

### 3.1 노선 이름과 선 이름

간선 하나에 이름이 두 가지 붙는다.

| 구분 | 뜻 | 예 | 담는 곳 |
|---|---|---|---|
| 노선 | 열차가 다니는 운행 계통(안내판의 '3호선') | `3호선`, `4호선`, `공항철도` | `edges.ls` → `tables.line_sets` → `tables.lines` |
| 선 | 선로 자체의 이름(OSM 선로 way의 `name`) | `일산선`, `과천선`, `인천국제공항선` | `edges.tn` → `tables.track_names` |

**노선 이름 정하는 규칙** (`build_graph.py`의 `LINE_TABLE`, `TRACK_SERVICE`)
1. 그 선로가 든 도시철도·광역전철 노선 relation 이름을 정리한다(`:` 뒤, 괄호, `급행`·`내선순환` 같은 꼬리를 뗀다). KTX·무궁화 같은 열차 운행 계통 relation은 쓰지 않는다.
2. 노선 이름표(`LINE_TABLE`)로 정식 이름을 정한다. 정식 이름은 전국에서 하나뿐이다.
   - 수도권: `1호선`~`9호선`, `경의중앙선`, `수인분당선`, `신분당선`, `공항철도`, `GTX-A`, `경춘선`, `경강선`, `서해선`, `신림선`, `우이신설선`, `김포골드라인`, `용인경전철`, `의정부경전철`, `인천 1호선`, `인천 2호선`, `2호선 성수지선`, `2호선 신정지선` 등.
   - 다른 도시는 도시 이름을 붙인다: `부산 1호선`~`부산 4호선`, `부산김해경전철`, `동해선 광역전철`, `대구 1호선`~`대구 3호선`, `대경선`, `대전 1호선`, `광주 1호선`.
   - 표는 42개 노선(그래프에 선로가 있는 것은 41개, `광주 2호선`은 선로가 아직 없다).
   - 합친 이름(같은 노선이 두 이름으로 나오던 것): `9호선`/`서울 지하철 9호선` → `9호선`, `GTX-A`/`수도권광역급행철도에이선` → `GTX-A`, `수도권 전철 1호선`/`서울 지하철 1호선`/`1호선` → `1호선`, `대구 2호선`/`대구 도시철도 2호선` → `대구 2호선`, `용인 경전철`/`용인경전철` → `용인경전철`, `안심~하양 복선전철` → `대구 1호선`.
3. relation에 들지 않은 선로는 선 이름으로 노선을 정한다. 그 선을 다니는 노선이 하나뿐이면 `TRACK_SERVICE` 표를 쓴다: `인천국제공항선` → `공항철도`, `일산선` → `3호선`, `경인선` → `1호선`, `수인선` → `수인분당선`, `진접선` → `4호선`, `별내선` → `8호선`, `성수지선`·`신정지선` → 2호선 지선. 표에 없으면 선 이름을 그대로 노선 이름으로 쓴다(예: `경부선`, `경부고속선`, `지축기지선`. 이런 이름은 `line_metro` = 0).
   - 이 표 덕분에 서울역 공항철도 승강장처럼 relation이 빠진 몇 개 way 때문에 같은 역에 허브가 둘 생기던 일이 없어졌다(환승 간선 465개 → 425개).
   - `경강선`·`서해선`·`경춘선`은 수도권 전철 구간이 아닌 같은 이름 선로(예: 강릉선 KTX가 다니는 경강선)도 같은 노선 이름이 된다.

**선 이름 정하는 규칙** (`track_name()`)
- 선로 way의 `name`에서 앞뒤 공백을 지우고, `X본선`은 `X선`으로 바꾼다(`경부본선` → `경부선`, `경의본선` → `경의선`, `호남본선`·`영동본선`·`태백본선`도 같음).
- 노선을 가리키는 이름은 정식 노선 이름으로 바꾼다(`서울 지하철 1호선` → `1호선`, `부산 도시철도 1호선` → `부산 1호선`).
- 2026-11-10 데이터에 `상행`·`하행`·`복선` 같은 꼬리가 붙은 선 이름은 없었다(`복선`은 `안심~하양 복선전철` 하나뿐이고 노선 이름표에서 `대구 1호선`으로 합쳤다).
- 본선 선로 길이가 긴 선 이름: 경부선 1,090km, 경부고속선 796km, 중앙선 646km, 호남선 510km, 동해선 461km, 경전선 436km, 호남고속선 369km, 전라선 354km, 경강선 347km, 서해선 263km. 수도권 전철이 다니는 선: 경원선 150.5km, 인천국제공항선 128.2km, 경의선 125.2km, 분당선 106.4km, 경인선 104.6km, 수인선 78.6km, 안산선 52.0km, 일산선 38.4km, 진접선 29.0km, 과천선 28.5km. 이름 없는 본선 선로는 182km다. 전체 목록은 `graph_report.json`의 `names.top_track_names_km`에 있다.

**안내 화면 표시**: `<짧은 노선 이름> · <선 이름>`. 선 이름이 노선 이름(정식 또는 짧은 이름)과 같으면 노선 이름만 쓴다.
- 예: `3호선 · 일산선`, `4호선 · 과천선`, `1호선 · 경인선`, `공항철도 · 인천국제공항선`, `2호선 · 신정지선`. 서울 시내 3호선 선로(선 이름 `3호선`)는 `3호선`.

## 4. `nodes`

| 키 | 내용 |
|---|---|
| `lat`, `lon` | 위도·경도 × 100000 (정수). 예: `3758851` → 37.58851 |
| `f` | 표시 비트. 1 = 터널 출입구(갱구, 터널과 비터널 선로가 만나는 점), 2 = 역 부착점(선로 위), 4 = 출입구(지상 쪽 끝, 진입점), 8 = 승강장 허브 |

## 5. `edges`

모든 배열의 길이는 간선 수와 같다. 간선 번호 순서는 `track` → `platform` → `transfer` → `entrance`이다.

| 키 | 내용 |
|---|---|
| `a`, `b` | 양 끝 노드 번호. 간선은 양방향으로 걸을 수 있다 |
| `len` | 길이(m, 소수 1자리) |
| `s` | 구조(`tables.structs` 번호) |
| `k` | 종류(`tables.kinds` 번호) |
| `r` | 철도 종류(`tables.railways` 번호, 선로가 아니면 -1) |
| `svc` | 본선/측선(`tables.services` 번호) |
| `ls` | 노선 묶음(`tables.line_sets` 번호) |
| `rg` | 지역(`tables.regions` 번호). 신뢰도는 지역 표에서 찾는다 |
| `src` | 환승 거리 출처(`tables.sources` 번호). 환승이 아니면 0 |
| `g` | 선 모양. Google 인코딩 폴리라인(소수 5자리). 노드 a에서 b 방향이고 양 끝점을 포함한다. `track`이 아니면 빈 문자열이고, 두 노드를 직선으로 그린다 |
| `tn` | 선 이름(`tables.track_names` 번호). 0 = 이름 없음. `track`이 아니면 0 |

- 선로를 간선으로 합칠 때(차수 2 노드 없애기) 선 이름이 다르면 합치지 않는다. 그래서 선 이름이 바뀌는 곳에서 간선이 나뉜다(선로 간선 35,008개 → 35,024개).

- 선 모양은 더글러스-포이커 방식으로 5m 오차 안에서 점을 줄였다. 길이(`len`)는 줄이기 전 좌표로 잰 값이다.
- 측선(차량기지·측선·인상선·건넘선)도 넣었고, 탐색 비용은 구조로만 정한다(측선 터널도 가중치 1). 화면에서 숨기려면 `svc != 0`인 간선을 거르되, 탐색에서는 빼면 안 된다.
  - OSM에는 본선이 측선을 거쳐서만 나머지 선로와 이어지는 곳이 있다. 예: 서해선 대곡~원시 남쪽 끝의 터널 way 970070469가 `service=yard`로 되어 있고, 경춘선 청량리 부근 way 903353258·1025050687은 측선으로만 이어진다. 측선을 빼면 이 본선들이 떨어져 나간다. 원시→대곡, 청량리→상봉 탐색에서 이 측선 간선을 지나는 것을 확인했다.

### 폴리라인 풀기 (JavaScript)

```js
function decodePolyline(s) {
  const pts = []; let i = 0, lat = 0, lon = 0;
  while (i < s.length) {
    for (const k of [0, 1]) {
      let r = 0, sh = 0, b;
      do { b = s.charCodeAt(i++) - 63; r |= (b & 31) << sh; sh += 5; } while (b >= 32);
      const d = (r & 1) ? ~(r >> 1) : (r >> 1);
      if (k === 0) lat += d; else lon += d;
    }
    pts.push([lat / 1e5, lon / 1e5]);
  }
  return pts;
}
```

## 6. `stations` (역 = 같은 이름 역들의 묶음)

```json
{"name": "한성대입구", "names": ["삼선교", "한성대입구"], "lat": 3758851, "lon": 12700596,
 "rg": 7, "hubs": [30824], "hub_ls": [3], "ug": [1], "plat": [2116, 7114]}
```

| 키 | 내용 |
|---|---|
| `name` | 표시 이름 |
| `names` | 검색용 이름(정규화: 괄호 내용·공백·끝의 '역' 제거, 별칭 포함) |
| `lat`, `lon` | OSM 역 노드들의 평균 위치 × 100000 |
| `rg` | 지역 번호 |
| `hubs` | 노선별 승강장 허브 노드 번호 |
| `hub_ls` | 허브마다 노선 묶음 번호 |
| `ug` | 허브마다 지하 여부(1/0) |
| `plat` | 선로 위 부착점 노드 번호 전체 |
| `depth` | 노선별 역 깊이 목록(6.1절). 자료가 있는 역에만 있고, 없으면 키 자체가 없다 |

### 6.1 `depth` (역 깊이)

```json
{"name": "종로3가", ..., "depth": [{"line": 2, "floor": "B2", "platform_m": 11.24, "track_m": 12.34},
                                  {"line": 7, "floor": "B4", "platform_m": 20.25, "track_m": 21.35},
                                  {"line": 11, "floor": "B5", "platform_m": 30.2, "track_m": 31.3}]}
```

| 키 | 내용 |
|---|---|
| `line` | 노선 번호(`tables.lines` 위치). 그 역 허브의 노선(`hub_ls`) 중 하나라서 허브와 맞춰 볼 수 있다. 보통 `1호선`~`8호선`이고, 지선에만 붙은 역은 지선 이름이다(예: 용답·신답 → `2호선 성수지선`, 도림천 → `2호선 신정지선`) |
| `floor` | 승강장 층수. 자료 글자 그대로: `B1`~`B8`(지하), `고가`, `지상` |
| `platform_m` | 정거장깊이(m, 자료의 `정거장깊이`). 지면(지반고)에서 승강장까지 |
| `track_m` | 선로 기준 정거장깊이(m, 자료의 `선로기준정거장깊이`). 지면에서 레일면까지. 이 자료에서는 277행 모두 `platform_m`보다 1.1m 깊다 |

- 출처: 서울교통공사 역사심도정보(2024-11-04, 서울 열린데이터광장), 공공누리 제1유형(출처 표시). 원본 `data\raw\seoul\station_depth_20241104.csv`(CP949, 277행, 서울교통공사 1~8호선). 그래프의 `attribution` 둘째 줄이 이 자료도 함께 밝힌다.
- 2026-11-11 추가: 서울교통공사 9호선 2·3단계 역사 심도 정보(OA-22446, 2026-01-31판). 원본 `data\raw\seoul9\station_depth9_20260131.csv`(CP949, 13행, 언주~중앙보훈병원). 열 순서가 1~8호선 자료와 같아 `SEOUL_DEPTH`에 두 파일을 함께 넣고 같은 방식으로 맞춘다. 290행 모두 역 250개에 맞았다. 9호선 1단계(개화~신논현)는 공개 자료가 없어 깊이가 없다.
- 값은 자료 그대로다. 고가·지상역은 음수일 수 있다(지면보다 높음, 예: 동작 4호선 `고가`, `platform_m` -20.9). 지상역 신답은 0.3처럼 양수도 있다.
- 맞추기: `build_graph.py`의 `match_depth_rows()`. 서울·경기 역 중 정규화한 이름이 같고, 부착점 노선이 자료의 호선(지선 포함)인 역을 고른다. 이름이 없으면 옛 이름·줄임말 표(`DEPTH_ALIASES`: 을지3가 → 을지로3가, 당고개 → 불암산, DMC → 디지털미디어시티 등)로 다시 찾는다. 같은 자료로 지하 여부 대조(12절)도 한다.
- 2026-11-10 빌드: 277행 모두 역 하나씩에 맞았다(못 맞춘 행 없음). 깊이가 있는 역은 240개(서울 225, 경기 15), 기록은 277개다. 한 역에 노선이 여럿이면 기록도 여럿이다(예: 종로3가 1·3·5호선).
- 가장 깊은 역(`platform_m`): 산성(8호선, B4) 54.69m, 버티고개(6호선, B5) 44.65m, 숭실대입구(7호선, B6) 44.53m, 신금호(5호선, B8) 42.16m, 독바위(6호선, B6) 36.84m.
- 서울교통공사 1~8호선만 있다. 9호선, 신분당선, 코레일 구간(1호선 서울역~청량리 밖, 경의중앙선 등), 다른 도시 역에는 없다.

### 역을 만든 규칙
1. OSM 역 노드(`railway=station|halt`, `public_transport=station`)를 읽는다. 공사중(`railway=construction`, `construction:railway`), 제주, 서비스역은 뺀다.
2. 정규화한 이름(별칭 포함)이 같고 500m 안에 있거나, 같은 `stop_area`에 든 역 노드를 한 역으로 묶는다.
3. 부착점
   - 선로 위의 정차 위치(`railway=stop`, `public_transport=stop_position`)를 먼저 쓴다. 정차 위치는 `stop_area`로, 없으면 300m 안의 같은 이름 역으로 역에 연결한다. 선로 밖에 찍힌 정차 위치는 30m 안의 선로에 붙인다.
   - 300m 안에 정차 위치가 없는 역 노드는 200m 안의 본선 선로 중 가장 가까운 선로와, 그보다 40m 안쪽으로 더 먼 같은 구조의 선로(상·하행 등)에 붙인다. 붙이는 자리에 노드를 새로 끼워 넣어 선로를 자른다.

## 7. 환승 규칙
- 같은 역 안의 허브끼리 600m 안이면 환승 간선을 둔다.
- 추정 거리(`estimated`): **직선 거리 × 1.3 + 50m**. 1.3은 통로가 곧지 않은 것, 50m는 계단·개찰구를 대략 반영한 값이다. 실측 근거는 없다.
- 서울교통공사 자료(`seoul_metro`): '환승역명 + 호선 + 환승노선'이 맞는 허브 쌍에 공개된 환승 거리를 넣는다. 140행 중 139행을 반영했다. 반영하지 못한 1행은 `5호선 강동 → 5호선`(OSM에서 5호선 본선과 지선의 노선 이름이 같아 구분할 수 없음)이다.
  - 자료의 노선 표기는 정식 노선 이름(3.1절)으로 바꾼다. 예: `1` → `1호선`, `경의중앙선` → `경의중앙선`, `경원선` → `1호선`(석계), `국철` → `수인분당선`(수서, 가정).
- 환승 통로가 실제로 지하로 이어져 있는지는 OSM에 거의 없다. 양쪽 승강장이 지하면 지하 통로가 있다고 **가정**한다. 발표·화면에서 밝혀야 한다.

## 10. `line_routes` (노선 relation의 정차역 순서)

길 안내에서 '오금 방면' 같은 종착역 방면을 찾는 데 쓴다. OSM 노선 relation(운행 계통) 하나가 한 줄이다(239개).

```json
{"l": 7, "dir": "오금 방면", "loop": 0, "st": [602, 906, 601, ...]}
```

| 키 | 내용 |
|---|---|
| `l` | 노선 번호(`tables.lines` 위치) |
| `dir` | 방면 표시. 보통 `<마지막 정차역> 방면`, 2호선 순환선은 `내선순환`·`외선순환` |
| `loop` | 1 = 첫 역과 마지막 역이 같은 순환 relation |
| `st` | 정차역 순서(`stations` 번호). relation의 `stop` 역할 노드를 정차 위치·`stop_area`로 역에 이어 만든다. 역에 잇지 못한 정차 위치는 빠진다 |

- 순환 표시(`내선순환`·`외선순환`)가 없는 순환 relation은 방면을 정할 수 없어 넣지 않았다. 같은 내용(노선·방면·정차역 순서)이 겹치는 relation은 하나만 넣었다.

## 11. 길 안내 단계 (`route.py`가 만드는 `steps`)

그래프에 저장하는 내용은 아니고, 탐색 결과를 안내 단계로 바꾸는 규칙이다. `route.py --json`의 `steps`에 들어 있고, 웹에서 같은 방식으로 옮겨 쓴다.

### 단계 나누기
1. 경로(간선 목록)를 환승 간선에서 나눈다. 환승 간선 하나가 `transfer` 단계 하나다.
2. 그 사이(선로·승강장 간선)는 노선이 바뀌는 곳에서 다시 나눠 `ride` 단계로 만든다. 간선마다 노선 고르는 방법:
   - 도시철도·광역전철 노선(`line_metro` = 1)만 본다. 지금 타던 노선이 다음 간선에도 있으면 계속 타고, 없으면 그 자리에서 가장 길게(m) 이어지는 노선으로 바꾼다. 노선이 없는 간선(승강장 간선, 이름 없는 선로)은 앞 노선을 이어 간다.
   - 그런 노선이 없는 선로(경부선·기지선 등)가 같은 노선 사이에 끼어 있으면 그 노선으로 메운다(relation이 빠진 틈, 예: 원흥→경복궁 경로의 삼송 부근 지축기지선 0.5km는 3호선 단계에 들어간다).
   - 남은 구간은 선로 이름에서 온 노선(예: `경부고속선`)으로 정한다.
3. 지상 노출 경고(`warning`)를, 노출이 시작되는 간선이 든 단계 바로 앞에 끼운다. 지하(가중치 1)에서 교량·지상으로 바뀔 때마다 하나, 출발부터 지상이면 출발역에서 하나.
4. `ride`·`transfer` 단계에는 1부터 번호(`no`)를 붙인다. 경고에는 번호가 없고, 어느 단계 안의 일인지 `in_step`으로 적는다.
- 걷는 시간: 거리 ÷ 걷는 속도. 기본 시속 3.5km(`--speed`로 바꿈). 모든 단계 거리의 합은 경로 총거리와 같다(반올림 1m 차이).

### `ride` (노선 하나를 따라 걷기)

| 키 | 내용 |
|---|---|
| `line`, `line_full` | 짧은 노선 이름, 정식 노선 이름 |
| `label` | 표시 문구. `<짧은 노선 이름> · <선 이름들>`. 노선 이름과 같은 선 이름은 뺀다. 예: `3호선 · 일산선` |
| `track_names` | 지나는 선 이름(순서대로, 중복 없이). 노선 이름과 같은 것도 들어 있다. 예: `["과천선", "4호선"]` |
| `track_parts` | 선 이름이 바뀔 때마다 나눈 구간 `[{name, from_station, to_station, distance_m}]`. `from_station`은 선이 바뀌기 직전에 지난 역 |
| `from_station`, `to_station` | 출발역(직전 단계가 끝난 역), 마지막으로 지난 역 |
| `passing` | 그 사이에 지나는 역 `[{station, at_m}]`. `at_m`은 단계 출발부터의 거리(m). 진행 표시에 쓴다 |
| `direction` | `<다음 역> 방면` |
| `terminal_direction` | 종착역 방면(예: `오금 방면`, `내선순환`, `하남검단산·마천 방면`). 종착역을 못 찾으면 도착역 방면(아래). 다음 역이 없는 단계에는 없다 |
| `distance_m`, `est_minutes`, `exposure_m` | 거리, 예상 시간(분), 그중 지상 노출 거리 |

- 종착역 방면 찾기(승강장 표지판처럼 종착역으로 적는다):
  1. `line_routes`에서 같은 노선이고 '출발역 바로 다음 정차역이 이 단계의 다음 역'이며 그 뒤에 도착역이 있는 relation을 모두 찾는다. 순환선은 정차역 순서를 한 바퀴 더 이어 붙여 찾는다.
  2. 그중 종착역이 다른 relation의 앞으로 지날 정차역에 있는 것(중간 종착)은 뺀다. 예: 5호선 상일동행은 하남검단산행이 지나는 상일동에서 끝나므로 뺀다. 4호선 사당·안산·산본행은 오이도행 길 위에서 끝난다.
  3. 남은 방면이 하나면 그대로 쓴다(예: `오금 방면`, `내선순환`).
  4. 여럿이면 도착역 뒤에서 노선이 갈라지는 경우다. 종착역 이름을 `line_routes` 순서대로 `·`로 이어 `<종착역>·<종착역> 방면`으로 쓴다. 예: 5호선 왕십리→천호 `하남검단산·마천 방면`, 경의중앙선 문산→파주 `용문·서울역 방면`.
     셋 이상(1호선만 해당)이면 가장 긴 두 방면만 남긴다. 방면마다 그 방면 relation 중 가장 많은 정차역 수(`st` 길이)로 비교하고, 같으면 `line_routes` 순서를 따른다. 예: 1호선 청량리→동대문(종착 인천·신창·서동탄) `인천·신창(순천향대) 방면`, 신도림→구로(인천·신창·서동탄·광명) `인천·신창(순천향대) 방면`, 가산디지털단지→금천구청(신창·서동탄·광명) `신창(순천향대)·서동탄 방면`.
  5. 하나도 못 찾으면(relation이 없는 노선·선로) 이 단계의 도착역 방면(`<to_station> 방면`)을 쓴다. 다음 역은 지나고 나면 반대쪽처럼 읽히기 때문이다.
- 글 안내·화면은 `terminal_direction`을 쓰고, 다음 역(`direction`)과 다르면 글 안내에 `(다음 역 …)`을 붙인다.

### `transfer` (환승 통로)

| 키 | 내용 |
|---|---|
| `station` | 환승역 |
| `from_line`, `to_line` | 앞뒤 `ride` 단계의 짧은 노선 이름(없으면 허브의 노선 이름) |
| `distance_m`, `est_minutes` | 환승 거리, 예상 시간 |
| `source` | `seoul_metro`(서울교통공사 자료) 또는 `estimated`(추정, 7절) |
| `underground` | 지하 통로로 보는지(양쪽 승강장이 모두 지하일 때 true, 7절의 가정) |

### `warning` (지상 노출 경고)

| 키 | 내용 |
|---|---|
| `at`, `after_m` | 노출이 시작되는 곳: 직전에 지난 역과 그 역에서 지난 거리(m). 역에서 바로 시작하면 0 |
| `portal` | 터널 출입구(갱구, 노드 `f`의 1)에서 나가는지 |
| `lat`, `lon` | 노출이 시작되는 지점 좌표 |
| `exposure_m` | 다시 지하로 들어갈 때까지(또는 도착까지)의 노출 거리. 여러 단계에 걸칠 수 있다 |
| `structure`, `structures` | 가장 긴 구조(`ground`·`bridge`), 구조별 거리(m) |
| `ends_underground` | true = 다시 지하로 들어감, false = 지상인 채로 도착 |
| `in_step` | 이 노출이 시작되는 단계의 번호 |

### 글 안내 (`route.py` 기본 출력)

## 12. 알려진 한계
- 역 깊이 자료와 대조한 277개 중 2개가 다르다: `1호선 서울`(지상 경부선 승강장도 1호선 노선에 들어 있어 부착점 3개 중 1개가 지상), `2호선 한양대`(자료는 B2, OSM은 교량으로 표시).
- 동대구처럼 OSM이 역 건물 밑 선로를 `tunnel`로 그린 곳은 지하로 계산된다.
- 선 이름은 OSM 선로 way의 `name`을 그대로 쓴다. 선 경계가 실제 공식 경계와 조금 다를 수 있다(예: 신도림~구로는 대부분 `경부선`, 구로 직전 0.3km가 `경인선`).
- 종착역 방면은 OSM 노선 relation의 정차 순서가 맞아야 나온다. relation이 실제 운행 계통과 다르면 방면도 다르게 나온다(예: 4호선 인덕원→사당은 진접행 relation이 남태령부터라 `불암산 방면`, 1호선 의정부→도봉산은 신창행 relation이 광운대부터라 `인천·서동탄 방면`).
- 1호선은 구로·금천구청·병점에서 갈라져 종착역이 3~4개 나오지만 가장 긴 두 방면만 적는다. 짧은 지선 쪽(서동탄·광명)은 이름에서 빠질 수 있다(예: 신도림→구로 `인천·신창(순천향대) 방면`).
- 경부고속선을 따라가는 긴 단계(예: 부산 시청 → 서울 을지로3가 시험의 129km 단계)에 지나는 역이 하나도 나오지 않는다. 원인은 확인하지 않았다(역이 본선 옆 승강장 선로에만 붙었을 가능성이 있다).
- 노선 relation이 일부만 덮은 선로에서는 한 선로를 따라가는데 단계가 나뉠 수 있다(예: 수서→평택지제는 `수서평택고속선` → `GTX-A · 수서평택고속선` → `수서평택고속선` 3단계).
- 부착 못 한 역 9개는 운행 선로 근처에 없는 역이다(레일바이크·관광열차, 장항선 옛 역 등). 목록은 `graph_report.json`에 있다.

## 13. basemap.json

- 만드는 스크립트: `scripts\build_basemap.py` (`python -I scripts\build_basemap.py`; 원본은 `data\raw\basemap\`, 없으면 `--fetch`). 쿼리는 `scripts\queries\basemap_*.overpassql`.
- 용도: 타일을 쓸 수 없는 곳(claude.ai Artifact, 오프라인)의 가벼운 바탕 지도. 크기 약 77KB(gzip 약 46KB).
- 출처: © OpenStreetMap contributors (ODbL), 2026-11-10 받음.

```json
{"format": "basemap-1", "precision": 5, "attribution": "© OpenStreetMap contributors (ODbL)",
 "lines":  [{"k": "coast", "p": "<인코딩 폴리라인>"}, {"k": "admin", "p": "..."}],
 "labels": [{"k": "region", "name": "서울특별시", "lat": 37.5667, "lon": 126.9783},
            {"k": "city", "name": "수원", "lat": 37.2633, "lon": 127.0287}]}
```

- `p`: 3.5절과 같은 Google 인코딩 폴리라인(소수 5자리)이라 같은 `decodePolyline`으로 푼다. 선 하나가 폴리라인 하나이고 닫힌 고리는 첫 점과 끝 점이 같다.
- `lines[].k`
  - `coast`: `natural=coastline` 중 한국 영역(ISO3166-1=KR)만. 북한·일본 해안은 영역 필터로 빠진다. 더글러스-포이커 200~400m, 2km보다 짧은 섬·조각은 뺐다(제주·울릉·독도 등 큰 섬은 있음).
  - `admin`: 시·도(admin_level=4) 경계선. 공유 경계는 한 번만 넣었다. OSM 경계는 바다(영해선)까지 그려져 있어, 시·도 사이 경계와 휴전선 구간만 쓰고 한 시·도에만 속한 바다 쪽 경계는 뺐다. 150m로 줄였다.
- `labels[].k`: `region` = 시·도 이름(광역시급은 OSM admin_centre, 도는 손으로 정하거나 면적 무게중심), `city` = 인구순 대표 도시와 도청 소재지(짧은 이름, 예 `수원`).
- OSM 현재 상태: 광주광역시와 전라남도가 `전남광주통합특별시`(relation 21039457) 하나라 시·도 경계에 둘 사이 선이 없다. 이름표도 하나다(`광주`는 city 이름표로만 있다).
- 한계: 휴전선 구간은 위경도 상자로 가려냈고(`DMZ_BOX`) 한강 하구 부근 경계는 근사다. 경계선이 해안선과 만나는 끝점은 단순화 때문에 몇백 m 어긋날 수 있다.

- 출발·도착 끝점 종류(router.js): 역·노드·지도 위 점에 더해 **선로 위 점**(`{kind: 'edgept', e, t, only?}`, 간선 a 쪽에서 0~1)과 **나갈 곳**(`{kind: 'egress', cand}`, exithere.js 후보). 이때 경로 앞뒤에 간선 일부(`startPart`·`endPart`)나 차량기지 안 지상 길(`endWalk`)이 붙고, 안내 목록에는 `approach`(지금 위치 → 첫 노드)와 `egress`(나갈 곳) 항목이 생긴다. 선로 위 점과 같은 간선 위의 수직구는 노드를 거치지 않고 바로 간다.

- 지도 위 점(지도 누르기·내 위치·출구 팝업): 1.5km 안 가까운 출입구 3곳과, 출입구 자료가 없는 1.5km 안의 역(허브)에 '가상 지상 간선'(직선 거리 × 1.3)으로 잇는다. 둘 다 없으면 20km 안 가장 가까운 역 3곳. 이 거리는 모두 지상 노출로 센다. 출발과 도착이 둘 다 점이면 '지상으로 바로 걷기'도 후보에 넣는다.
  - 터널 출입구·차량기지(2026-11-11, `router.egressConns`): `egress.json`(19절)을 받았으면 1.5km 안의 가까운 3곳도 같은 방식으로 잇는다. 터널 출입구는 묶은 출입구 노드(`nodes`) 하나하나, 차량기지는 나가는 곳(`lat`·`lon`)까지 걷고 기지 안을 대표 노드(`node`)까지 더 걷는다(직선 × 1.3, 지상 노출). 어디로 들어갈지는 다른 후보와 같이 비용으로 고른다. 수직구·비상 출구와 '가장 가까운 지하로'에는 쓰지 않는다. 단계 글: '○○ 터널 입구로 들어가기' · '○○ 터널 출입구로 나가기' · '○○차량기지로 들어가기/나가기'(egress 이름). `egress.json`을 아직 안 받았으면 역 출구로 먼저 잇고 받기 시작해, 받은 뒤 경로가 달라지면 다시 찾는다(길 안내 중에는 그대로). `egress.json`을 주지 않으면 예전과 같다(`check_router.js`의 `route.py` 비교).
- 대안 경로(2026-11-11, `router.alternative`): 기본 탐색(지상 1000)은 그대로 두고, 지상 가중치 `ALT.exposedW` = 15로 한 번 더 찾는다. 다른 경로이고, 걷는 시간이 20% 이상 또는 30분 이상 줄고, 늘어나는 지상 노출이 2km 이하일 때만 결과 카드에 한 줄('지상 1.2km 걸으면 22km 짧아요 · 약 6시간 단축')을 보이고, 누르면 그 경로로 바꾼다(그 뒤에는 '지하 우선 경로로'). 고르지 않은 경로는 지도에 가늘고 옅은 선. 앞이 막혀 다시 찾은 길 안내에서는 첫 확인 지점 전까지 카드에 같은 한 줄이 보이고, 누르면 바꾼 경로로 안내를 이어 간다. 가장 가까운 지하로·여기서 나가기·바로 걷기에는 두지 않는다.
- 길 안내 따라가기(2026-11-11, `app.keepCentered`): 지금 위치(GPS 또는 추정)가 지도에서 보이는 곳(위 카드·아래 단추를 뺀 곳)의 가운데 칸(가로·세로 20%)을 벗어나면 가운데로 0.6초 동안 옮긴다(움직이는 중이면 그만큼 앞을 겨냥, 움직임 줄이기면 바로). 단계가 바뀌면 지금 위치를 가운데에 두고 다음 확인 지점까지 보이게 맞춘다. 지도를 끌거나 키보드 화살표로 옮기면 멈추고 '현재 위치로'로 다시 따라간다. 시연(`demo.js`)도 같은 함수를 쓴다.
- 검증(2026-11-11 추가): `node scripts\check_alt.js` — 대안 경로(기본 탐색 그대로, 옥수→압구정 대안 있음, 부산역→서면·서울역→강남·노량진→용산 없음, 시연 이야기(명동→수서, 광나루–천호 하저터널 막힘) 막힘 뒤 대안: 대안을 누르면(2026-11-13 `takeAlt`) 지상 노출이 약 722m 늘고 두 번째 하저터널은 수인분당선 서울숲–압구정로데오). `node scripts\check_connect.js` — 9호선 개화 부근 터널 출입구 옆에서 출발하면 터널 입구로(지상 노출 2,778m → 68m), 도착이면 출입구로 나가기, 방화차량사업소 옆은 기지로(3,123m → 1,455m), 시청 앞은 역 출구 그대로, `egress.json`이 없으면 예전과 같음.
- 지상 걷기 간선(웹에서만): 지하로 갈 길이 없을 때(앞이 막힘, 끊긴 노선)의 대비책. 1.5km 안의 다른 역끼리 가장 가까운 출입구(없으면 허브) 사이를 직선 × 1.3 길이, 구조 `ground`, 종류 `surface`로 잇는다(2026-11-10 그래프에서 1,704개). `graph.json` 간선 뒤에 붙여 원래 간선 번호는 그대로고, 기본 탐색(= `route.py`)에서는 쓰지 않는다. 기본 탐색이 실패할 때만 `findRoute(..., {surface: true})`로 다시 찾고, 안내에는 '지상 걷기' 단계(`type: 'surface'`)로 나온다.
- 앞이 막힘: 마지막으로 '도착'을 누른 체크포인트와 다음 체크포인트 사이의 선로 간선, 그리고 그 선 모양에서 40m 안에 나란히 있는 선로(같은 터널의 반대 방향)를 막는다. 들어갈·나갈 출구가 막히면 그 출입구 간선만 막는다. 되돌아갈 거리는 마지막 확인 뒤 걸은 시간 × 걷는 속도(다음 체크포인트까지를 넘지 않게)로 추정한다.
- 승강장 깊이: 역 시트의 '이 역 정보'에서 `stations[].depth`(6.1절, 서울교통공사 1~8호선 역만)를 승강장 줄마다 보여 준다(지하 층이면 층·승강장·선로 깊이, 고가·지상이면 그 글자만). 없는 역은 깊이를 숨긴다.
- 지상 도보 길(`walk.js`): 인터넷이 되면 FOSSGIS OSRM 도보 경로(`routing.openstreetmap.de/routed-foot`)로 출발·도착 지점과 출구 사이 등을 실제 길로 바꾼다. 거리·시간·지상 노출도 그 거리로 바뀐다(경로 선택은 직선 × 1.3으로 한 그대로). 지도·결과에 '도보 경로: FOSSGIS OSRM · © OpenStreetMap'을 밝힌다. claude.ai 미리보기·오프라인에서는 요청이 막혀 직선을 쓴다.
- 여기서 지하로 갈 수 있는 곳(`reach.js`): 2026-11-10 그래프, 시속 3.5km. 시청(서울) 30분 6곳 · 1시간 22곳 · 2시간 65곳 · 4시간 150곳, 강남 5 · 20 · 50 · 115곳, 대화 1 · 2 · 4 · 4곳(일산선은 백석 뒤로 지상이라 4곳에서 멈춘다).
- 검증: `node scripts\check_router.js` — 역 쌍 9개(한강 5호선 차단 1개 포함)를 `route.py --json`과 비교한다(간선 목록, 총거리, 노출, 단계 내용, 글 안내 문장). `node scripts\check_guide.js` — 가장 가까운 지하로(시청 앞, 해운대 해변, 역 없는 지리산), 대화→백석 체크포인트·도착·앞이 막힘·다시 찾기, 들어갈 출구가 막혔을 때. `node scripts\check_reach.js` — 도달 범위(시청·대화·강남·지상역, 지하 간선만 썼는지, 띠·막은 간선). `node scripts\check_walk.js` — 가짜 OSRM 응답으로 도보 구간 바꾸기(요약·체크포인트·위치 추정 선이 새 거리와 맞는지, 저장, 실패·시간 초과, 가장 가까운 지하로 순위 바꾸기). `node scripts\check_exit_here.js` — 여기서 나가기(공덕~마포 터널 한가운데 egress.json 있음/없음, 터널 출입구 가까이, 같은 간선 위 수직구(가장 긴 터널 예시·egress.json 수직구), 지하로 들어가는 차량기지, 역 시트, 고른 곳까지 다시 찾은 경로 거리 = 후보 거리·노출 0, 가던 쪽이 막혀 반대쪽으로, 강동→둔촌동 갈림길 체크포인트와 갈림길 뒤 앞이 막힘, 경로 위 수직구 위치). `node scripts\check_transfer.js` — 환승 카드 내용(서울역→강남: 공덕 공항철도→5호선·여의도 5→9호선·신논현 9호선→신분당선, 부평→구로: 신도림 지상 환승·까치산 같은 깊이, 종각→안국: 종로3가 약 9m 아래로; 방향·출처 글·1.2m/s 시간·행동 안내, transfer 단계 키가 그대로인지), 손으로 만든 `extra.json` 예시(앞뒤 뒤집기, `prev_alt`), 실제 `extra.json`(있으면), 경로에서 벗어난 거리. `node scripts\check_load.js` — 첫 로딩에서 나눠 하는 일(14.1절): 첫 화면 선로 + 나머지 = 그릴 선로 전부(예전 묶음과 같은 개수), 장소 검색 열쇠를 나눠 만들어도 한 번에 만든 것과 같고 중간에 검색해도 결과가 같음, `index.html`의 미리 받기·글꼴 CSS 설정. `node scripts\check_passage.js` — `passage.json` 형식·양 끝(20절)과 그리기 고르기(`passage.js`: 모양이 있으면 지하도 선, 없으면 출구 직선·환승 옅은 점선, 방향 뒤집기, 길 안내 선의 총 거리 그대로).

- 역 안 지하도 모양(20절, 사용자 승인): `passage.json`에 그 환승 간선의 선이 있으면 두 승강장 사이를 그 지하도 선(경로의 지하 색 실선, `edges.a` 허브 → `edges.b` 허브, b → a로 걸으면 뒤집음)으로 그린다. 출구 구간(경로의 처음·끝 출입구 간선, 여기서 나가기로 역 출구까지, 역 시트·결과에서 누른 출구)도 그 출입구의 선이 있으면 직선 대신 지하도 선(출구 → 역)으로 그린다. 선 끝과 허브 사이(자료 없음)는 3m 이상이면 옅은 점선이다. **그림만 바뀐다**: 거리·시간·탐색·체크포인트는 그래프 간선 그대로이고, 길 안내의 위치 추정 선(`guide.routeTrack`의 `shape`)만 그린 모양을 따라간다(간선 안에서 길이 비율로 자리를 찾으므로 거리는 같다). `passage.json`은 경로가 출입구·환승 간선을 지나거나 출구를 누를 때 처음 받는다(14.1절).

### 14.1 처음 불러오는 순서 (첫 로딩, 2026-11-11)

첫 화면(지도·검색 막대, 철도망 그림, 역 검색·경로 찾기)에 필요한 것을 먼저 받고 나머지는 뒤로 미룬다. 기능과 다 불러온 뒤의 화면은 예전과 같다.

1. `index.html`을 읽자마자 `graph.json`을 받기 시작한다(`<link rel="preload" href="data/graph.json" as="fetch" crossorigin>`). 예전에는 Leaflet과 스크립트를 다 받아 실행한 뒤 `app.js`가 요청했다. `app.js`의 `fetch('data/graph.json')`은 미리 받은 응답을 그대로 쓴다(`crossorigin`이 없으면 fetch와 맞지 않아 두 번 받는다. 시험에서 한 번만 받는 것을 확인했다).
2. 글꼴 CSS(Google Fonts)는 `media="print"`로 받아 두기만 해서 첫 화면을 막지 않는다. `app.js`가 `graph.json`을 다 받은 뒤(`enableFonts`) `media="all"`로 켠다. 글꼴 파일(첫 화면 글자에 약 270KB)이 `graph.json`과 같은 때 받히면 철도망이 그만큼 늦게 오기 때문이다. 그 전에는 기본 글꼴로 보인다(`display=swap`이라 예전에도 글꼴 파일이 오기 전에는 기본 글꼴이었다).
3. `graph.json` → 검사·색인(`indexGraph`) → 역 검색·경로 찾기가 된다.
4. 철도망은 지금 보이는 곳(화면의 2배 넓이)에 닿는 선로만 먼저 그린다(`layers.js` `NetworkLayer`, `edgesInBox`). 서울 도심 줌 12 폰 화면이면 선로 간선의 약 5%다. 나머지는 화면이 놀 때(`requestIdleCallback`, 없으면 `setTimeout`) 한 번에 약 8ms씩 선 모양을 풀어 두고, 다 풀면 묶음(구조 × 본선/측선, 6개)마다 하나씩 전국 선로로 바꾼다. 바꾼 뒤 모습은 예전과 같다(같은 묶음·같은 순서. 아래 결과 참고).
5. 첫 화면 뒤 바로: `basemap.json`(간이 배경 지도).
6. 철도망을 다 그리면 차례로: `extra.json` → `egress.json`(출구 후보 표시를 켠 채 줌 12 이상일 때) → `passage.json` → `places.json`. 그 전에 필요하면 그때 받는다.
   - `extra.json`: 경로 결과·역 시트를 열 때(환승 계단 위치·출구 주변 이름. 받으면 다시 그린다).
   - `egress.json`: 줌 12 이상으로 확대·출구 후보를 켬, 길 안내 시작, 여기서 나가기.
   - `passage.json`: 경로가 출입구·환승 간선을 지날 때, 출구를 눌렀을 때(받기 전에는 출구 직선·환승 옅은 점선, 받으면 다시 그린다).
   - `places.json`: 검색 화면을 열 때(받기 전에는 역 이름 검색만).
   - 쓸 때만 받지 않고 결국 받아 두는 까닭: 지하·재난 때는 인터넷이 끊길 수 있다. 앱을 연 뒤 끊겨도 장소 검색·여기서 나가기·환승 계단 위치를 써야 한다.
7. 장소 검색 열쇠(`UG.places.prepare(index, 8)`)를 화면이 놀 때 8ms씩 나눠 만든다(예전에는 받은 뒤 한 번에 만들어 느린 폰 기준 약 0.6초 멈췄다). 다 만들기 전에 검색하면 남은 부분을 그 자리에서 마저 만든다. 결과는 한 번에 만든 것과 같다(`check_load.js`).

잰 방법: 헤드리스 Chrome(DevTools 프로토콜), 폰 화면 390×844, 내려받기 9Mbps·올리기 1.5Mbps·지연 150ms, CPU 4배 느리게, 캐시 없음. 배경 지도 타일·Photon·OSRM은 막았다(타일은 실제 폰에서는 `graph.json`과 함께 받히므로 실제 시간은 더 걸릴 수 있다). ### 14.2 오프라인 사용 (설치·서비스 워커, 2026-11-11)

한 번 열면 앱과 데이터가 기기에 저장되어 인터넷 없이 동작한다(plan.md 4번). 홈 화면에 추가(설치)할 수 있다.

- 파일: `web\sw.js`(서비스 워커), `web\js\offline.js`(등록과 화면), `web\manifest.webmanifest`(이름 지하로, `start_url`·`scope` = `./`, standalone, 색 = 어두운 화면 `--bg`), `web\icons\`(앱 표시를 헤드리스 Chrome으로 그린 PNG: 192·512, maskable 512, apple-touch-icon 180). `index.html` 앞부분에 `<link rel="manifest">`·`<link rel="apple-touch-icon">`.
- 판: `pages.yml`이 `sw.js`의 `const VERSION = '__VERSION__';` 줄을 커밋 번호 7자리(스크립트 `?v=`와 같은 값)로 바꾸고 바뀌었는지 확인한다. 저장소(Cache Storage) 이름은 `jiharo-<판>`. 배포마다 `sw.js` 글자가 달라지므로 브라우저가 앱을 열 때 새 판을 알아챈다.
- 등록하는 곳: 서비스 워커를 지원하고, 보안 연결이고, 맨 위 창이고, 배포본(스크립트 주소에 `?v=`)이고, claude.ai·claudeusercontent.com이 아닐 때만. claude.ai 미리보기(iframe)·개발용 서버에서는 등록하지 않고 정보 탭 줄도 숨긴다(예전과 같다). 미리보기에 `manifest.webmanifest`가 없으면 그 요청만 실패한다.
- 언제 받나(14.1절과 겨루지 않게):
  1. 첫 화면이 뜬 뒤(`stage('interactive')`) 등록 → 설치: index 페이지(서버에 확인, 이 판의 `?v=`가 있어야 함)와 그 안의 `<script src>` 전부(js 24개 + Leaflet). 하나라도 못 받으면 설치하지 않는다.
  2. 뒤로 미룬 자료를 다 받은 뒤(`stage('idle')`) 데이터 6개(`graph`·`basemap`·`extra`·`egress`·`passage`·`places`, 7.26MB, gzip 2.04MB)를 하나씩 저장한다. 방금 받은 것이라 브라우저 캐시에서 온다(시험: 서버에서 파일마다 한 번만 받음). 첫 방문에 화면이 쓴 글꼴(CSS·글꼴 조각)도 함께 저장한다.
- 응답 방식:

| 요청 | 방식 |
|---|---|
| index 페이지(열기), `js/*.js`, Leaflet, `data/*.json` | 저장한 것 먼저(이 판 저장소). 없으면 받아서 저장 |
| 배경 지도 타일(`tile.openstreetmap.org`) | 받아서 저장(최근 400장, 넘으면 오래된 것부터 지움). 끊겼거나 4초 안에 안 오면 저장한 것. 사용자가 본 타일만 저장하고 미리 받지 않는다(OSM 타일 사용 정책, 브라우저 캐시는 서버의 캐시 기간을 따른다) |
| Google Fonts CSS / 글꼴 파일 | CSS는 타일과 같은 방식, 글꼴 파일은 저장한 것 먼저(합쳐 150개) |
| Photon(장소 검색)·OSRM(도보 길)·manifest·아이콘 | 손대지 않는다(`walk.js`가 도보 길을 따로 저장한다) |
| 발표 무대가 띄운 앱(`?stage=1`)의 페이지·`js`·데이터 | 저장한 것을 쓰지 않고 서버에서 받는다(무대의 3D 는 늘 최신이라 앱이 예전 판이면 이야기가 어긋난다). 타일·글꼴은 위와 같다 |

- 다른 곳(cdnjs·타일·글꼴 CSS)의 no-cors 요청은 CORS 요청으로 다시 만들어 저장한다(세 곳 모두 CORS 허용). 내용을 볼 수 없는 응답은 브라우저가 저장 공간을 크게 잡기 때문이다.
- 새 판: 앱을 열 때 브라우저가 `sw.js`를 확인 → 바뀌었으면 뒤에서 설치(페이지·스크립트는 새로, 데이터는 `If-None-Match`로 물어 안 바뀌었으면 옮김: 시험에서 데이터 6개 모두 304) → 알림 한 줄 '새 버전 — 다시 열면 적용'(길 안내 중이면 알림 없이 정보 탭에만) → 다음에 열 때 `offline.js`가 기다리던 판을 켜고 한 번 다시 불러온다(길 안내 중에는 하지 않음) → 새 판이 예전 판 저장소를 지운다. 쓰는 중에 바꾸지 않는 까닭: 메모리의 철도망과 새 데이터(출구 후보의 노드 번호 등)가 섞이지 않게.
- 화면: 정보 탭 안전 안내 아래 '● 오프라인 준비 중 · 3.4MB' → '● 오프라인 사용 준비됨 · 7.6MB'(끊겨서 못 받으면 '오프라인 준비 멈춤 · 연결되면 이어서', 연결되면 이어 받음), 설치할 수 있으면 '홈 화면에 추가'(안드로이드 Chrome `beforeinstallprompt`), iOS는 '공유 → 홈 화면에 추가' 한 줄. 인터넷이 끊기면(`navigator.onLine`) 검색 막대 오른쪽에 '오프라인'. 설치한 앱으로 열면 저장 공간을 지우지 않게 한 번 부탁한다(`navigator.storage.persist`).
- 검증: `node scripts\check_offline.js` — manifest·아이콘(PNG 크기)·theme-color, `sw.js` 판 자리표시와 `pages.yml`의 바꾸기·확인, 데이터 목록 = `app.js` CFG, 가짜 `self`로 돌린 요청 종류(Photon·OSRM은 손대지 않음)·앱 파일 목록·오래된 것 지우기, `offline.js` 등록 조건(배포본·iframe·claude 도메인·미지원).
- 헤드리스 Chrome 시험(2026-11-11, 이 PC 서버가 `pages.yml`처럼 `/underground-route/`에 gzip·ETag로 냄, 폰 화면 375×812): 첫 방문 → 정보 탭 '오프라인 사용 준비됨 · 7.6MB'(저장소: 앱 32개 7.61MB, 타일 24장 0.86MB, 글꼴 24개 0.48MB) → 페이지와 서비스 워커 모두 오프라인(DevTools) + 서버 끔 → 다시 열기: 앱·철도망·간이 배경 지도·본 곳의 타일(12/12), 역·오프라인 장소 검색, 서울역 → 강남 경로, 길 안내, 여기서 나가기(egress.json 2,065곳)가 동작, 서버 요청 0. 새 판 배포 흉내 → 알림 → 다음에 열 때 새 판·예전 저장소 지워짐. `Page.getAppManifest` 오류 없음, 설치 가능성 오류 없음.
- 한계: 첫 화면의 타일은 서비스 워커가 맡기 전에 받아 저장되지 않는다(다음에 열 때부터). 타일을 저장하지 않은 곳(확대·다른 지역)은 빈 바탕에 간이 배경 지도 선만 보이고 지명은 없다(저장한 타일이 하나라도 뜨면 간이 지도 지명을 숨긴다). 온라인에서 한 번도 쓰지 않은 글자의 글꼴 조각은 오프라인에서 기본 글꼴로 보인다. iOS(저장 한도, Safari의 7일 규칙)는 확인하지 못했다.

## 15. places.json (오프라인 장소 검색 색인)

인터넷 없이 목적지를 찾기 위한 장소 이름표다. 지도 앱처럼 "서울대병원", "역삼동", "OO아파트", "강남구청", "OO초등학교"로 찾게 한다. 온라인 검색(Photon)은 따로 붙이고, 이 파일은 오프라인일 때(또는 온라인 결과와 함께) 쓴다.

- 만드는 스크립트: `scripts\build_places.py` (프로젝트 폴더에서 `python -I scripts\build_places.py --fetch`. 원본이 이미 있으면 `--fetch` 없이 만들기만 한다. 만들기는 약 10초)
- 원본: `data\raw\places\*.json` (Overpass 응답 그대로, 한 번에 하나씩 받음). 시·도 경계는 `data\raw\basemap\admin.json`, 역은 `web\data\graph.json`의 `stations`를 읽기만 한다.
- 검색 함수: `web\js\places.js` — `searchPlaces(index, query, {near: [lat, lon], limit: 10})`. 브라우저에서는 `UG.places.searchPlaces`(전역 `searchPlaces`도 둔다), Node에서는 `require()`. 화면에 붙일 때는 `UG.search.register(provider)`로 검색 제공자를 하나 더하면 된다(이 작업에서는 붙이지 않았다).
- 크기(2026-11-10 빌드): 2,999,976 byte, gzip 840,950 byte. 장소 60,497개. 목표 3,000,000 byte에 맞추려고 일부를 뺐다(아래 '크기 맞추기').
- 출처 표기: © OpenStreetMap contributors (ODbL). OSM 기준 시각 2026-11-10.

### 15.1 형식

```json
{"format": "places-1",
 "attribution": "© OpenStreetMap contributors (ODbL)",
 "osm_base": "2026-11-10",
 "types": ["sido","sigungu","dong","village","station","hospital","university","school","gov","police","fire","library","apartment","landmark"],
 "areas": ["", "강원특별자치도", "경기도", "서울특별시 종로구", "경기도 수원시 장안구", ...],
 "p": [["강원특별자치도", 0, 3777253, 12838207, 0], ["서울대학교병원", 5, 3757961, 12699900, 3], ...]}
```

`p`의 한 줄이 장소 하나다: `[이름, 종류 번호, 위도×1e5, 경도×1e5, 지역 번호, (다른 이름 목록)]`

| 칸 | 내용 |
|---|---|
| 이름 | 표시 이름(OSM `name`). 역은 `<역 이름>역`. 아파트 건물에서 온 단지는 동 번호를 뗀 이름 |
| 종류 번호 | `types` 위치 |
| 위도·경도 | × 100000 정수(그래프와 같은 정밀도) |
| 지역 번호 | `areas` 위치. 그 점이 든 시·도 + 시·군·구(+ 일반구). 같은 이름(여러 `중구청`, `신사동`)을 구별하는 데 쓴다. 시·도 항목은 빈 문자열, 시·군·구 항목은 상위 지역(예: `장안구` → `경기도 수원시`) |
| 다른 이름 | 있을 때만(6번째 칸). OSM `short_name`·`alt_name`·`official_name`·`old_name`(최대 2개), 역은 `stations[].names`의 별칭 |

- 정렬: 종류 → 지역 → 이름(gzip이 잘 줄도록). 순서에 뜻은 없다.
- 지역 이름은 2026-11-10 OSM 그대로다(예: `전남광주통합특별시`, 인천 `제물포구`).

### 15.4 검색 순위 (`web\js\places.js`)

1. 정규화(이름과 질의어 똑같이): 소문자로 바꾸고, 괄호 안 내용을 지우고, 한글·영문·숫자·자모가 아닌 글자(공백, `·`, `-` 등)를 지운다. 세 글자 이상이면 끝의 `역`을 뗀다(`서울역` → `서울`). `동`은 떼지 않는다.
2. 열쇠(장소마다 처음 검색할 때 한 번 만들어 둔다): 본 이름과 다른 이름 각각에서 더 만든다.
   - 앞의 시·도 이름을 뗀 것: `서울특별시강남구청` → `강남구청`
   - 시·도 줄임: `세종특별자치시청` → `세종시청`, `부산광역시청` → `부산시청`, `제주특별자치도청` → `제주도청`
   - `대학교` → `대`: `서울대학교병원` → `서울대병원`
   - 행정동 번호를 뗀 것(`dong`만): `역삼1동` → `역삼동`, `종로1·2·3·4가동` → `종로동`. 그래서 "역삼동"으로 역삼1·2동도 나온다.
3. 맞춤 점수: 같음 1000 > 앞부분 600 > 가운데 300. 앞부분·가운데는 남는 글자 하나에 8점씩 깎는다(최대 150). 별칭 열쇠로 맞으면 20점 깎는다.
4. 질의어 변형: 끝의 `아파트`를 뗀 질의어로도 맞춘다(10점 깎음, 아파트가 아닌 장소는 300점 더 깎음). OSM 이름이 `은마`인 단지를 "은마아파트"로 찾기 위한 것이다. 이름 쪽에서 `아파트`를 떼지 않는 것은 "강남"이 `강남아파트`와 '같음'으로 맞아 강남구보다 앞서는 것을 막기 위해서다.
5. 종류 가산점: 시·도 80, 시·군·구 70, 동 60, 대학 55, 병원·관공서 50, 역 45, 명소 40, 아파트 30, 학교 25, 경찰·소방·도서관 20, 리 15. 역은 이름에서 `역`을 떼고 맞추므로, `수원시청`·`강남구청`처럼 시설과 이름이 같아지면 시설이 앞서도록 낮게 두었다.
6. 거리 가산점(`near`를 줄 때): `150 / (1 + 거리km / 2)` — 0km 150점, 2km 75점, 10km 25점, 100km 3점. 맞춤 단계 사이의 차이(약 400점)를 넘지 않으므로, 가까운 곳은 같은 단계 안에서만 앞선다(예: 여러 `신사동` 중 가까운 것).
7. 초성 검색: 질의어가 자음(ㄱ~ㅎ)만이면 열쇠의 초성으로 같은 규칙을 쓰고 100점 깎는다(`ㅅㅇㄷㅂㅇ` → 서울대학교병원, `ㄱㄴㄱㅊ` → 강남구청).
8. 점수가 같으면 이름이 짧은 것이 먼저다. 결과는 `{name, type, area, lat, lon, score}`이고, `near`를 주면 `distance_km`도 붙는다.

- 속도(이 PC, Node 24): JSON 풀기 약 40ms, 첫 검색 때 열쇠 만들기 120~280ms(62,627개), 검색 한 번 2~5ms(전체를 한 번 훑는다). 휴대폰에서는 재지 않았다. 화면이 놀고 있을 때 `UG.places.prepare(index)`를 미리 불러 두면 첫 검색이 빨라진다. `prepare(index, budgetMs)`로 시간을 주면 그만큼만 하고 멈췄다가(다 못 했으면 `null`) 다음에 이어서 한다. 웹은 places.json을 받으면 화면이 놀 때 8ms씩 나눠 만든다(14.1절).

### 16.1 `fast` (빠른 환승)

원본 한 행의 뜻: `노선명` 열차가 `역명`에서 `종착역명` 쪽으로 갈 때, `환승선`(`환승이후역명` 방향)으로 갈아타는 계단에 가장 가까운 차량(`차량순서`, 1 = 그 열차의 맨 앞)과 출입문.

| 키 | 내용 |
|---|---|
| `s` | 환승역(`stations` 번호) |
| `line` | 타고 온 노선(`tables.lines` 번호). 그 역 허브의 노선이다. 지선 열차면 지선(예: 신도림에서 끝나는 신정지선 열차 → `2호선 신정지선`) |
| `to_line` | 갈아탈 노선(`tables.lines` 번호) |
| `prev` | `toward` 쪽으로 가는 열차가 `s` 바로 전에 서는 역(`stations` 번호). 없으면 `null`(아래) |
| `prev_alt` | 있을 때만. 같은 방향의 다른 앞 역 목록(지선이 합쳐지는 역, 급행이 건너뛴 역). 예: 1호선 창동 인천 방면 `prev` 방학, `prev_alt` [도봉산] |
| `toward` | 자료의 종착역명 그대로(괄호 포함). 빈 문자열일 수 있다 |
| `next`, `next_name` | 갈아탄 뒤 첫 역(`stations` 번호, 못 찾거나 자료에 없으면 `null`)과 자료의 역 이름(없으면 빈 문자열) |
| `car`, `door` | 차량 번호(1 = 열차 진행 방향 맨 앞), 출입문 번호(자료에 없으면 `null`) |
| `cars` | 그 노선의 편성 길이(량) |
| `pos` | `front`·`middle`·`back` — 열차 진행 방향 기준 위치 |

**길 안내에서 쓰는 법**: 환승 단계 직전에 걸어서 지난 역(앞 역)이 `prev` 또는 `prev_alt`에 있으면 걷는 방향이 그 열차와 같으므로 `pos`를 그대로 쓴다. 아니면 `front` ↔ `back`을 바꾸고 `middle`은 그대로 둔다. `(s, line, to_line)`이 같은 항목이 방향마다 있으므로, 갈아탄 뒤 첫 역이 `next`와 같은 항목을 먼저 고른다(`next`가 `null`인 항목은 방향과 상관없는 항목).
- `prev`가 `null`인 항목은 두 가지뿐이고, 둘 다 위 규칙(같지 않으면 뒤집기)으로 맞다.
  1. 열차가 `s`에서 출발하는 경우(예: 부산 3호선 수영 → 대저 방면, 경강선 판교 → 여주 방면). 이 역에 걸어서 도착하는 사람은 반드시 열차가 떠나는 쪽에서 오므로 뒤집는 것이 맞다. 82개.
  2. 열차 방향을 모르지만 `pos`가 `middle`인 경우. 뒤집어도 `middle`이다. 35개.
- 열차 방향을 모르고 `middle`도 아닌 행은 앞뒤를 정할 수 없어 넣지 않았다(81행). 대부분 종착역명이 빈 행(1·3·4호선 서울역·시청·종로3가 등)이고, 나머지는 relation이 그 역을 지나 더 가는데 그 역에서 끝나는 열차(신분당선 강남, 인천 1호선 계양, 3호선 수서, 7호선 부평구청, 경의중앙선 용산, 수인분당선 수원)다. 이런 열차가 어느 쪽에서 오는지는 추측하지 않았다.

**맞추기 규칙** (`build_extra.py`)
- 노선: `(운영기관, 노선명)` → 정식 노선 이름(3.1절). `N호선`은 부산교통공사·대구교통공사면 `부산 N호선`·`대구 N호선`, 나머지(서울교통공사·코레일·인천교통공사 7호선)는 `N호선`. `경의중앙` → `경의중앙선`, `수인분당` → `수인분당선`, `경춘` → `경춘선`, `경강` → `경강선`, `동해` → `동해선 광역전철`, `우이신설` → `우이신설선`, `용인에버라인` → `용인경전철`, `자기부상` → `인천공항 자기부상철도`, `인천1호선`·`인천2호선` → `인천 1호선`·`인천 2호선`.
- 역: 이름을 `build_graph.py`의 `normalize_name`으로 정리하고(괄호·공백·끝의 '역'), 없으면 옛 이름 표(`DEPTH_ALIASES`)로 다시 찾는다. 그 노선(지선 포함) 허브가 있는 역만 고른다. `종착역명`·`환승이후역명`도 같은 방법이다.
- 같은 노선 표기끼리의 환승(예: `2호선` 신도림 → `2호선`)은 본선 ↔ 지선 환승이다. 갈아탄 뒤 첫 역과 이어진 쪽을 갈아탈 노선으로, 나머지를 타고 온 노선으로 본다.
- `prev`: `line_routes`(10절)에서 그 노선의 relation 중 `s` 뒤에 종착역이 있는 것의 `s` 바로 앞 정차역. 순환(2호선)은 종착역까지 정차 수가 적은 방향만 쓴다(2호선 자료의 종착역명은 대개 바로 다음 역이다). relation 하나로 안 되면(지선이 갈리는 곳 등) 모든 relation을 이은 방향 그래프에서 `s` → 종착역 최단 경로의 첫 역을 구하고, relation에서 (앞 역, `s`, 그 첫 역)으로 이어진 앞 역을 쓴다. 종착역이 `s` 자신이면 `s`가 끝인 relation의 바로 앞 역. 앞 역이 여럿이면 `s`에서 가까운 것을 `prev`로, 나머지를 `prev_alt`로 둔다.
- `cars`: 아래 표의 값, 표에 없으면 그 노선 자료의 최대 차량순서. 표는 일반 지식으로 넣었고 온라인으로 다시 확인하지 않았다. 자료의 차량순서가 표보다 크면 그 행을 뺀다(인천 2호선 검암 `6호차` 2행: 2량 열차라 잘못된 값).
  - 표: 1~4호선 10, 5~7호선 8, 8호선 6, 신분당선·공항철도·수인분당선 6, 경강선 4, 인천 1호선 8, 인천 2호선·우이신설선·의정부경전철·부산김해경전철 2, 용인경전철 1, 부산 1호선 8, 부산 2호선 6, 대구 1·2호선 6, 대구 3호선 3.
  - 자료 최대값을 쓴 노선: 9호선 4, 경의중앙선 8, 경춘선 7, 동해선 광역전철 4, 부산 3호선 4, 부산 4호선 6. **9호선은 지금 6량 열차가 다닌다고 알고 있으나 확인하지 못했다.** 자료가 4량 기준(같은 계단이 한 방향 4-4, 반대 방향 1-1)이라 자료대로 4를 썼다. 경춘선 7은 실제 편성과 다를 수 있다(확인 못 함).
- `pos`: 차량 가운데 위치 `x = (car − 0.5) / cars`가 1/3 미만이면 `front`, 2/3 초과면 `back`, 나머지 `middle`. 10량: 1~3 / 4~7 / 8~10, 8량: 1~3 / 4~5 / 6~8, 6량: 1~2 / 3~4 / 5~6, 4량: 1 / 2~3 / 4, 2량: 1 / - / 2. 차량 번호 대신 가운데로 재는 것은 방향을 뒤집었을 때(`car` → `cars + 1 − car`) `front` ↔ `back`이 정확히 바뀌고 2량 열차도 앞·뒤로 나뉘게 하려는 것이다(`car ≤ cars/3`로 재면 10량의 7호차가 `back`인데 뒤집은 4호차는 `middle`이 된다).
- 맞춘 결과가 똑같은 항목은 하나만 넣었다(33개 뺌. 원본에 똑같은 행이 34행 있다).

### 16.2 `exits` (출구 주변 이름)

- 열쇠: 역 번호(문자열) → 출구 번호(문자열, `entrances.ref`와 같은 꼴: `"1"`, `"10"`, `"9-1"`) → 이름 목록.
- 역 맞추기: `호선`(1~9) + `전철역명`으로 16.1절과 같은 방법. 한 역에 여러 호선 행이 있으면(예: 서울역 1·4호선) 출구 번호별로 합친다.
- 이름: 띄어쓰기만 다른 것은 하나로 합치고, 출구마다 4개까지 남긴다. 넘으면 동·가 이름(예: `동자동`, `봉래동1가`) → 큰 시설(이름이 역·대학·병원·구청·공원·시장·학교·아파트 등으로 끝남) → 나머지 순으로 고르고, 남긴 이름은 자료 순서(가나다순)대로 둔다. 4개로 줄인 출구는 581개다(6개로 두면 `exits`가 약 25KB 더 크다).
- 출구 번호가 아닌 행(반포 `00(연결통로)` 1행)은 뺐다.
- 서울교통공사 1~9호선 역만 있다(9호선은 서울교통공사가 운영하는 구간).

## 17. 갈림길 안내 (junctions.js)

역 사이를 걷다가 선로가 갈라지는 곳에서 다른 노선의 지선이나 차량기지로 잘못 들어가지 않게, 경로 위의 갈림길을 찾아 '어느 쪽으로 가야 하는지'를 알려 준다. 그래프에 저장하는 내용은 아니고, 탐색 결과(간선 목록)에서 그때 계산한다.

- 파일: `web\js\junctions.js` (DOM 없음, 브라우저 `UG.junctions`, Node `require()`). `graph.js` 다음에 불러온다.
- 검증: `node scripts\check_junctions.js` (아래 시험 결과).
- 화면: 단계 목록의 갈림길 줄과 요약 칩(`panel.js`), 길 안내 체크포인트(`guide.js`의 `buildCheckpoints`: 역 사이 갈림길마다 `kind: 'junction'`, `jn` = `plan.junctions` 번호, 큰 단추 '통과'), 지도 갈림길 그림(`app.js`의 `forkData`, `layers.js`의 `GuideLayer.setFork`). 갈림길 뒤에서 '앞이 막힘'을 누르면 그 갈림길 노드에서 다시 찾는다.

### 17.1 API

| 함수 | 하는 일 |
|---|---|
| `findJunctions(G, route, options)` | `G` = `graph.indexGraph` 결과, `route` = `router.findRoute(...)` 결과 또는 그 `path`(`[{e,u,v}]`). 경로 순서대로 갈림길 목록을 돌려준다. `options`로 아래 기준값을 바꿀 수 있고, `options.skipped`에 배열을 주면 안내하지 않은 갈래를 이유(`crossover`·`behind`·`stub`·`short-link`·`same-next-station`·`rejoins-route`)와 함께 넣어 준다 |
| `junctionText(j)` | 한국어 안내 문장. 예: `갈림길 · 강동에서 약 260m · 오른쪽 갈래로 (5호선 마천지선 · 둔촌동 방면) · 왼쪽 갈래는 5호선 (길동 방면)`. 갈래 방향이 서로 다르면 `오른쪽 선로로 (…) · 왼쪽은 …`, `직진 선로로 (…)` |
| `junctionGlyph(j)` | Y자 그림 자료. 걷는 방향이 위(0°), 오른쪽 +. 들어오는 선은 아래(180°). 100×100 상자 기준 좌표(`center` 50,50 → 갈래 끝 `x`,`y`)라 `<line>` 몇 개로 그리면 된다. 실제 갈림 각도(`angle`)는 5~15°로 작아서 그림용 각도(`draw`)는 갈래 사이를 30° 이상 벌리고 ±75° 안에 둔다 |

갈림길 하나(`j`):

| 키 | 내용 |
|---|---|
| `node`, `lat`, `lon` | 갈림길 노드와 위치 |
| `pos`, `at_m` | 경로 간선 `path[pos]`를 지나면 갈림길(`guide.js` 체크포인트의 `pos`와 같은 뜻), 경로 시작부터 거리(m, 출입구까지 걷는 거리는 넣지 않음) |
| `structure` | 갈림길로 들어오는 선로의 구조(`tunnel`·`bridge`·`ground`) |
| `prev`, `fromPrev_m` | 직전에 지난 역 `{si, name}`과 그 역(선로 위 부착점)부터 거리 |
| `next`, `toNext_m` | 경로에서 다음에 닿는 역과 거기까지 거리 |
| `chosen`, `alternatives` | 갈 갈래, 다른 갈래 목록 |

갈래: `edge`(첫 간선), `angle`(꺾인 각도, 오른쪽 +), `dir`(`left`·`right`·`straight`), `side`(안내 말: `왼쪽`·`오른쪽`·`직진`·`왼쪽 갈래`·`가운데 갈래`·`오른쪽 갈래`), `rank`(왼쪽부터 0), `kind`(`line` 노선 선로·`depot` 차량기지·`deadend` 막다른 선로·`track` 이름 없는 선로), `name`(예: `2호선 성수지선`, `차량기지`, `차량기지 지축기지선`), `via`(노선 선로로 이어지기 전에 지나는 서비스 선로: `연결선`·`측선`·`차량기지 선로`), `toward`(방면 역), `structure`(첫 간선의 구조).

### 17.2 규칙

- 갈림길 후보: 경로가 선로 간선(`kind` = `track`)으로 들어와 선로 간선으로 나가는 노드에 다른 선로 간선이 더 있는 곳. 승강장·환승·출입구·지상 걷기 간선은 보지 않는다(역은 이미 체크포인트다).
- 갈래 따라가기(`followBranch`): 갈래로 나가 선로만 따라 최대 6km 걷는다. 갈림길을 만나면 건넘선이 아닌 것 → 같은 선 이름 → 덜 꺾이는 것 순으로 고르고, 100°보다 꺾이는 선(되돌아가기)은 고르지 않는다. 역 2곳에 닿으면 멈춘다. 고른 갈래는 경로가 선로인 동안 경로를 그대로 따른다.
- 안내하지 않는 갈래(순서대로)
  1. 건넘선(`svc` = `crossover`). 단, 건너가서 다른 노선의 본선을 타고 경로와 다른 다음 역으로 가면 갈림길로 본다(신도림 서쪽 신정지선 → 2호선 본선 문래 방면).
  2. 뒤쪽 선로: 꺾인 각도가 100°보다 큼(뒤에서 합류하는 선로, 앞으로 걷는 사람은 고를 일이 없다).
  3. 50m보다 짧은 막다른 선로.
  4. 150m 안에서 같은 노선(선 이름이 같거나, 이름이 없으면 노선 묶음이 겹침)의 옆 선로에 붙는 짧은 연결선(건넘선 태그가 빠진 것).
  5. 경로와 같은 다음 역에 닿는 나란한 선로. 두 갈래의 선 이름이 서로 다르면 안내하고(강동 서쪽 5호선 본선·마천지선처럼 같은 역의 다른 승강장으로 갈라짐), 방면을 `강동 지나 길동`처럼 그다음 역까지 적는다.
  6. 2km 안에서 경로의 앞쪽 노드로 다시 합쳐지는 선(대피선·통과선, 9호선 사평역 옆 급행 선로). 단 그 사이 지상 노출이 경로보다 많거나 경로의 1.5배 + 100m보다 길면 안내한다(삼송 → 지상역 지축 → 구파발로 도는 일산선).
- 방향: 들어오는 경로 선 모양의 마지막 80m와 갈래 선 모양의 처음 80m(`lookM`)로 방위각을 재서 꺾인 각도를 구한다. |각도| ≤ 20°면 직진. 갈래 둘 이상이 같은 쪽(대개 둘 다 직진)이면 각도 순서로 `왼쪽 갈래`·`오른쪽 갈래`(셋이면 `가운데 갈래`)라 한다. 두 갈래의 각도 차이가 3°보다 작으면 240m 지점의 각도로 순서를 정한다.
- 이름표: 갈래에서 2km 안의 이름 있는 첫 간선으로 `<짧은 노선 이름> <선 이름>`(선 이름이 노선 이름과 같으면 노선 이름만). 선 이름에 `기지`가 들었거나, 첫 간선이 차량기지·측선(`yard`·`siding`)이고 그 뒤로 이름 있는 선로가 없거나 따라간 길의 절반 이상이 차량기지·측선이면 `차량기지`. 방면은 따라가서 처음 닿는 역(고른 갈래는 경로의 다음 역).
- 기준값(`DEFAULTS`): `lookM` 80, `straightDeg` 20, `behindDeg` 100, `crossoverM` 150, `stubM` 50, `walkM` 6000, `nameM` 2000, `rejoinM` 2000.

- 건대입구 → 용답은 지상(고가)인 성수를 피해 지하로만 돌아가는 경로라 성수를 지나지 않는다. 성수지선은 성수역에서 따로 승강장 선로를 쓰고(본선과는 역 남동쪽의 차량기지·건넘선 선로로만 이어짐), 그래서 성수 → 용답에는 선로 갈림길이 없다. 성수에서 본선 ↔ 지선은 환승 간선(허브 사이 23m)으로 안내된다.
- 강동 → 길동은 강동의 길동행 승강장 선로(부착점 912)를 쓰는데, 이 선로는 강동~길동 사이에 갈라지지 않는다. 같은 쪽 선로의 갈림은 강동 서쪽(천호 → 길동 시험)에 있다.

### 17.4 한계

- 좌우는 OSM 선 모양으로만 정한다. 실제 분기기 위치·좌우 배치와 다를 수 있고 현장에서 확인하지 않았다. 갈림 각도가 3°보다 작게 붙어 있는 곳(예: 강동 서쪽, 두 갈래가 4m 떨어진 승강장 부착점으로 곧게 그려짐)은 240m 앞 각도로 순서를 정해 특히 불확실하다.
- 갈림길로 들어오는 선로가 짧고 바로 앞이 승강장 간선이면 들어오는 방향을 그 짧은 선로로만 잰다.
- 막은 간선(앞이 막힘)도 갈래로 보여 준다(선로는 그대로 있으므로).
- 일반철도 본선(경부고속선 등)은 역 사이가 6km보다 길어 방면이 비는 갈래가 있고, 역 구내에서 갈림길이 수백 m 안에 여러 개 이어진다(합치지 않음). 지하 경로에서는 드물다.
- 건넘선 태그가 빠진 선은 4번(150m, 같은 노선) 규칙으로만 거른다. 다른 노선으로 이어지는 짧은 연결선은 갈림길로 남는다.

## 18. 여기서 나가기 (exithere.js)

지금 있는 곳에서 지하로 걸어 닿는 '지상으로 나가는 곳'을 가까운 순서로 보여 주고, 고르면 그곳까지 다시 안내한다(plan.md 결정 2026-11-10: 역 출구 + 터널 출입구 · 수직구·비상 출구 · 차량기지, 전시에는 출입 통제를 따지지 않음).

- 지금 위치: 길 안내 중이면 쓸 만한 GPS(22절: 6초 안에 온 정확도 80m 안 위치, 잃은 뒤 추정 위치가 지하 구간이면 엄하게 다시 잡음)가 경로 150m 안에 있을 때 그 경로 위 자리, 경로에서 멀면 400m 안 가장 가까운 선로(`snapToNetwork`), GPS 가 없으면 추정 위치(마지막 확인 지점 + 걸은 시간 × 속도) → `guide.locateOnPath`로 그래프 위 자리(선로 위 점). 역 시트에서는 그 역의 허브들.
- 거리: 지하 간선만(가중치 1: 터널·지하 승강장·지하 환승·출입구) 따라가는 다익스트라, 5km 까지, 막은 간선 제외. 출입구 간선은 지상 허브에 붙은 것도 지난다(그 역 안에서 출구로 나갈 때).
- 후보(`findExits`): 역 출구(`entrances`, 역마다 가까운 2개, 역 시트의 그 역은 8개), `egress.json`(`format: 'egress-1'`, `scripts\build_egress.py`)의 `portal`(노드 `node`·`nodes` 중 가까운 것), `shaft`·`emergency_exit`(선로 위 점 `edge`·`t`와 나란한 선로 `also`, 같은 간선이면 간선을 따라 바로), `depot`(기지 노드 중 지하 거리 + 기지 안 지상 길(직선 × 1.3)이 가장 짧은 것). 지하 걷는 거리 순 10개.
- `egress.json`은 처음 필요할 때 한 번 받는다(출구 후보 표시를 켠 채 줌 12 이상, 길 안내 시작, 여기서 나가기). 없으면 역 출구만 쓴다.
- 긴 터널: 역 사이(갈림길 제외)가 1.5km 넘고 경로 앞쪽에 수직구·비상 출구가 있으면 길 안내 카드에 '○○m 앞 비상 출구'(`onRoute`, 보조 줄이 비어 있을 때만).
- 고른 뒤 '앞이 막힘': 같은 곳으로 지하로(노출을 늘리지 않고) 다시 갈 수 있으면 다시 안내하고, 아니면 다시 출발할 곳에서 후보를 다시 보여 준다. 아직 아무 곳도 확인하기 전(선로 위 점에서 출발)이면 가던 쪽 첫 간선까지 막고 반대쪽으로만 찾는다(`only`).
- 2026-11-10 시험(`check_exit_here.js`): 공덕→마포 314m 지점에서 공덕 8번 340m · 공덕 1번 348m · 마포 4번 357m …(6~8ms). 3호선 백석–대곡 터널 출입구 112m 앞에서 1순위 = 그 출입구. egress.json 수직구는 1개(8호선 강동구청–몽촌토성)뿐이라 긴 일반철도 터널은 예시 수직구로 시험했다.
- 한계: 수직구·비상 출구에 지상 계단이 있는지는 OSM 에 없어 확인하지 못했다. 차량기지의 '나가는 곳'은 출입문 자료가 없으면 근사 위치다(egress.json `note`).

## 19. egress.json (역 출구가 아닌, 지상으로 나가는 곳)

역 출구가 막혔을 때 쓸 다른 출구 후보다. 터널 출입구(선로가 지상으로 나오는 곳), 터널 중간의 환기구·수직구·비상 출구, 차량기지를 담는다. 역 출구(`railway=subway_entrance`)는 `graph.json`의 `entrances`(8절)에 이미 있어 넣지 않았다. 출입 통제(울타리·문)는 따지지 않는다. 전시에는 막혀 있어도 뚫고 간다고 본다(`docs\plan.md`의 '지상으로 나가는 곳').

- 만드는 스크립트: `scripts\build_egress.py`. 프로젝트 폴더에서 `python -I scripts\build_egress.py`를 실행한다. 원본이 없으면 `--fetch`를 붙여 Overpass에서 받는다. 기본 서버가 안 될 때는 `--server <URL>`로 다른 공개 서버를 맨 앞에 둔다. 만들기는 약 3~10초 걸린다.
- 원본: `data\raw\egress\*.json`(Overpass 응답 그대로). 쿼리 원문은 같은 이름의 `.overpassql`이다. `web\data\graph.json`, `data\derived\ways_kr.json`, `data\raw\basemap\admin.json`은 읽기만 한다.
- 점검 결과: `data\derived\egress_report.json`. 태그 패턴별 개수, 터널에서 80m 밖이라 뺀 후보, 기지 목록, 율현터널·GTX-A 회랑 확인, 검사 결과를 담는다.
- 크기(2026-11-10 빌드): 661,264 byte, gzip 94,977 byte.
- 출처 표기: © OpenStreetMap contributors (ODbL). OSM 기준 시각은 2026-11-10이다.

### 19.1 형식

```json
{"format": "egress-1", "attribution": "© OpenStreetMap contributors (ODbL)", "osm_base": "2026-11-10",
 "items": [
  {"k": "portal", "name": "5호선 마천–거여 터널 출입구", "lat": 37.49, "lon": 127.15,
   "node": 1234, "edge": 5678, "t": 0.0, "lines": [7], "note": "선로 2개 · 바깥: 지상 · ...",
   "nodes": [1234, 1240], "osm": "node/111"},
  {"k": "shaft", "name": "...", "lat": .., "lon": .., "node": null, "edge": 11450, "t": 0.9975,
   "lines": [..], "note": "...", "also": [[11451, 0.0045]], "osm": "node/14293331599"},
  {"k": "depot", "name": "방화차량기지", "lat": .., "lon": .., "node": 2345, "edge": null, "t": null,
   "lines": [..], "note": "...", "nodes": [...], "approach": "tunnel", "gate": "node/222", "osm": "way/333"}]}
```

| 키 | 내용 |
|---|---|
| `k` | 종류: `portal`(터널 출입구), `shaft`(환기구·수직구), `emergency_exit`(비상 출구), `depot`(차량기지·조차장) |
| `name` | 표시 이름. OSM 이름이 있으면 그대로 쓴다. 없으면 `<짧은 노선 이름> <역A>–<역B> <종류>`로 짓는다(아래) |
| `lat`, `lon` | 지상으로 나가는 점(소수 5자리). 출입구는 그 노드, 환기구·비상 출구는 OSM 점, 기지는 나가는 곳(출입문 또는 도로에 가까운 경계 지점) |
| `node` | 그래프 노드 번호. 출입구는 대표 출입구 노드, 기지는 대표 측선 노드(아래). 환기구·비상 출구는 `null` |
| `edge`, `t` | 그 점이 붙은 선로 간선 번호와 간선 위 위치(0 = 간선 `a` 쪽 끝, 1 = `b` 쪽 끝, 선 모양 길이 비율). 출입구는 대표 노드에 붙은 터널 쪽 간선(t는 0 또는 1). 기지는 `null` |
| `lines` | 노선 번호 목록(`tables.lines` 위치). 붙은 간선들의 `ls`를 합친 것 |
| `note` | 사람이 읽는 설명(한국어). 근사·추정이면 여기에 밝힌다 |
| `nodes` | (출입구·기지) 묶은 그래프 노드 전체. 출입구는 60m 안에서 묶은 나란한 선로의 출입구 노드들, 기지는 기지 안 측선 노드들 |
| `also` | (환기구·비상 출구) 80m 안에 있는 다른 터널 간선 `[간선, t]`(최대 4개). 상·하행이 따로 그려진 터널의 반대 선로다 |
| `approach` | (기지) 본선과 이어지는 길: `tunnel`(본선과 만나는 곳이 터널 안이거나, 진입 선로에 터널이 있음 = 지하에서 걸어 들어갈 수 있음) 또는 `surface` |
| `gate` | (기지) 나가는 곳으로 쓴 OSM 출입문 노드(`node/<id>`). 없으면 `null` |
| `osm` | 출처 OSM 요소(`node/<id>`, `way/<id>`, `relation/<id>`). OSM 기지 면 밖의 측선 묶음은 `graph-yard/<번호>`(그래프에서 만든 것) |

- 같은 길 찾기 그래프로 갈 수 있는 것만 넣었다. 노드가 있으면 그 노드는 역이 있는 연결 요소에 든다.
- 정렬: 종류(`portal` → `shaft` → `emergency_exit` → `depot`) → 시·도 → 이름. 순서에 뜻은 없다.

### 19.2 터널 출입구 (`portal`)
- `graph.json`에서 노드 `f`에 1(터널 출입구)이 있는 노드를 모두 쓴다. 터널 선로와 교량·지상 선로가 만나는 점이다.
- 60m 안의 출입구는 하나로 묶는다(상·하행 선로, 나란한 선로). 본선 출입구를 먼저 씨앗으로 삼고, 씨앗에서 60m 안의 출입구를 그 묶음에 넣는다. 묶은 노드는 모두 `nodes`에 넣는다. 반대 선로를 걷는 사람도 자기 선로의 출입구 노드로 찾을 수 있게 하기 위해서다.
- 이름: `<짧은 노선 이름> <역A>–<역B> 터널 출입구`. 역A는 터널 쪽으로 선로를 따라가서 처음 닿는 역, 역B는 바깥쪽으로 처음 닿는 역이다(80km 안, 선로 간선만). 두 역이 같거나 하나만 있으면 `<역> 부근 터널 출입구`라고 쓴다. 노선 이름은 도시철도·광역전철 노선을 먼저 쓰고, 없으면 선 이름에서 온 노선 이름(예: `경부고속선`)을 쓴다(최대 2개, `·`로 잇는다).
- `note`: 묶은 선로 수, 바깥 구조(`지상`·`교량`), 측선 여부, 터널 쪽·바깥쪽 첫 역. 바깥이 `교량`이면 나가도 다리 위다(강·골짜기 위일 수 있다).
- 뺀 것: 기지 안의 측선 출입구(모든 선로가 측선이고 기지 항목의 노드이거나 기지 면 안·100m 안), 역과 이어지지 않은 선로의 출입구(레일바이크, 관광철도, 석탄부두선 등).
- `osm`: 그 좌표에 있는 OSM 노드 중 터널 way와 터널 아닌 way가 함께 쓰는 노드.

### 19.3 환기구·수직구 (`shaft`), 비상 출구 (`emergency_exit`)
- OSM에서 받은 점·면 중 아래 조건에 맞고, 그래프의 터널 선로 간선에서 80m 안에 있는 것만 넣는다.
  - `shaft`: `man_made=ventilation_shaft`, `railway=ventilation_shaft`, `building=ventilation_shaft|ventilation`, `man_made=tower` + `tower:type=ventilation`, 이름에 `수직구·환기구·환기탑·환기실·환기소·환기시설·배기구·급기구·사갱·작업구`.
  - `emergency_exit`: `entrance=emergency`, `exit=emergency`, `railway=emergency_exit`, 이름에 `비상구·비상탈출·비상출구·비상계단·피난구·탈출구`.
- 붙이기: 풀어낸 터널 간선 선 모양에서 가장 가까운 점을 찾아 `edge`·`t`로 적는다. 80m 안의 다른 터널 간선(가장 가까운 것보다 40m 안쪽으로 더 먼 것까지)은 `also`에 넣는다. 30m 안의 같은 종류 점은 하나로 합친다.
- 이름: OSM `name`. 없으면 `<노선> <역A>–<역B> 환기구·수직구`(또는 `비상 출구`). 역A·역B는 간선 양쪽으로 처음 닿는 역이다.
- 지상으로 올라가는 계단·사다리가 실제로 있는지는 OSM에 없다. 모든 항목의 `note`에 '확인 안 됨'으로 적었다.

### 19.4 차량기지 (`depot`)
- 후보(OSM): 이름에 `차량기지·차량사업소·검수고·검수기지·정비기지·차량정비·주박기지·차량관리단·철도차량·기지·사업소·정비단·차량센터`가 든 철도 용지(`landuse=railway`) 면, 그리고 `railway=depot|yard|workshop|wash|traverser`. 이름에 '기지'가 든 선로 way(예: `오송정비기지선`)와 군사 시설 이름은 뺀다.
- 묶기: 큰 면부터 대표로 삼고, 그 안에 드는 작은 면·점(건물, `railway=yard` 점 등)은 같은 기지로 묶는다. 이름 없는 `railway=depot|yard` 점은 그 점을 품은 철도 용지 면을 경계로 쓴다.
- 기지 노드: 선 모양이 기지 면 안을 지나는 선로 간선 중 측선(`svc != 0`) 간선의 양 끝 노드(`nodes`). 측선이 없으면 면 안을 지나는 모든 선로 간선의 양 끝을 쓴다(`note`에 밝힘). 점으로만 그린 기지는 400m 안. 노드의 절반 이상이 겹치는 기지는 하나로 합친다.
- OSM 기지 면 밖의 큰 측선 묶음도 넣는다: 측선(`yard`·`siding`) 간선이 이어진 묶음 중 `yard` 길이가 2km 이상이고, 노드의 30% 이상이 이미 OSM 기지에 들지 않은 것(`osm`이 `graph-yard/<번호>`). 차량기지·조차장·큰 역 구내가 섞여 있다. 이름은 묶음의 선 이름 중 `기지·검수·주박·차량·조차장`이 든 것(예: `지축기지선 측선`), 없으면 `<가까운 역> 부근 측선·기지`.
- 대표 노드(`node`): 기지 노드 중 역이 있는 연결 요소에 들고(길 찾기로 갈 수 있음) 나가는 곳에 가장 가까운 것.
- 나가는 곳(`lat`, `lon`)
  1. 기지 경계 40m 안의 OSM 출입문(`barrier=gate|lift_gate|sliding_gate|swing_gate|entrance|...` 또는 `entrance=*`). 여러 개면 이름에 `정문`이 든 것, 그다음 문 종류, 그다음 공공 도로에 가까운 것. `gate`에 그 노드를 적는다.
  2. 출입문이 없으면 경계를 20m 간격으로 짚어 공공 도로(`highway=trunk|primary|secondary|tertiary|unclassified|residential|living_street|road|pedestrian` 등, 기지 안 도로 제외)에 가장 가까운 경계 지점. 근사이고 `note`에 '근사'라고 밝힌다.
  3. 경계가 없는 기지(점, 측선 묶음)는 측선 노드 중 공공 도로에 가장 가까운 곳의 도로 위 점(400m 안).
- `approach`: 기지 노드에서 선로를 따라 본선(`svc = 0`) 간선이 붙은 첫 노드까지 가장 짧은 길을 찾는다. 그 노드의 본선 간선이 모두 터널이거나 길에 터널 간선이 있으면 `tunnel`, 아니면 `surface`. `note`에 본선 이름과 기지 측선 중 터널 길이를 적는다. 기지 측선의 절반 넘게 터널이면 '지하 기지'로 적는다.
- 기지 안 시설(검수고 등)의 위치, 담장의 실제 틈, 출입문이 열려 있는지는 알 수 없다.

## 20. passage.json (역 안 지하도 선 모양)

출구 구간과 환승을 직선 대신 실제 지하도 모양으로 **그리기** 위한 자료다. 분석과 결정은 `docs\passage-data-check.md`(추천 A1 + B1, 사용자 승인)에 있다. 그림만 바꾸고 `graph.json`·탐색·거리·시간은 그대로다.

- 만드는 스크립트: `scripts\build_passage.py` (`python -I scripts\build_passage.py`, 표준 라이브러리만, 약 1초). WKT 읽기·투영은 `passage_check.py`, 단순화·인코딩은 `build_graph.py`의 함수를 그대로 불러 쓴다.
- 점검: `node scripts\check_passage.js`. 결과 수치·뺀 환승 목록: `data\derived\passage_report.json`.
- 원본: `data\raw\passage\seoul_station_passage.csv`(CP949). 서울특별시 서울시 지하철역 연계 지하도 공간정보, 공공데이터포털 [15098161](https://www.data.go.kr/data/15098161/openapi.do), 이용허락범위 제한 없음. 내용은 2021년 무렵(분석 문서 7절). 서울만 있다.
- 크기(2026-11-10 빌드): 43,014 byte, gzip 22,495 byte(파이썬 gzip 9단계. Node zlib 9단계로는 22,820 byte).

```json
{"format": "passage-1", "precision": 5,
 "source": {"name": "서울시 지하철역 연계 지하도 공간정보", "url": "https://www.data.go.kr/data/15098161/openapi.do",
            "license": "이용허락범위 제한 없음", "as_of": "2021년 무렵"},
 "exits":     {"89": "<인코딩 폴리라인>", ...},
 "transfers": {"38551": "<인코딩 폴리라인>", ...}}
```

| 키 | 내용 |
|---|---|
| `precision` | 폴리라인 소수 자릿수. 5절 `edges.g`와 같은 Google 인코딩(소수 5자리)이라 `graph.js`의 `decodePolyline`으로 그대로 푼다 |
| `source` | 화면 출처 표기용. `as_of`를 함께 보여 줘야 한다(2021년 뒤에 생기거나 바뀐 출구·통로는 모른다) |
| `exits` | 열쇠 = `entrances` 배열 번호(8절, 문자열). 값 = 출구 → 역 방향 지하도 선 |
| `transfers` | 열쇠 = 환승 간선 번호(`edges`의 `k`가 `transfer`인 간선, 문자열). 값 = `edges.a` 허브 쪽 → `edges.b` 허브 쪽 지하도 선 |

### 20.1 선의 방향과 양 끝

- **출구(`exits`)**: 첫 점 = graph 출입구 노드 좌표(`entrances.node`), 둘째 점 = 맞춘 지하도 출구 끝점(20m 안), 그 뒤 지하도를 따라가 **끝 점 = 그 출입구 간선(`entrance` 종류)의 허브를 지하도 선에 수선으로 내린 점**이다. 허브는 출입구 간선이 잇는 허브(8절: 역의 가장 가까운 지하 허브)라서 탐색이 쓰는 허브와 같다. 끝 점과 허브 사이는 40m 안이다(중앙값 3m).
- **환승(`transfers`)**: 첫 점 = `edges.a[j]` 허브를 그 역 지하도 선에 내린 점, 끝 점 = `edges.b[j]` 허브를 내린 점. 사이는 지하도 위 최단 경로다. 경로가 b → a 방향이면 점 순서를 뒤집어 쓴다.
- 허브(승강장 가운데)와 선 끝 사이는 자료가 없다. 웹에서는 짧은 옅은 점선으로 잇는다(출구: 끝 점 ↔ 허브, 환승: 허브 a ↔ 첫 점, 끝 점 ↔ 허브 b). 3m 미만이면 점선 없이 바로 잇는다(`passage.js`의 `GAP_M`).
- 열쇠가 없는 출구·환승은 지금 방식(직선·점선) 그대로 그린다.
- **길이는 쓰지 않는다.** 표시 거리·시간은 그래프 간선 `len`(출구 = 직선, 환승 = 서울교통공사 값·추정값) 그대로다. 지하도는 층·계단이 없는 대합실 수준 도식이라 길이가 공사 값과 0.31~2.82배로 흩어진다(분석 문서 4절). 그린 선의 길이와 안내 숫자는 다를 수 있다(출구 그린 길이 중앙값 90m, 직선 간선의 1.44배).

### 20.2 만드는 규칙

1. 지하도 노드·링크를 읽는다. LINESTRING의 점 사이 구분자가 빠진 것은 경도 시작 위치로 자른다(`passage_check.parse_wkt`). 노드 표에 없는 링크 끝(31개)은 선 끝 좌표로 만든다.
2. **역은 위치로 정한다**(CSV 역 이름표에 오류가 있다. 예: 신당 링크의 노드가 `창신`). 출구는 출구 노드가 든 연결 요소를 쓰고, 환승은 연결 요소마다 300m 안의 서울·경기 역 허브·출입구에 노드별로 투표해 정한 역의 요소들을 쓴다.
3. 출구 맞추기: 서울 역의 OSM 출입구와 노드 유형 1(출구 끝점)을 20m 안에서 가까운 쌍부터 1:1로 맞춘다.
4. 출구 선: 출입구 간선의 허브를 출구 노드의 연결 요소에 수선으로 내려 40m 안이면, 출구 노드에서 그 투영점까지 지하도 위 최단 경로(다익스트라, 평면 근사 거리)를 이어 붙인다.
5. 환승 선: 두 허브를 역 지하도 링크에 수선으로 내려 둘 다 40m 안이고 같은 연결 요소면, 두 투영점 사이 최단 경로(같은 링크면 그 링크 위 구간과 비교).
6. 더글러스-포이커 1.5m로 점을 줄인다(양 끝은 그대로). 고리 링크(시작 = 끝 노드)는 경로에 쓰지 않는다.
7. **자료 뒤에 열린 승강장은 뺀다.** 신림선(2022-05), 서해선(2023-07), GTX-A(수서 2024-03, 서울역·연신내 2024-12), 신분당선 신사·논현(2022-05) 허브는 근처 지하도가 옛 노선 통로일 뿐이므로, 이 허브로 가는 출구 구간과 이 허브가 낀 환승을 만들지 않는다(`NEW_LINES`, `NEW_LINE_AT`).
8. 환승을 빼는 규칙(하나라도 맞으면 뺀다)
   - 지하도 길이 5m 미만: 두 허브가 지하도의 같은 지점(대개 통로 끝)에 내려앉아 그릴 선이 없다.
   - (지하도 길이 + 두 수선) > 환승 간선 `len` × 3.
   - 두 투영점 사이 직선이 20m 이상인데 지하도 길이가 그 4배 초과(별 모양 도식으로 크게 돌아감), 또는 직선 20m 미만인데 지하도 150m 초과. 2026-11-10 빌드에서는 이 두 규칙에 걸린 쌍이 없다. 교대(2↔3호선, 공사 값의 2.37배, 직선의 1.28배)는 분석 문서대로 L자 모양을 그릴 만하다고 보고 남겼다.

## 21. 걸음 기반 위치 (pdr.js)

역 사이에서 '마지막 확인 지점 + 걸은 시간 × 속도'(14절 `guide.js`) 대신 폰 가속도로 걸음을 세어 걸은 거리를 잰다(plan.md 6번 '여유가 있으면'). 터널 안에서는 경로를 따라 한 줄로만 움직이므로 경로 위 거리만 알면 된다: **거리 = 걸음 수 × 보폭**. 나침반은 쓰지 않는다(선로·철골이 자기장을 흐트러뜨린다). 서 있으면 거리가 늘지 않는 것이 시간 추정과 가장 다른 점이다.

- 파일: `web\js\pdr.js` (브라우저 `UG.pdr`, Node `require()`). 걸음 찾기·보폭은 DOM 없음, 센서·화면 켜 두기만 `window`를 쓴다.
- 검증: `node scripts\check_pdr.js` (합성 신호. 21.5절).
- 화면 연결(2026-11-11): 21.4절의 1~8을 연결했다. '안내 시작'을 누를 때만 켜고(시연·다시 찾기는 켜지 않음), iOS 거절·센서 없음은 알리지 않고 시간으로 추정한다. 길 안내 카드의 위치 칩은 `GPS` · `걸음`(센 걸음) · `추정`(걸은 시간), 방금 확인했으면 `확인한 곳`.

### 21.1 걸음 찾기 (`StepDetector`)

1. `devicemotion`의 `accelerationIncludingGravity` 세 축으로 크기 `√(x²+y²+z²)`를 낸다. 크기만 쓰므로 폰을 어느 방향으로 들든(손·주머니·눕힘) 같다.
2. 띠 거르개(1차 거르개를 표본 간격 `dt`로 계산해 표본 수가 50·60·100Hz로 달라도 같다): 3Hz 저역 통과 두 번 − 0.5Hz 느린 평균(중력·자세). 걸음(초당 1.4~2.2번)은 남고 차량 진동·손 떨림(8Hz 이상)과 기울임은 빠진다.
3. 봉우리: 거른 신호가 문턱을 넘었다가 0 아래로 내려오면 그 사이 가장 높은 곳이 걸음 후보 하나다. 문턱 = max(0.3, 최근 봉우리 높이 평균 × 0.25)라서 큰 봉우리(계단·주머니)와 작은 봉우리(손에 들고 천천히)를 따라간다. 2초 동안 후보가 없으면 문턱을 처음으로 되돌린다.
4. 간격: 앞 후보와 0.25초 안이면 같은 걸음의 두 번째 봉우리로 보고 버린다(천천히 걸으면 최근 간격 중앙값의 0.35배까지 늘어난다). 2초보다 길면 멈춘 것으로 본다.
5. 걷기 판정: 후보 5개가 고르게(가장 긴 간격 ÷ 가장 짧은 간격 ≤ 1.5) 이어져야 걷기로 보고, 그 5개를 한꺼번에 센다(빠뜨리지 않음). 걷는 중에는 후보마다 1걸음. 최근 4간격이 2배 넘게 들쭉날쭉하면 걷기가 아닌 것으로 보고 다시 모은다(덜컹임·흔들기).
6. 걸음 빠르기(`cadence`): 최근 8간격의 중앙값으로 낸 분당 걸음.

### 21.2 보폭과 자동 보정 (`StrideEstimator`)

- 기본 보폭 0.70m, 범위 0.45~1.0m. 키를 알면 `create({stride})`로 줄 수 있다(지금은 키를 받지 않는다).
- 체크포인트를 확인하면('도착'·'통과'·'환승 완료') 지난 확인 지점부터의 실제 경로 거리를 안다. 잰 보폭 = 실제 거리 ÷ 그 사이 센 걸음.
  - 쓰지 않는 구간: 50걸음 미만, 잰 보폭이 0.35m 미만이거나 1.3m 초과(다른 곳에서 눌렀거나 걸음을 크게 놓침), 시간으로 채운 거리(21.3절)가 실제 거리의 10%를 넘음.
  - 새 보폭 = 지금 보폭 + 비율 × (잰 보폭(0.45~1.0으로 자름) − 지금 보폭). 비율 = 걸음 ÷ (걸음 + 300), 최대 0.8. 많이 걸은 구간일수록 많이 믿고, 한 번 잘못 눌러도 다 바뀌지 않는다.
  - 보정은 '센 걸음 하나당 거리'를 맞추는 것이다. 걸음을 일정하게 조금 덜 세는 폰에서도 거리가 맞아진다(1.0m 안에서).

### 21.3 서 있을 때와 센서가 못 본 시간

- 걸음이 없으면 거리가 늘지 않는다(서 있음, 쉬는 중).
- 센서 값이 1초 넘게 안 온 시간(화면이 꺼짐·숨음, 센서 멈춤)은 예전처럼 시간 × 걷는 속도로 채운다. 꺼진 동안 걸었을 가능성이 크고, 다시 보일 때 위치가 뒤로 튀지 않게 하려는 것이다.
- 흔들림(거른 신호의 2초 RMS)이 0.6m/s²보다 큰데 3초 넘게 걸음을 못 세면(가방 속 등) 그때부터 시간 × 속도로 채운다. 가만히 서 있으면 흔들림이 약 0.05라 채우지 않는다.
- 그래서 센서가 켜진 뒤에는 시간 추정으로 바꿔 끼우지 않는다(바꿔 끼우면 서 있던 시간만큼 위치가 튄다). 시간 추정은 센서를 쓸 수 없을 때(`usable()`이 false)만 쓴다.

| 이름 | 하는 일 |
|---|---|
| `UG.pdr.create(opts)` | 걸음 추적기를 만든다. `opts`: `stride`(m), `fillSpeed()`(m/s, 못 본 시간을 채울 속도. 길 안내는 `state.speed / 3.6`), 그 밖에 `DEFAULTS`의 기준값. 시험용 `now()`, `window` |

### 21.6 한계

- 정확도: 실제 폰과 실제 터널에서 재지 않았다. 합성 신호 결과(걸음 오차 2% 안, 보정 뒤 보폭 오차 1% 안)는 실제 정확도가 아니다. 폰 걸음 세기는 보통 몇 % 오차가 나고, 보폭은 걸음마다 달라 거리 오차는 그보다 크다. 침목·자갈 위에서는 보폭이 짧고 고르지 않다(보정이 일부 맞춘다). 체크포인트에서 사용자가 확인하는 것이 여전히 기준이다.
- 놓치거나 잘못 세는 경우(위 표의 참고 줄): 폰을 손에 쥐고 팔과 함께 흔들면 두 걸음에 하나만 셀 수 있다(보정이 1.0m에서 막혀 거리가 약 20% 짧게 나온다). 주머니에서 한쪽 다리 걸음이 아주 약하면 덜 센다. 걷지 않고 폰을 크게 흔들면 걸음으로 셀 수 있다(다른 만보기 앱과 같은 약점).
- iOS: 처음 한 번 '동작 및 방향' 권한을 묻는다. 안내 시작 단추를 누를 때 물어야 하고, 거절하면 Safari가 다시 묻지 않아 시간 추정으로 돌아간다.
- 화면: 웹 앱은 화면이 켜져 있고 앱이 앞에 있을 때만 센서 값이 온다. 화면 꺼짐 막기(Wake Lock)는 배터리 절약 모드 등에서 거절될 수 있고, 꺼진 동안은 시간 × 속도로 채운다. 화면을 계속 켜 두면 배터리를 많이 쓴다.
- claude.ai 미리보기(iframe)는 센서와 Wake Lock을 막는다: `start()`는 3초 뒤 `unsupported`, `keepScreenOn()`은 `false`이고, 지금처럼 시간 추정으로 동작한다. HTTP로 연 페이지도 센서가 없다(GitHub Pages는 HTTPS라 된다).
- 기준값(`DEFAULTS`)은 합성 신호로만 정했다. 실제 폰 기록으로 다시 맞춰야 한다(특히 `minPeak` 0.3, `activeRms` 0.6).

## 22. 길 안내 중 GPS (guide.js `GpsGate`, 2026-11-12)

실제 폰 시험에서 'GPS 를 다시 잡거나 끊김 포착이 늦음'(사용자 2026-11-12): 지하에 내려간 뒤 파란 점이 20~30초 지상에 남고, 역 안에서는 와이파이·기지국 위치(정확도 20~60m)를 GPS 로 써서 점이 추정 위치에서 끌려갔다.

- 원인(코드에서 확인): ① 길 안내 중에도 `maximumAge` 10초라 브라우저가 저장해 둔 위치가 와도, 받은 시각(`Date.now()`)으로 적어 막 잡은 위치로 보였다. ② 끊김 기준이 20초였다(+ 저장된 위치 10초). ③ 지하 구간을 따지지 않아 정확도 80m 안이면 역 안 와이파이 위치도 GPS 로 썼다.
- 사용자 결정(2026-11-12): **GPS 가 잡히는 동안에는 추정 위치로 바꾸지 않는다.** 경로 진행(걸은 시간·걸음 추정)만으로 바꾸지 않는다. 추정은 실제보다 앞서거나 뒤처질 수 있다.
- 위치 받기(`app.js`): 길 안내 중 `enableHighAccuracy` + `maximumAge: 0`(평소는 지금처럼 낮은 정확도·10초, 배터리). 저장해 둔 위치는 이것으로 막는다. 위치 시각 `t` = 받은 시각(`Date.now()`): 끊김(6초)·간격은 모두 이것으로 잰다. `pos.timestamp`는 `ts`로 따로 두고 `Date.now()`와 견주지 않는다. 안드로이드는 GNSS 위성 시각을 줄 때가 있어, 견주면 기기 시계가 몇 초만 앞서도 모든 위치가 오래된 것으로 보여 길 안내 내내 GPS 를 못 쓸 수 있다. `ts`는 같은 시계끼리인 위치들의 순서만 본다(`notNewer`): 둘 다 `ts`가 있고 새 위치의 `ts`가 같거나 작으면(같은 위치를 또 받음·더 오래된 위치가 늦게 옴) 버린다. 그래서 점이 뒤로 가지 않고, 같은 위치를 또 받아도 끊김 시계가 새로 시작하지 않는다. 위치를 받을 때마다 '받은 시각 + 6초'에 다시 그리게 해 두어 5초마다 그리기를 기다리지 않는다.
- 잃음: 마지막 위치를 받은 때부터 **6초**(`freshMs`) 동안 새 위치가 없거나, 정확도가 **80m**(`goodM`)보다 나쁜 위치가 옴. 이때부터 추정 위치(`걸음`·`추정`·`확인한 곳`)를 쓴다. GNSS 는 잡혀 있으면 대개 1초마다 위치를 주므로 6초는 연달아 5번 넘게 빠진 것이다. 걷는 속도로 6~8m.
- 다시 잡음: 보통은 쓸 만한 위치(6초 안·80m 안) 하나로 바로(전과 같음). **GPS 를 잃은 상태이고 추정 위치가 지하 구간일 때만** 엄하게 본다: 잃은 뒤 연달아 온 위치가 3번 넘게(`ugCount`)·3초 넘게(`ugSpanMs`) 이어지고, 모두 정확도 25m 안(`ugGoodM`; 고도가 없는 위치는 15m 안, `ugNoAltM`)이며, 서로 30m 안(`ugSpreadM`)에 모여 있어야 한다. 그 사이 25m(고도 없으면 15m)보다 나쁜 위치가 오거나 6초 끊기면 처음부터 센다. 다시 잡은 뒤에는 위 '잃음' 기준만 본다. 다른 출구로 나와도 같고, 그 뒤는 '경로에서 벗어남'(150m)이 판단한다.
- 고도: 안드로이드에서 고도가 없는 위치는 대개 와이파이·기지국 위치다. iOS·PC 는 다를 수 있어 고도만으로 버리지 않고 정확도 기준만 더 엄하게 한다.
- 지하 구간(`routeTrack`의 조각 `ug`): 간선 구조가 `under_structs`(출입구 통로·터널·지하 승강장·지하 환승 통로)면 지하. 경로 탐색이 '지하'로 치는 기준과 같아 지하 조각 길이 = 총거리 − 지상 노출이다. 출발 지점 → 출구, 출구 → 도착 지점, 바로 걷기, 역 사이 지상 걷기, 차량기지 안 걷기는 지상. 선로 위 지금 위치에서 출발하는 조각(`approach`)과 수직구까지(`egress`)는 그 간선을 따른다.
- 추정 위치가 지하인지(`underNow`): 마지막 확인 지점 + 걸은 거리(다음 확인 지점까지). 방금 확인했으면 그 뒤 조각(지하역 출구에서 '도착'을 누르면 그 뒤는 출구 통로), 다음 확인 지점에 닿았는데 아직 확인하지 않았으면 그 앞 조각, 다 왔으면 지상. GPS 는 보지 않는다.
- 위치 칩 글(`GPS` · `걸음` · `추정` · `확인한 곳` · `경로 밖 …`)과 시연(위치를 숨겨 늘 추정)은 그대로다.
- 검증: `node scripts\check_gps.js` — 회현역 2번 출구 → 강남역 8번 출구 실제 경로 위에서 위치 순서를 가짜 시계로 흉내 낸다. 지하 조각 길이 = 총거리 − 노출, 확인 지점마다 지하/지상, 출구를 지나도 위치가 오면 GPS 그대로, 끊긴 뒤 6초에 추정(5.9초는 GPS), 잃은 뒤 역 안 40m 위치 20번·고도 없는 20m·50m 를 오가는 20m·중간에 끊긴 좋은 위치는 추정 그대로, 나와서 6m 위치가 4번째(3초)에 GPS, 다른 출구(경로에서 341m)도 다시 잡음, 같은 `ts`를 다시 받음·더 오래된 `ts`가 늦게 옴은 버림, 기기 시계가 `ts`보다 30초 빨라도 GPS 를 씀, `ts` 없는 위치도 씀, 지상 걷기는 예전 규칙과 같고 끊김만 6초.
- 한계: 실제 폰·실제 지하에서 재지 않았다. 계단에서 GNSS 가 얼마나 빨리 끊기는지, 역 안 와이파이 위치의 실제 정확도 값, 기기별 `pos.timestamp`·고도 값, 지상(고가 밑·건물 사이)에서 6초 넘게 빠지는 일이 얼마나 잦은지는 모른다. 길 안내 밖(`maximumAge` 10초)에서 처음 받은 위치가 저장해 둔 위치면 받은 시각으로 새 위치처럼 보인다(전과 같음. 길 안내 중에는 `maximumAge` 0). 계단을 내려가는 동안 정확도 80m 안의 와이파이 위치가 끊김 없이 이어지면 잃지 않은 것으로 보고 GPS 를 계속 쓴다(사용자 결정: 잡히는 동안은 GPS).
