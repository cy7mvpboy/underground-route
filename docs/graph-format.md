# 경로 탐색 그래프 형식 (`web\data\graph.json`)

- 만드는 스크립트: `scripts\build_graph.py` (프로젝트 폴더에서 `python -I scripts\build_graph.py`)
- 참조 탐색기: `scripts\route.py` (JavaScript로 옮길 원본)
- 점검 결과: `data\derived\graph_report.json` (통계, 부착 못 한 역, 서울 자료 대조 결과, 한강 횡단 간선 목록)
- 크기(2026-11-10 빌드): 3,227,492 byte, gzip 970,700 byte(파이썬 gzip 9단계). 전국을 파일 하나에 담는다.
  - 노선·선 이름과 정차 순서를 넣기 전에는 3,047,859 byte(gzip 953,091 byte)였다. 늘어난 것은 대부분 간선 `tn` 열과 `line_routes`다.
  - 역 깊이(`stations[].depth`)를 넣기 전에는 3,208,525 byte(gzip 967,433 byte)였다(+18,967 byte).

## 1. 그래프가 무엇을 나타내나

사람이 걸을 수 있는 길을 점(노드)과 선(간선)으로 나타낸다. 간선은 네 종류다.

| 종류(kind) | 뜻 | 길이 |
|---|---|---|
| `track` | 선로 한 구간. 끝점·분기점·구조 변화점(터널↔교량↔지상)·역 부착점에서 자른다. | 원래 OSM 좌표로 잰 길이 |
| `platform` | 선로 위 역 부착점 ↔ 그 역의 '승강장 허브' | 직선 거리 |
| `transfer` | 같은 역 안의 허브 ↔ 허브(환승) | 서울교통공사 값 또는 추정값 |
| `entrance` | 지상 출입구 ↔ 역 허브 | 직선 거리 |

### 승강장 허브
- 역(같은 이름 역들의 묶음)마다 **노선별로** 허브 노드를 하나 둔다. 노선은 그 부착점에 붙은 선로의 노선 이름 묶음이다.
- 상·하행 선로처럼 같은 노선의 부착점은 같은 허브에 이어진다. 그래서 같은 노선의 반대편 선로로 건너갈 때는 허브를 거친다.
- 환승은 허브끼리만 잇는다. 이렇게 하면 다른 노선을 거쳐 같은 노선의 반대 선로로 가는 '지름길'이 생기지 않는다.
- 탐색의 출발점·도착점은 역의 허브들이다.

### 지하·지상 판정
- 선로: `tunnel` 태그가 있고 값이 `no`가 아니면 `tunnel`, 아니면 `bridge` 태그로 `bridge`, 나머지는 `ground`.
  - `layer<0`만 있는 선로는 지상(`ground`)이다. 경부선 금정~수원이 `layer=-1`이지만 실제로는 지상이기 때문이다(`docs\data-check.md` 4.4절).
  - `covered=yes`(방음터널 등)도 지상이다.
- 역 부착점: 그 점에 붙은 본선 선로가 모두 터널이면 지하.
- 허브: 부착점 중 하나라도 지하면 지하.
- 승강장 간선: 부착점이 지하면 `underground`, 아니면 `ground`.
- 환승 간선: 양쪽 허브가 모두 지하면 `underground`, 아니면 `ground`.
- 출입구 간선: 지하 허브에 이으면 `entrance`, 지상 허브밖에 없으면 `ground`.

### 탐색 비용
- 비용 = 길이(m) × 가중치.
- 가중치: `tables.under_structs`(`tunnel`, `entrance`, `underground`)는 `weights.under`(1), 나머지(`bridge`, `ground`)는 `weights.exposed`(1000).
- 그래서 지상 1m는 지하 1km와 같은 비용이다. 지하로만 가는 길이 있으면 그 길이 뽑히고, 없으면 지상 노출이 가장 짧은 길이 뽑힌다.
- 막힌 간선은 간선 번호(배열 위치)로 지정하고, 탐색할 때 건너뛴다.

## 2. 최상위 구조

```json
{
  "format": "underground-route-graph", "version": 1,
  "attribution": ["...", "..."], "osm_base": "2026-11-10",
  "weights": {"under": 1, "exposed": 1000},
  "tables": {...}, "nodes": {...}, "edges": {...},
  "stations": [...], "entrances": {...}, "presets": {...}, "line_routes": [...]
}
```

- 기존 키의 뜻은 바꾸지 않고 새 키만 더한다. 2026-11-10에 `tables.line_short`, `tables.line_metro`, `tables.track_names`, `edges.tn`, `line_routes`를 더했고, `tables.lines`의 이름을 정식 노선 이름으로 바꿨다(3.1절). 같은 날 `stations[].depth`(6.1절)를 더했다. 이때 다른 키·노드·간선 번호는 바뀌지 않았다.

크기를 줄이려고 노드와 간선은 **열(column)별 배열**로 저장한다. 노드 i의 위도는 `nodes.lat[i]`, 간선 j의 시작 노드는 `edges.a[j]`이다. 노드 번호·간선 번호는 배열 위치(0부터)다.

## 3. `tables` (코드 → 이름 표)

| 키 | 내용 |
|---|---|
| `structs` | `["tunnel","bridge","ground","entrance","underground"]` — `edges.s`의 값 |
| `under_structs` | 가중치 1인 구조 이름 목록 |
| `kinds` | `["track","platform","transfer","entrance"]` — `edges.k`의 값 |
| `sources` | `["","seoul_metro","estimated"]` — `edges.src`의 값(환승 거리 출처) |
| `railways` | `["rail","subway","light_rail","monorail","narrow_gauge"]` — `edges.r`의 값(선로가 아니면 -1) |
| `services` | `["","yard","siding","spur","crossover"]` — `edges.svc`의 값(""=본선, 나머지=측선·차량기지) |
| `lines` | 정식 노선 이름 목록(263개, 가나다순). 예: `"5호선"`, `"수인분당선"`, `"부산 1호선"`, `"경부고속선"` |
| `line_short` | `lines`와 같은 순서의 짧은 이름(안내 화면용). 예: `"2호선 성수지선"` → `"2호선"`, `"동해선 광역전철"` → `"동해선"` |
| `line_metro` | `lines`와 같은 순서. 1 = 도시철도·광역전철 노선(3.1절 노선 이름표에 있는 노선), 0 = 선로 이름에서 온 이름(경부선, 기지선 등) |
| `line_sets` | 노선 번호 묶음 목록. `edges.ls`, `stations[].hub_ls`가 이 목록의 번호다. 0번은 빈 묶음 |
| `track_names` | 선 이름 목록(275개 + 0번 빈 문자열). `edges.tn`의 값. 예: `"일산선"`, `"과천선"`, `"경인선"`, `"인천국제공항선"` |
| `regions` | `[{"name": "서울특별시", "conf": "good"}, ...]` — `edges.rg`, `stations[].rg`의 값 |

- 지역 신뢰도 `conf`: `good`(서울·인천·경기·부산·대구·대전), `caveat`(전남광주통합특별시·울산·세종·강원·경북·경남), `unchecked`(충북·충남·전북). 제주는 그래프에서 뺐다. 화면에서 `caveat`·`unchecked` 지역 구간은 '신뢰도 낮음'으로 표시한다.

### 3.1 노선 이름과 선 이름

간선 하나에 이름이 두 가지 붙는다.

| 구분 | 뜻 | 예 | 담는 곳 |
|---|---|---|---|
| 노선 | 열차가 다니는 운행 계통(안내판의 '3호선') | `3호선`, `4호선`, `공항철도` | `edges.ls` → `tables.line_sets` → `tables.lines` |
| 선 | 선로 자체의 이름(OSM 선로 way의 `name`) | `일산선`, `과천선`, `인천국제공항선` | `edges.tn` → `tables.track_names` |

**노선 이름 정하는 규칙** (`build_graph.py`의 `LINE_TABLE`, `TRACK_SERVICE`)
1. 그 선로가 든 도시철도·광역전철 노선 relation 이름을 정리한다(`:` 뒤, 괄호, `급행`·`내선순환` 같은 꼬리를 뗀다). KTX·무궁화 같은 열차 운행 계통 relation은 쓰지 않는다.
2. 노선 이름표(`LINE_TABLE`)로 정식 이름을 정한다. 정식 이름은 전국에서 하나뿐이다.
   - 수도권: `1호선`~`9호선`, `경의중앙선`, `수인분당선`, `신분당선`, `공항철도`, `GTX-A`, `경춘선`, `경강선`, `서해선`, `신림선`, `우이신설선`, `김포골드라인`, `용인경전철`, `의정부경전철`, `인천 1호선`, `인천 2호선`, `2호선 성수지선`, `2호선 신정지선` 등.
   - 다른 도시는 도시 이름을 붙인다: `부산 1호선`~`부산 4호선`, `부산김해경전철`, `동해선 광역전철`, `대구 1호선`~`대구 3호선`, `대경선`, `대전 1호선`, `광주 1호선`.
   - 표는 42개 노선(그래프에 선로가 있는 것은 41개, `광주 2호선`은 선로가 아직 없다).
   - 합친 이름(같은 노선이 두 이름으로 나오던 것): `9호선`/`서울 지하철 9호선` → `9호선`, `GTX-A`/`수도권광역급행철도에이선` → `GTX-A`, `수도권 전철 1호선`/`서울 지하철 1호선`/`1호선` → `1호선`, `대구 2호선`/`대구 도시철도 2호선` → `대구 2호선`, `용인 경전철`/`용인경전철` → `용인경전철`, `안심~하양 복선전철` → `대구 1호선`.
3. relation에 들지 않은 선로는 선 이름으로 노선을 정한다. 그 선을 다니는 노선이 하나뿐이면 `TRACK_SERVICE` 표를 쓴다: `인천국제공항선` → `공항철도`, `일산선` → `3호선`, `경인선` → `1호선`, `수인선` → `수인분당선`, `진접선` → `4호선`, `별내선` → `8호선`, `성수지선`·`신정지선` → 2호선 지선. 표에 없으면 선 이름을 그대로 노선 이름으로 쓴다(예: `경부선`, `경부고속선`, `지축기지선`. 이런 이름은 `line_metro` = 0).
   - 이 표 덕분에 서울역 공항철도 승강장처럼 relation이 빠진 몇 개 way 때문에 같은 역에 허브가 둘 생기던 일이 없어졌다(환승 간선 465개 → 425개).
   - `경강선`·`서해선`·`경춘선`은 수도권 전철 구간이 아닌 같은 이름 선로(예: 강릉선 KTX가 다니는 경강선)도 같은 노선 이름이 된다.

**선 이름 정하는 규칙** (`track_name()`)
- 선로 way의 `name`에서 앞뒤 공백을 지우고, `X본선`은 `X선`으로 바꾼다(`경부본선` → `경부선`, `경의본선` → `경의선`, `호남본선`·`영동본선`·`태백본선`도 같음).
- 노선을 가리키는 이름은 정식 노선 이름으로 바꾼다(`서울 지하철 1호선` → `1호선`, `부산 도시철도 1호선` → `부산 1호선`).
- 2026-11-10 데이터에 `상행`·`하행`·`복선` 같은 꼬리가 붙은 선 이름은 없었다(`복선`은 `안심~하양 복선전철` 하나뿐이고 노선 이름표에서 `대구 1호선`으로 합쳤다).
- 본선 선로 길이가 긴 선 이름: 경부선 1,090km, 경부고속선 796km, 중앙선 646km, 호남선 510km, 동해선 461km, 경전선 436km, 호남고속선 369km, 전라선 354km, 경강선 347km, 서해선 263km. 수도권 전철이 다니는 선: 경원선 150.5km, 인천국제공항선 128.2km, 경의선 125.2km, 분당선 106.4km, 경인선 104.6km, 수인선 78.6km, 안산선 52.0km, 일산선 38.4km, 진접선 29.0km, 과천선 28.5km. 이름 없는 본선 선로는 182km다. 전체 목록은 `graph_report.json`의 `names.top_track_names_km`에 있다.

**안내 화면 표시**: `<짧은 노선 이름> · <선 이름>`. 선 이름이 노선 이름(정식 또는 짧은 이름)과 같으면 노선 이름만 쓴다.
- 예: `3호선 · 일산선`, `4호선 · 과천선`, `1호선 · 경인선`, `공항철도 · 인천국제공항선`, `2호선 · 신정지선`. 서울 시내 3호선 선로(선 이름 `3호선`)는 `3호선`.

## 4. `nodes`

| 키 | 내용 |
|---|---|
| `lat`, `lon` | 위도·경도 × 100000 (정수). 예: `3758851` → 37.58851 |
| `f` | 표시 비트. 1 = 터널 출입구(갱구, 터널과 비터널 선로가 만나는 점), 2 = 역 부착점(선로 위), 4 = 출입구(지상 쪽 끝, 진입점), 8 = 승강장 허브 |

## 5. `edges`

모든 배열의 길이는 간선 수와 같다. 간선 번호 순서는 `track` → `platform` → `transfer` → `entrance`이다.

| 키 | 내용 |
|---|---|
| `a`, `b` | 양 끝 노드 번호. 간선은 양방향으로 걸을 수 있다 |
| `len` | 길이(m, 소수 1자리) |
| `s` | 구조(`tables.structs` 번호) |
| `k` | 종류(`tables.kinds` 번호) |
| `r` | 철도 종류(`tables.railways` 번호, 선로가 아니면 -1) |
| `svc` | 본선/측선(`tables.services` 번호) |
| `ls` | 노선 묶음(`tables.line_sets` 번호) |
| `rg` | 지역(`tables.regions` 번호). 신뢰도는 지역 표에서 찾는다 |
| `src` | 환승 거리 출처(`tables.sources` 번호). 환승이 아니면 0 |
| `g` | 선 모양. Google 인코딩 폴리라인(소수 5자리). 노드 a에서 b 방향이고 양 끝점을 포함한다. `track`이 아니면 빈 문자열이고, 두 노드를 직선으로 그린다 |
| `tn` | 선 이름(`tables.track_names` 번호). 0 = 이름 없음. `track`이 아니면 0 |

- 선로를 간선으로 합칠 때(차수 2 노드 없애기) 선 이름이 다르면 합치지 않는다. 그래서 선 이름이 바뀌는 곳에서 간선이 나뉜다(선로 간선 35,008개 → 35,024개).

- 선 모양은 더글러스-포이커 방식으로 5m 오차 안에서 점을 줄였다. 길이(`len`)는 줄이기 전 좌표로 잰 값이다.
- 측선(차량기지·측선·인상선·건넘선)도 넣었고, 탐색 비용은 구조로만 정한다(측선 터널도 가중치 1). 화면에서 숨기려면 `svc != 0`인 간선을 거르되, 탐색에서는 빼면 안 된다.
  - OSM에는 본선이 측선을 거쳐서만 나머지 선로와 이어지는 곳이 있다. 예: 서해선 대곡~원시 남쪽 끝의 터널 way 970070469가 `service=yard`로 되어 있고, 경춘선 청량리 부근 way 903353258·1025050687은 측선으로만 이어진다. 측선을 빼면 이 본선들이 떨어져 나간다. 원시→대곡, 청량리→상봉 탐색에서 이 측선 간선을 지나는 것을 확인했다.

### 폴리라인 풀기 (JavaScript)

```js
function decodePolyline(s) {
  const pts = []; let i = 0, lat = 0, lon = 0;
  while (i < s.length) {
    for (const k of [0, 1]) {
      let r = 0, sh = 0, b;
      do { b = s.charCodeAt(i++) - 63; r |= (b & 31) << sh; sh += 5; } while (b >= 32);
      const d = (r & 1) ? ~(r >> 1) : (r >> 1);
      if (k === 0) lat += d; else lon += d;
    }
    pts.push([lat / 1e5, lon / 1e5]);
  }
  return pts;
}
```

## 6. `stations` (역 = 같은 이름 역들의 묶음)

```json
{"name": "한성대입구", "names": ["삼선교", "한성대입구"], "lat": 3758851, "lon": 12700596,
 "rg": 7, "hubs": [30824], "hub_ls": [3], "ug": [1], "plat": [2116, 7114]}
```

| 키 | 내용 |
|---|---|
| `name` | 표시 이름 |
| `names` | 검색용 이름(정규화: 괄호 내용·공백·끝의 '역' 제거, 별칭 포함) |
| `lat`, `lon` | OSM 역 노드들의 평균 위치 × 100000 |
| `rg` | 지역 번호 |
| `hubs` | 노선별 승강장 허브 노드 번호 |
| `hub_ls` | 허브마다 노선 묶음 번호 |
| `ug` | 허브마다 지하 여부(1/0) |
| `plat` | 선로 위 부착점 노드 번호 전체 |
| `depth` | 노선별 역 깊이 목록(6.1절). 자료가 있는 역에만 있고, 없으면 키 자체가 없다 |

### 6.1 `depth` (역 깊이)

```json
{"name": "종로3가", ..., "depth": [{"line": 2, "floor": "B2", "platform_m": 11.24, "track_m": 12.34},
                                  {"line": 7, "floor": "B4", "platform_m": 20.25, "track_m": 21.35},
                                  {"line": 11, "floor": "B5", "platform_m": 30.2, "track_m": 31.3}]}
```

| 키 | 내용 |
|---|---|
| `line` | 노선 번호(`tables.lines` 위치). 그 역 허브의 노선(`hub_ls`) 중 하나라서 허브와 맞춰 볼 수 있다. 보통 `1호선`~`8호선`이고, 지선에만 붙은 역은 지선 이름이다(예: 용답·신답 → `2호선 성수지선`, 도림천 → `2호선 신정지선`) |
| `floor` | 승강장 층수. 자료 글자 그대로: `B1`~`B8`(지하), `고가`, `지상` |
| `platform_m` | 정거장깊이(m, 자료의 `정거장깊이`). 지면(지반고)에서 승강장까지 |
| `track_m` | 선로 기준 정거장깊이(m, 자료의 `선로기준정거장깊이`). 지면에서 레일면까지. 이 자료에서는 277행 모두 `platform_m`보다 1.1m 깊다 |

- 출처: 서울교통공사 역사심도정보(2024-11-04, 서울 열린데이터광장), 공공누리 제1유형(출처 표시). 원본 `data\raw\seoul\station_depth_20241104.csv`(CP949, 277행, 서울교통공사 1~8호선). 그래프의 `attribution` 둘째 줄이 이 자료도 함께 밝힌다.
- 값은 자료 그대로다. 고가·지상역은 음수일 수 있다(지면보다 높음, 예: 동작 4호선 `고가`, `platform_m` -20.9). 지상역 신답은 0.3처럼 양수도 있다.
- 맞추기: `build_graph.py`의 `match_depth_rows()`. 서울·경기 역 중 정규화한 이름이 같고, 부착점 노선이 자료의 호선(지선 포함)인 역을 고른다. 이름이 없으면 옛 이름·줄임말 표(`DEPTH_ALIASES`: 을지3가 → 을지로3가, 당고개 → 불암산, DMC → 디지털미디어시티 등)로 다시 찾는다. 같은 자료로 지하 여부 대조(12절)도 한다.
- 2026-11-10 빌드: 277행 모두 역 하나씩에 맞았다(못 맞춘 행 없음). 깊이가 있는 역은 240개(서울 225, 경기 15), 기록은 277개다. 한 역에 노선이 여럿이면 기록도 여럿이다(예: 종로3가 1·3·5호선).
- 가장 깊은 역(`platform_m`): 산성(8호선, B4) 54.69m, 버티고개(6호선, B5) 44.65m, 숭실대입구(7호선, B6) 44.53m, 신금호(5호선, B8) 42.16m, 독바위(6호선, B6) 36.84m.
- 서울교통공사 1~8호선만 있다. 9호선, 신분당선, 코레일 구간(1호선 서울역~청량리 밖, 경의중앙선 등), 다른 도시 역에는 없다.

### 역을 만든 규칙
1. OSM 역 노드(`railway=station|halt`, `public_transport=station`)를 읽는다. 공사중(`railway=construction`, `construction:railway`), 제주, 서비스역은 뺀다.
2. 정규화한 이름(별칭 포함)이 같고 500m 안에 있거나, 같은 `stop_area`에 든 역 노드를 한 역으로 묶는다.
3. 부착점
   - 선로 위의 정차 위치(`railway=stop`, `public_transport=stop_position`)를 먼저 쓴다. 정차 위치는 `stop_area`로, 없으면 300m 안의 같은 이름 역으로 역에 연결한다. 선로 밖에 찍힌 정차 위치는 30m 안의 선로에 붙인다.
   - 300m 안에 정차 위치가 없는 역 노드는 200m 안의 본선 선로 중 가장 가까운 선로와, 그보다 40m 안쪽으로 더 먼 같은 구조의 선로(상·하행 등)에 붙인다. 붙이는 자리에 노드를 새로 끼워 넣어 선로를 자른다.

## 7. 환승 규칙
- 같은 역 안의 허브끼리 600m 안이면 환승 간선을 둔다.
- 추정 거리(`estimated`): **직선 거리 × 1.3 + 50m**. 1.3은 통로가 곧지 않은 것, 50m는 계단·개찰구를 대략 반영한 값이다. 실측 근거는 없다.
- 서울교통공사 자료(`seoul_metro`): '환승역명 + 호선 + 환승노선'이 맞는 허브 쌍에 공개된 환승 거리를 넣는다. 140행 중 139행을 반영했다. 반영하지 못한 1행은 `5호선 강동 → 5호선`(OSM에서 5호선 본선과 지선의 노선 이름이 같아 구분할 수 없음)이다.
  - 자료의 노선 표기는 정식 노선 이름(3.1절)으로 바꾼다. 예: `1` → `1호선`, `경의중앙선` → `경의중앙선`, `경원선` → `1호선`(석계), `국철` → `수인분당선`(수서, 가정).
- 환승 통로가 실제로 지하로 이어져 있는지는 OSM에 거의 없다. 양쪽 승강장이 지하면 지하 통로가 있다고 **가정**한다. 발표·화면에서 밝혀야 한다.

## 10. `line_routes` (노선 relation의 정차역 순서)

길 안내에서 '오금 방면' 같은 종착역 방면을 찾는 데 쓴다. OSM 노선 relation(운행 계통) 하나가 한 줄이다(239개).

```json
{"l": 7, "dir": "오금 방면", "loop": 0, "st": [602, 906, 601, ...]}
```

| 키 | 내용 |
|---|---|
| `l` | 노선 번호(`tables.lines` 위치) |
| `dir` | 방면 표시. 보통 `<마지막 정차역> 방면`, 2호선 순환선은 `내선순환`·`외선순환` |
| `loop` | 1 = 첫 역과 마지막 역이 같은 순환 relation |
| `st` | 정차역 순서(`stations` 번호). relation의 `stop` 역할 노드를 정차 위치·`stop_area`로 역에 이어 만든다. 역에 잇지 못한 정차 위치는 빠진다 |

- 순환 표시(`내선순환`·`외선순환`)가 없는 순환 relation은 방면을 정할 수 없어 넣지 않았다. 같은 내용(노선·방면·정차역 순서)이 겹치는 relation은 하나만 넣었다.

## 11. 길 안내 단계 (`route.py`가 만드는 `steps`)

그래프에 저장하는 내용은 아니고, 탐색 결과를 안내 단계로 바꾸는 규칙이다. `route.py --json`의 `steps`에 들어 있고, 웹에서 같은 방식으로 옮겨 쓴다.

### 단계 나누기
1. 경로(간선 목록)를 환승 간선에서 나눈다. 환승 간선 하나가 `transfer` 단계 하나다.
2. 그 사이(선로·승강장 간선)는 노선이 바뀌는 곳에서 다시 나눠 `ride` 단계로 만든다. 간선마다 노선 고르는 방법:
   - 도시철도·광역전철 노선(`line_metro` = 1)만 본다. 지금 타던 노선이 다음 간선에도 있으면 계속 타고, 없으면 그 자리에서 가장 길게(m) 이어지는 노선으로 바꾼다. 노선이 없는 간선(승강장 간선, 이름 없는 선로)은 앞 노선을 이어 간다.
   - 그런 노선이 없는 선로(경부선·기지선 등)가 같은 노선 사이에 끼어 있으면 그 노선으로 메운다(relation이 빠진 틈, 예: 원흥→경복궁 경로의 삼송 부근 지축기지선 0.5km는 3호선 단계에 들어간다).
   - 남은 구간은 선로 이름에서 온 노선(예: `경부고속선`)으로 정한다.
3. 지상 노출 경고(`warning`)를, 노출이 시작되는 간선이 든 단계 바로 앞에 끼운다. 지하(가중치 1)에서 교량·지상으로 바뀔 때마다 하나, 출발부터 지상이면 출발역에서 하나.
4. `ride`·`transfer` 단계에는 1부터 번호(`no`)를 붙인다. 경고에는 번호가 없고, 어느 단계 안의 일인지 `in_step`으로 적는다.
- 걷는 시간: 거리 ÷ 걷는 속도. 기본 시속 3.5km(`--speed`로 바꿈). 모든 단계 거리의 합은 경로 총거리와 같다(반올림 1m 차이).

### `ride` (노선 하나를 따라 걷기)

| 키 | 내용 |
|---|---|
| `line`, `line_full` | 짧은 노선 이름, 정식 노선 이름 |
| `label` | 표시 문구. `<짧은 노선 이름> · <선 이름들>`. 노선 이름과 같은 선 이름은 뺀다. 예: `3호선 · 일산선` |
| `track_names` | 지나는 선 이름(순서대로, 중복 없이). 노선 이름과 같은 것도 들어 있다. 예: `["과천선", "4호선"]` |
| `track_parts` | 선 이름이 바뀔 때마다 나눈 구간 `[{name, from_station, to_station, distance_m}]`. `from_station`은 선이 바뀌기 직전에 지난 역 |
| `from_station`, `to_station` | 출발역(직전 단계가 끝난 역), 마지막으로 지난 역 |
| `passing` | 그 사이에 지나는 역 `[{station, at_m}]`. `at_m`은 단계 출발부터의 거리(m). 진행 표시에 쓴다 |
| `direction` | `<다음 역> 방면` |
| `terminal_direction` | 종착역 방면(예: `오금 방면`, `내선순환`). 확실할 때만 있다(아래) |
| `distance_m`, `est_minutes`, `exposure_m` | 거리, 예상 시간(분), 그중 지상 노출 거리 |

- 종착역 방면 찾기: `line_routes`에서 같은 노선이고 '출발역 바로 다음 정차역이 이 단계의 다음 역'이며 그 뒤에 도착역이 있는 relation을 모두 찾는다. 그 방면이 하나뿐이면 쓰고, 여러 개(예: 1호선 인천행·동두천행, 4호선 불암산행·진접행)면 넣지 않는다. 순환선은 정차역 순서를 한 바퀴 더 이어 붙여 찾는다.

### `transfer` (환승 통로)

| 키 | 내용 |
|---|---|
| `station` | 환승역 |
| `from_line`, `to_line` | 앞뒤 `ride` 단계의 짧은 노선 이름(없으면 허브의 노선 이름) |
| `distance_m`, `est_minutes` | 환승 거리, 예상 시간 |
| `source` | `seoul_metro`(서울교통공사 자료) 또는 `estimated`(추정, 7절) |
| `underground` | 지하 통로로 보는지(양쪽 승강장이 모두 지하일 때 true, 7절의 가정) |

### `warning` (지상 노출 경고)

| 키 | 내용 |
|---|---|
| `at`, `after_m` | 노출이 시작되는 곳: 직전에 지난 역과 그 역에서 지난 거리(m). 역에서 바로 시작하면 0 |
| `portal` | 터널 출입구(갱구, 노드 `f`의 1)에서 나가는지 |
| `lat`, `lon` | 노출이 시작되는 지점 좌표 |
| `exposure_m` | 다시 지하로 들어갈 때까지(또는 도착까지)의 노출 거리. 여러 단계에 걸칠 수 있다 |
| `structure`, `structures` | 가장 긴 구조(`ground`·`bridge`), 구조별 거리(m) |
| `ends_underground` | true = 다시 지하로 들어감, false = 지상인 채로 도착 |
| `in_step` | 이 노출이 시작되는 단계의 번호 |

### 글 안내 (`route.py` 기본 출력)

```
① 3호선 · 일산선 | 대화 → 오금 방면(다음 역 주엽) … 백석까지 5.3km, 약 1시간 30분 (지나는 역: 주엽 1.4, 정발산 3.0, 마두 3.9)
① 4호선 · 과천선 | 인덕원 → 정부과천청사 방면 … 사당까지 10.5km, 약 3시간 1분 (지나는 역: 정부과천청사 3.1, …, 남태령 8.9)
    선 구간: 과천선 인덕원→남태령 8.9km · 4호선 남태령→사당 1.7km
   ※ 지상 노출 | 신도림에서 도착할 때까지 1.1km (지상 1.1km)
⑩ 환승 | 신도림: 2호선 → 1호선, 81m, 약 1분 (서울교통공사 자료, 지상)
```

- 지나는 역 뒤의 숫자는 단계 출발부터의 거리(km)다. 예전 체크포인트 목록은 `--checkpoints`로 본다.

## 12. 알려진 한계
- 역 깊이 자료와 대조한 277개 중 2개가 다르다: `1호선 서울`(지상 경부선 승강장도 1호선 노선에 들어 있어 부착점 3개 중 1개가 지상), `2호선 한양대`(자료는 B2, OSM은 교량으로 표시).
- 동대구처럼 OSM이 역 건물 밑 선로를 `tunnel`로 그린 곳은 지하로 계산된다.
- 선 이름은 OSM 선로 way의 `name`을 그대로 쓴다. 선 경계가 실제 공식 경계와 조금 다를 수 있다(예: 신도림~구로는 대부분 `경부선`, 구로 직전 0.3km가 `경인선`).
- 종착역 방면은 OSM 노선 relation의 정차 순서가 맞아야 나온다. 방면이 여럿인 노선(1·4·5·7호선 등)은 대부분 `<다음 역> 방면`만 나온다.
- 경부고속선을 따라가는 긴 단계(예: 부산 시청 → 서울 을지로3가 시험의 129km 단계)에 지나는 역이 하나도 나오지 않는다. 원인은 확인하지 않았다(역이 본선 옆 승강장 선로에만 붙었을 가능성이 있다).
- 노선 relation이 일부만 덮은 선로에서는 한 선로를 따라가는데 단계가 나뉠 수 있다(예: 수서→평택지제는 `수서평택고속선` → `GTX-A · 수서평택고속선` → `수서평택고속선` 3단계).
- 부착 못 한 역 9개는 운행 선로 근처에 없는 역이다(레일바이크·관광열차, 장항선 옛 역 등). 목록은 `graph_report.json`에 있다.

## 13. basemap.json

- 만드는 스크립트: `scripts\build_basemap.py` (`python -I scripts\build_basemap.py`; 원본은 `data\raw\basemap\`, 없으면 `--fetch`). 쿼리는 `scripts\queries\basemap_*.overpassql`.
- 용도: 타일을 쓸 수 없는 곳(claude.ai Artifact, 오프라인)의 가벼운 바탕 지도. 크기 약 77KB(gzip 약 46KB).
- 출처: © OpenStreetMap contributors (ODbL), 2026-11-10 받음.

```json
{"format": "basemap-1", "precision": 5, "attribution": "© OpenStreetMap contributors (ODbL)",
 "lines":  [{"k": "coast", "p": "<인코딩 폴리라인>"}, {"k": "admin", "p": "..."}],
 "labels": [{"k": "region", "name": "서울특별시", "lat": 37.5667, "lon": 126.9783},
            {"k": "city", "name": "수원", "lat": 37.2633, "lon": 127.0287}]}
```

- `p`: 3.5절과 같은 Google 인코딩 폴리라인(소수 5자리)이라 같은 `decodePolyline`으로 푼다. 선 하나가 폴리라인 하나이고 닫힌 고리는 첫 점과 끝 점이 같다.
- `lines[].k`
  - `coast`: `natural=coastline` 중 한국 영역(ISO3166-1=KR)만. 북한·일본 해안은 영역 필터로 빠진다. 더글러스-포이커 200~400m, 2km보다 짧은 섬·조각은 뺐다(제주·울릉·독도 등 큰 섬은 있음).
  - `admin`: 시·도(admin_level=4) 경계선. 공유 경계는 한 번만 넣었다. OSM 경계는 바다(영해선)까지 그려져 있어, 시·도 사이 경계와 휴전선 구간만 쓰고 한 시·도에만 속한 바다 쪽 경계는 뺐다. 150m로 줄였다.
- `labels[].k`: `region` = 시·도 이름(광역시급은 OSM admin_centre, 도는 손으로 정하거나 면적 무게중심), `city` = 인구순 대표 도시와 도청 소재지(짧은 이름, 예 `수원`).
- OSM 현재 상태: 광주광역시와 전라남도가 `전남광주통합특별시`(relation 21039457) 하나라 시·도 경계에 둘 사이 선이 없다. 이름표도 하나다(`광주`는 city 이름표로만 있다).
- 한계: 휴전선 구간은 위경도 상자로 가려냈고(`DMZ_BOX`) 한강 하구 부근 경계는 근사다. 경계선이 해안선과 만나는 끝점은 단순화 때문에 몇백 m 어긋날 수 있다.

- 지도 위 점(지도 누르기·내 위치·출구 팝업): 1.5km 안 가까운 출입구 3곳과, 출입구 자료가 없는 1.5km 안의 역(허브)에 '가상 지상 간선'(직선 거리 × 1.3)으로 잇는다. 둘 다 없으면 20km 안 가장 가까운 역 3곳. 이 거리는 모두 지상 노출로 센다. 출발과 도착이 둘 다 점이면 '지상으로 바로 걷기'도 후보에 넣는다.
- 지상 걷기 간선(웹에서만): 지하로 갈 길이 없을 때(앞이 막힘, 끊긴 노선)의 대비책. 1.5km 안의 다른 역끼리 가장 가까운 출입구(없으면 허브) 사이를 직선 × 1.3 길이, 구조 `ground`, 종류 `surface`로 잇는다(2026-11-10 그래프에서 1,704개). `graph.json` 간선 뒤에 붙여 원래 간선 번호는 그대로고, 기본 탐색(= `route.py`)에서는 쓰지 않는다. 기본 탐색이 실패할 때만 `findRoute(..., {surface: true})`로 다시 찾고, 안내에는 '지상 걷기' 단계(`type: 'surface'`)로 나온다.
- 앞이 막힘: 마지막으로 '도착'을 누른 체크포인트와 다음 체크포인트 사이의 선로 간선, 그리고 그 선 모양에서 40m 안에 나란히 있는 선로(같은 터널의 반대 방향)를 막는다. 들어갈·나갈 출구가 막히면 그 출입구 간선만 막는다. 되돌아갈 거리는 마지막 확인 뒤 걸은 시간 × 걷는 속도(다음 체크포인트까지를 넘지 않게)로 추정한다.
- 승강장 깊이: 역 시트의 '이 역 정보'에서 `stations[].depth`(6.1절, 서울교통공사 1~8호선 역만)를 승강장 줄마다 보여 준다(지하 층이면 층·승강장·선로 깊이, 고가·지상이면 그 글자만). 없는 역은 깊이를 숨긴다.
- 지상 도보 길(`walk.js`): 인터넷이 되면 FOSSGIS OSRM 도보 경로(`routing.openstreetmap.de/routed-foot`)로 출발·도착 지점과 출구 사이 등을 실제 길로 바꾼다. 거리·시간·지상 노출도 그 거리로 바뀐다(경로 선택은 직선 × 1.3으로 한 그대로). 지도·결과에 '도보 경로: FOSSGIS OSRM · © OpenStreetMap'을 밝힌다. claude.ai 미리보기·오프라인에서는 요청이 막혀 직선을 쓴다.
- 여기서 지하로 갈 수 있는 곳(`reach.js`): 2026-11-10 그래프, 시속 3.5km. 시청(서울) 30분 6곳 · 1시간 22곳 · 2시간 65곳 · 4시간 150곳, 강남 5 · 20 · 50 · 115곳, 대화 1 · 2 · 4 · 4곳(일산선은 백석 뒤로 지상이라 4곳에서 멈춘다).
- 검증: `node scripts\check_router.js` — 역 쌍 9개(한강 5호선 차단 1개 포함)를 `route.py --json`과 비교한다(간선 목록, 총거리, 노출, 단계 내용, 글 안내 문장). `node scripts\check_guide.js` — 가장 가까운 지하로(시청 앞, 해운대 해변, 역 없는 지리산), 대화→백석 체크포인트·도착·앞이 막힘·다시 찾기, 들어갈 출구가 막혔을 때. `node scripts\check_reach.js` — 도달 범위(시청·대화·강남·지상역, 지하 간선만 썼는지, 띠·막은 간선). `node scripts\check_walk.js` — 가짜 OSRM 응답으로 도보 구간 바꾸기(요약·체크포인트·위치 추정 선이 새 거리와 맞는지, 저장, 실패·시간 초과, 가장 가까운 지하로 순위 바꾸기).
- 연결점: `UG.search.register(provider)`(검색 제공자 더하기), `UG.app.onPlan(cb)`·`UG.app.plan().items`(경로가 바뀔 때), `UG.app.blocked` + `UG.app.reroute()`(구간 막기), `UG.app.pointEndpoint(lat, lon, label)`, `UG.app.startGuide()`, `UG.app.runNearest(lat, lon, label, isCenter)`, `UG.app.openStation(역 번호, {tab})`, `UG.app.openSearch('to')`, `UG.app.drawWalkLeg(coords, kind)`(지상 도보 구간 그리기, 다른 길 찾기로 바꿀 자리).

## 15. places.json (오프라인 장소 검색 색인)

인터넷 없이 목적지를 찾기 위한 장소 이름표다. 지도 앱처럼 "서울대병원", "역삼동", "OO아파트", "강남구청", "OO초등학교"로 찾게 한다. 온라인 검색(Photon)은 따로 붙이고, 이 파일은 오프라인일 때(또는 온라인 결과와 함께) 쓴다.

- 만드는 스크립트: `scripts\build_places.py` (프로젝트 폴더에서 `python -I scripts\build_places.py --fetch`. 원본이 이미 있으면 `--fetch` 없이 만들기만 한다. 만들기는 약 10초)
- 원본: `data\raw\places\*.json` (Overpass 응답 그대로, 한 번에 하나씩 받음). 시·도 경계는 `data\raw\basemap\admin.json`, 역은 `web\data\graph.json`의 `stations`를 읽기만 한다.
- 검색 함수: `web\js\places.js` — `searchPlaces(index, query, {near: [lat, lon], limit: 10})`. 브라우저에서는 `UG.places.searchPlaces`(전역 `searchPlaces`도 둔다), Node에서는 `require()`. 화면에 붙일 때는 `UG.search.register(provider)`로 검색 제공자를 하나 더하면 된다(이 작업에서는 붙이지 않았다).
- 크기(2026-11-10 빌드): 2,999,976 byte, gzip 840,950 byte. 장소 60,497개. 목표 3,000,000 byte에 맞추려고 일부를 뺐다(아래 '크기 맞추기').
- 출처 표기: © OpenStreetMap contributors (ODbL). OSM 기준 시각 2026-11-10.

### 15.1 형식

```json
{"format": "places-1",
 "attribution": "© OpenStreetMap contributors (ODbL)",
 "osm_base": "2026-11-10",
 "types": ["sido","sigungu","dong","village","station","hospital","university","school","gov","police","fire","library","apartment","landmark"],
 "areas": ["", "강원특별자치도", "경기도", "서울특별시 종로구", "경기도 수원시 장안구", ...],
 "p": [["강원특별자치도", 0, 3777253, 12838207, 0], ["서울대학교병원", 5, 3757961, 12699900, 3], ...]}
```

`p`의 한 줄이 장소 하나다: `[이름, 종류 번호, 위도×1e5, 경도×1e5, 지역 번호, (다른 이름 목록)]`

| 칸 | 내용 |
|---|---|
| 이름 | 표시 이름(OSM `name`). 역은 `<역 이름>역`. 아파트 건물에서 온 단지는 동 번호를 뗀 이름 |
| 종류 번호 | `types` 위치 |
| 위도·경도 | × 100000 정수(그래프와 같은 정밀도) |
| 지역 번호 | `areas` 위치. 그 점이 든 시·도 + 시·군·구(+ 일반구). 같은 이름(여러 `중구청`, `신사동`)을 구별하는 데 쓴다. 시·도 항목은 빈 문자열, 시·군·구 항목은 상위 지역(예: `장안구` → `경기도 수원시`) |
| 다른 이름 | 있을 때만(6번째 칸). OSM `short_name`·`alt_name`·`official_name`·`old_name`(최대 2개), 역은 `stations[].names`의 별칭 |

- 정렬: 종류 → 지역 → 이름(gzip이 잘 줄도록). 순서에 뜻은 없다.
- 지역 이름은 2026-11-10 OSM 그대로다(예: `전남광주통합특별시`, 인천 `제물포구`).

### 15.2 종류와 출처 (개수는 2026-11-10 빌드)

| 종류 | 개수 | 뜻 | OSM 출처 | 대표 좌표 |
|---|---:|---|---|---|

### 15.3 크기 맞추기

3,000,000 byte를 넘으면 아래 순서로 묶음을 뺀다. 넘침을 해소하는 마지막 묶음은 일부만 뺀다(아파트는 건물이 적은 단지부터).

1. `village`(리) → 2. `library` → 3. 아파트 D(건물 1동뿐인 단지, 빌라·오피스텔이 많다) → 4. 아파트 C(건물 2~4동으로만 아는 단지) → 5. 아파트 B(이름에 '아파트·단지'가 없는 주거단지 경계: 빌라·연립·마을과 브랜드 이름 단지가 섞임) → 6. `fire` → 7. `police` → 8. 아파트 A(이름에 '아파트·단지'가 든 주거단지 경계, 또는 건물 5동 이상 단지) → 9. `landmark`
- 2026-11-10 빌드에서 뺀 것: 리 15,119, 도서관 2,353, 아파트 D 5,776, 아파트 C 478, 아파트 B 3,499(일부).

### 15.4 검색 순위 (`web\js\places.js`)

1. 정규화(이름과 질의어 똑같이): 소문자로 바꾸고, 괄호 안 내용을 지우고, 한글·영문·숫자·자모가 아닌 글자(공백, `·`, `-` 등)를 지운다. 세 글자 이상이면 끝의 `역`을 뗀다(`서울역` → `서울`). `동`은 떼지 않는다.
2. 열쇠(장소마다 처음 검색할 때 한 번 만들어 둔다): 본 이름과 다른 이름 각각에서 더 만든다.
   - 앞의 시·도 이름을 뗀 것: `서울특별시강남구청` → `강남구청`
   - 시·도 줄임: `세종특별자치시청` → `세종시청`, `부산광역시청` → `부산시청`, `제주특별자치도청` → `제주도청`
   - `대학교` → `대`: `서울대학교병원` → `서울대병원`
   - 행정동 번호를 뗀 것(`dong`만): `역삼1동` → `역삼동`, `종로1·2·3·4가동` → `종로동`. 그래서 "역삼동"으로 역삼1·2동도 나온다.
3. 맞춤 점수: 같음 1000 > 앞부분 600 > 가운데 300. 앞부분·가운데는 남는 글자 하나에 8점씩 깎는다(최대 150). 별칭 열쇠로 맞으면 20점 깎는다.
4. 질의어 변형: 끝의 `아파트`를 뗀 질의어로도 맞춘다(10점 깎음, 아파트가 아닌 장소는 300점 더 깎음). OSM 이름이 `은마`인 단지를 "은마아파트"로 찾기 위한 것이다. 이름 쪽에서 `아파트`를 떼지 않는 것은 "강남"이 `강남아파트`와 '같음'으로 맞아 강남구보다 앞서는 것을 막기 위해서다.
5. 종류 가산점: 시·도 80, 시·군·구 70, 동 60, 대학 55, 병원·관공서 50, 역 45, 명소 40, 아파트 30, 학교 25, 경찰·소방·도서관 20, 리 15. 역은 이름에서 `역`을 떼고 맞추므로, `수원시청`·`강남구청`처럼 시설과 이름이 같아지면 시설이 앞서도록 낮게 두었다.
6. 거리 가산점(`near`를 줄 때): `150 / (1 + 거리km / 2)` — 0km 150점, 2km 75점, 10km 25점, 100km 3점. 맞춤 단계 사이의 차이(약 400점)를 넘지 않으므로, 가까운 곳은 같은 단계 안에서만 앞선다(예: 여러 `신사동` 중 가까운 것).
7. 초성 검색: 질의어가 자음(ㄱ~ㅎ)만이면 열쇠의 초성으로 같은 규칙을 쓰고 100점 깎는다(`ㅅㅇㄷㅂㅇ` → 서울대학교병원, `ㄱㄴㄱㅊ` → 강남구청).
8. 점수가 같으면 이름이 짧은 것이 먼저다. 결과는 `{name, type, area, lat, lon, score}`이고, `near`를 주면 `distance_km`도 붙는다.

- 속도(이 PC, Node 24): JSON 풀기 약 40ms, 첫 검색 때 열쇠 만들기 120~280ms(62,627개), 검색 한 번 2~5ms(전체를 한 번 훑는다). 휴대폰에서는 재지 않았다. 화면이 놀고 있을 때 `UG.places.prepare(index)`를 미리 불러 두면 첫 검색이 빨라진다.

### 15.5 시험 결과와 한계 (2026-11-10)

`searchPlaces` 1위(근처 지정 없음): 서울대병원 → 서울대학교병원(종로구), 강남구청 → 강남구청, 역삼동 → 역삼동(그다음 역삼1·2동), 잠실 → 잠실역(그다음 잠실동), 해운대 → 해운대역(그다음 해운대구), 동대구 → 동대구역, 판교 → 판교(분당구 `place` 점, 그다음 판교역), 수원시청 → 수원시청, 광화문 → 광화문역(그다음 광화문광장).

- 서울 대치동 은마아파트는 OSM에 단지 이름이 없다(건물 이름이 번호뿐이고 주거단지 경계도 없음). "은마아파트"는 부산·전주의 같은 이름 단지가 먼저 나오고, 서울 쪽은 `은마종합상가`·`은마치안센터`가 나온다. `near`로 서울 위치를 주어도 이름이 정확히 같은 다른 지역 단지가 앞선다(맞춤 단계 차이가 거리 가산점보다 크다).
- 광화문(문 자체)은 OSM 자료에 없어(`tourism`·`historic` 태그로 받지 못함) 광화문광장·광화문역으로 대신한다.
- 행정동 relation은 2,083개뿐이다(전국 행정동 약 3,500). 나머지는 `place` 점(법정동)으로 채워지지만, 행정동 이름(예: OO1동)으로만 찾으면 빠지는 곳이 있다.
- 아파트는 OSM에 이름이 있는 단지만 들어 있고, 크기 때문에 일부를 뺐다(15.3절). 리(마을)와 도서관은 들어 있지 않다.
