# 지하로 — 코드 설명과 예상 질문

발표에서 코드를 직접 설명하기 위한 문서다. 큰 그림에서 시작해 핵심 함수까지 내려간다.

- 근거는 저장소의 코드와 `docs\graph-format.md`, `docs\plan.md`, `docs\계획서.md`다. 코드와 문서가 다르면 코드를 따르고 `참고`로 적었다.
- 코드는 짧게 잘라 실었다. 줄임은 `...`로 표시했다. 함수 이름으로 찾을 수 있게 줄 번호는 적지 않았다.
- 직접 돌려 확인하지 못한 수치(속도, 정확도)는 문서에 적힌 값을 옮기고 그렇게 밝혔다.

## 2. 데이터 파이프라인

### 2.1 OSM 받기

- OSM은 지도를 만드는 공개 데이터베이스다. 선로는 `way`(점들을 이은 선), 역은 `node`(점)로 들어 있다.
- Overpass API는 OSM에서 조건에 맞는 것만 뽑아 주는 공개 서버다. 쿼리 파일에 조건을 쓴다.
- 선로는 한 번에 받기엔 크다. 그래서 위도·경도 상자(타일) 6개로 나눠 받는다(`ways_A1`, `A2`, `B`, `C`, `D`, `E`). 예를 들어 `A1`은 위도 37.0~37.7, 경도 124.5~128.0이다.

```
[out:json][timeout:300][bbox:37.0,124.5,37.7,128.0];
way[railway~"^(rail|subway|light_rail|monorail|narrow_gauge)$"];
out geom;
```

- `overpass_fetch.py`는 한 번에 하나만 요청한다. 실패하면 30초 쉬고 대체 서버로 한 번만 더 시도하고, 계속 두드리지 않는다(공개 서버 예절).
- 역(`stations`), 정차 위치(`stops`), 출입구(`entrances`), 노선 relation(`routes`)은 한국 전체(`ISO3166-1=KR`)로 따로 받는다.
- `merge_ways.py`가 타일 파일을 합쳐 중복을 없애고, 가운데 노드가 속한 시·도를 붙인다. 북한·일본 선로는 어느 시·도에도 안 들어가 빠진다.

### 2.2 지하·교량·지상 판정

`build_graph.py`의 `classify`가 전부다.

```python
def classify(tags):
    t, b = tags.get("tunnel"), tags.get("bridge")
    if t and t != "no":
        return "tunnel"
    if b and b != "no":
        return "bridge"
    return "ground"  # layer<0, covered=yes도 지상으로 둔다
```

- **`tunnel` 태그만 지하로 본다.** `layer<0`은 지하로 보지 않는다.
- 이유: 경부선 금정~수원(약 16km, 선로 4줄)은 OSM에서 `layer=-1`인데 실제로는 지상이다. 경인일보 기사에 금정~군포~당정 4.84km가 지상으로 운행 중이라고 나온다(`docs\data-check.md` 4.4절). `layer<0`을 지하로 치면 이 구간이 지하로 잘못 잡힌다.
- 전국에서 `layer<0`인데 `tunnel`이 없는 본선은 90.1km이고 그중 63.6km가 이 경부선이다.
- `covered=yes`(방음터널 등)도 지상으로 둔다.
- 한계: 동대구처럼 OSM이 역 건물 밑 선로를 `tunnel`로 그린 곳은 지하로 계산된다(`graph-format.md` 12절).

### 2.3 그래프 만들기 (`build_graph.py`의 `main` 순서)

1. **선로 읽기** (`load_tracks`): 선로마다 속성(구조, 철도 종류, 측선 여부, 노선 이름, 지역, 선 이름)을 붙인다. 제주는 뺀다.
2. **역 묶기** (`group_stations`): 정규화한 이름(괄호·공백·끝의 '역' 제거)이 같고 500m 안에 있거나 같은 `stop_area`에 든 역 노드를 한 역으로 묶는다.
3. **역을 선로에 붙이기** (`attach_stations`): 선로 위 정차 위치를 먼저 쓴다. 없으면 200m 안의 가장 가까운 본선에 붙인다. 이때 가장 가까운 선로와 **구조가 같은** 선로만 함께 붙인다(지상역이 그 밑을 지나는 다른 노선 터널에 붙는 것을 막는다).
4. **선로 자르기** (`split_tracks`): 끝점, 다른 선로와 만나는 점, 역 부착점에서 선로를 잘라 간선 후보로 만든다.
5. **합치기** (`contract`): 이웃이 둘뿐이고 양쪽 속성이 같은 중간 점은 없애고 두 간선을 하나로 합친다. 그래프가 작아진다. 단, 터널 출입구와 역 부착점은 남긴다.
6. **터널 출입구 표시**: 터널 선로와 터널 아닌 선로가 만나는 노드에 표시 비트 1을 준다(`portal`).
7. **역 허브** (`build_stations`), **환승** (`build_transfers`), **출입구** (`link_entrances`): 아래에서 설명한다.
8. **쓰기** (`write_graph`): 압축 JSON을 만든다.

#### 승강장 허브

```python
by_lines = defaultdict(list)
for a in atts:
    by_lines[tuple(a["lines"])].append(a)
for lines, group_atts in by_lines.items():
    hp = (평균 위도, 평균 경도)          # 부착점들의 중심
    v = len(nodes)
    nodes.append({"p": hp, "flag": 8})   # 허브 노드
    s["hubs"].append({"node": v, "lines": list(lines), "ug": any(a["ug"] for a in group_atts), ...})
    for a in group_atts:                 # 부착점 → 허브 간선(platform)
        platform_edges.append({"a": a["node"], "b": v, ...})
```

(위 코드는 줄여 쓴 것이다. 원문은 `build_stations`.)

- 역 하나에서 **노선별로** 허브를 하나 만든다. 상·하행 선로는 같은 허브에 이어진다.
- 환승 간선은 허브끼리만 잇는다. 그래서 '다른 노선을 거쳐 같은 노선의 반대 선로로 가는 지름길'이 생기지 않는다.
- 부착점이 지하인지는 그 점에 붙은 본선이 **모두** 터널인지로 정한다(`att_info`). 허브는 부착점 중 하나라도 지하면 지하다.

#### 환승 간선

```python
def est_transfer_m(d):
    """추정 환승 거리: 직선 거리 × 1.3 + 50m (통로가 굽고 계단이 있는 것을 대략 반영)."""
    return d * 1.3 + 50
```

- 같은 역 안의 허브끼리 600m 안(`GROUP_RADIUS_M + 100`)이면 환승 간선을 만들고, 처음에는 위 추정 거리를 넣는다.
- 서울교통공사 환승 거리 자료(CSV)에서 '환승역명 + 호선 + 환승노선'이 맞는 허브 쌍은 실측 값으로 바꾼다(`src = seoul_metro`). 140행 중 139행을 반영했다. 못 맞춘 1행은 5호선 본선·지선을 OSM에서 구분할 수 없는 경우다.
- 양쪽 승강장이 모두 지하면 환승 통로가 지하라고 **가정**한다. OSM에는 환승 통로 정보가 거의 없다. 이 가정은 발표에서 밝혀야 한다(`graph-format.md` 7절).
- 추정식의 1.3과 50m는 실측 근거가 없다. 문서에도 그렇게 적혀 있다.

- OSM 출입구 4,562개를 300m 안의 역에 잇는다. 태그 설명(예: `잠실역7번출구`)의 역 이름이 맞는 역을 먼저 고르고, 없으면 가장 가까운 역을 고른다.
- 역 안에서는 가장 가까운 **지하** 허브에 잇는다. 지하 허브가 있으면 간선 구조가 `entrance`(가중치 1), 지상 허브밖에 없으면 `ground`(가중치 1000)다.
- 4,551개가 이어졌다.

### 2.4 압축해서 저장하기

간선이 수만 개라 객체 목록으로 두면 파일이 커진다. 그래서 **열(column)별 배열**로 저장한다.

```json
"edges": {"a": [0, 5, ...], "b": [3, 9, ...], "len": [120.5, 88.0, ...],
          "s": [0, 2, ...], "k": [0, 0, ...], "g": ["_p~iF~ps|U...", ...], ...}
```

- 간선 j의 길이는 `edges.len[j]`다. 노드·간선 번호는 배열 위치다.
- `s`는 구조 번호(`tables.structs`: 터널, 교량, 지상, 출입구, 지하 통로), `k`는 종류 번호(`track`, `platform`, `transfer`, `entrance`)다.
- 좌표는 위도·경도 × 100000 정수로 줄인다(`3758851` → 37.58851).
- 선 모양(`g`)은 더글러스-포이커 방식으로 점을 줄인 뒤(오차 5m 이내) 폴리라인으로 압축한다. 길이(`len`)는 줄이기 전 좌표로 잰 값이라 정확하다.
- 브라우저는 `graph.js`의 `decodePolyline`로 푼다. 각 점은 앞 점과의 차이(델타)만 저장돼 있어서 누적해 더한다.

```js
function decodePolyline(s, precision) {
  const f = Math.pow(10, precision == null ? 5 : precision);
  const pts = [];
  let i = 0, lat = 0, lon = 0;
  while (i < s.length) {
    for (let k = 0; k < 2; k++) {
      let r = 0, sh = 0, b;
      do { b = s.charCodeAt(i++) - 63; r |= (b & 31) << sh; sh += 5; } while (b >= 32);
      const d = (r & 1) ? ~(r >> 1) : (r >> 1);
      if (k === 0) lat += d; else lon += d;
    }
    pts.push([lat / f, lon / f]);
  }
  return pts;
}
```

- 크기: 3,227,492 byte, gzip 970,700 byte(2026-11-10 빌드, `graph-format.md` 맨 위).
- 허브·출입구·환승 간선은 `track`이 아니라서 `g`가 빈 문자열이다. 두 노드를 직선으로 그린다.

## 3. 경로 탐색

### 3.1 색인 만들기 (`graph.js`의 `indexGraph`)

받은 JSON을 곧바로 탐색에 쓰지 않고 한 번 색인한다.

```js
const under = new Set(T.under_structs.map(function (s) { return T.structs.indexOf(s); }));
const weight = new Float64Array(nEdges);
for (let e = 0; e < nEdges; e++) weight[e] = under.has(E.s[e]) ? g.weights.under : g.weights.exposed;
```

- **가중치**: 구조가 터널·출입구·지하 통로면 `weights.under`(1), 교량·지상이면 `weights.exposed`(1000)다. 값은 `graph.json`의 `weights`에 들어 있어 코드를 고치지 않고 바꿀 수 있다.
- **인접 목록(CSR)**: 노드마다 '이웃 간선과 반대쪽 노드' 목록을 큰 배열 둘(`adjEdge`, `adjNode`)에 평평하게 담는다. 노드 v의 이웃은 `adjStart[v]`부터 `adjStart[v+1]` 직전까지다. 객체 목록보다 메모리를 덜 쓰고 빠르다.
- 그 밖에 노드 → 역 번호(`nodeStation`), 허브 → 노선 이름, 역 → 출입구 목록을 만든다.
- 웹에서만 '지상 걷기 간선'을 더 붙인다(1.5km 안의 다른 역끼리, 직선 × 1.3). 기본 탐색은 이 간선을 쓰지 않는다(3.5절).

### 3.2 비용과 가중치

**비용 = 길이(m) × 가중치.**

| 경로 | 계산 | 비용 |
|---|---|---|
| 지하 3,000m | 3,000 × 1 | 3,000 |
| 지하 500m + 지상 10m | 500 × 1 + 10 × 1000 | 10,500 |

두 번째가 훨씬 짧지만 비용이 크다. 그래서 첫 번째가 뽑힌다. 즉 지상 1m는 지하 1km와 같다. 지하로만 가는 길이 있으면 그 길이 자동으로 뽑히고, 없으면 지상 노출이 가장 짧은 길이 뽑힌다. 이 문서에서 '지상 노출'은 교량과 지상 구간의 길이다.

- 별도의 '지하 우선' 분기 코드는 없다. 가중치 하나로 같은 효과를 낸다.
- 1000이라는 값을 어떻게 골랐는지는 문서에 근거가 없다. `plan.md`는 "지상 1m를 지하 1km처럼 비싸게"라고만 적었다. 지하 우회가 지상 1m당 1km를 넘으면 지상 구간을 택한다는 뜻이다(8절 Q2 참고).

### 3.3 다익스트라 (단계별)

`route.py`의 `dijkstra`가 가장 읽기 쉽다. JavaScript(`router.js`)도 같은 구조다.

```python
while heap:
    c, v = heapq.heappop(heap)
    if v in done:
        continue
    done.add(v)
    if v in targets:
        return v, prev
    for ei, w in g["adj"][v]:
        if ei in blocked:
            continue
        nc = c + E["len"][ei] * g["weight"][ei]
        if nc < cost.get(w, float("inf")):
            cost[w] = nc
            prev[w] = (ei, v)
            heapq.heappush(heap, (nc, w))
```

단계로 풀면 다음과 같다. (앞에서 `cost`는 출발 노드들을 0으로, `heap`은 `(0, 출발 노드)`로 채워 둔다.)

1. 힙에서 **지금까지 비용이 가장 작은 노드** v를 꺼낸다.
2. 이미 확정한 노드(`done`)면 건너뛴다. 힙에 같은 노드가 여러 번 들어 있을 수 있어서다.
3. v를 확정한다. v가 도착 노드 중 하나면 **그 자리에서 끝낸다.** 비용이 작은 순으로 꺼내므로 처음 꺼낸 도착 노드가 최저 비용이다.
4. v의 이웃을 본다. 막힌 간선(`blocked`)은 건너뛴다.
5. 이웃 w까지 `v까지 비용 + 길이 × 가중치`를 계산한다. 기존 기록보다 싸면 `cost`, `prev`(어느 간선으로 왔는지)를 고치고 힙에 넣는다.
6. 끝나면 `prev`를 도착 노드에서 거꾸로 따라가(`path_edges`) 간선 순서를 얻는다.

- **출발·도착이 여러 노드다.** 역은 허브가 여러 개(노선마다 하나)라서 모든 허브를 비용 0으로 출발 목록에 넣고, 도착 허브 중 먼저 닿는 곳에서 끝낸다.
- **이진 힙.** 힙에 넣고 빼는 비용은 노드 수의 로그에 비례한다. 파이썬은 `heapq`를 쓰고, JavaScript에는 내장 힙이 없어 직접 구현했다(`router.js`의 `Heap`).

```js
Heap.prototype.less = function (i, j) {
  return this.c[i] < this.c[j] || (this.c[i] === this.c[j] && this.v[i] < this.v[j]);
};
Heap.prototype.push = function (cost, node) {
  this.c.push(cost); this.v.push(node);
  let i = this.c.length - 1;
  while (i > 0) {
    const p = (i - 1) >> 1;
    if (!this.less(i, p)) break;
    this.swap(i, p); i = p;
  }
};
```

- `less`가 비용이 같으면 **노드 번호가 작은 쪽**을 먼저 꺼내게 한다. 파이썬의 `heapq`가 튜플 `(비용, 노드)`를 비교하는 것과 같은 순서다. 비용이 같은 경로가 여럿일 때 두 언어가 같은 경로를 고르게 하려는 것이다.
- JavaScript 쪽은 노드 수만큼의 숫자 배열(`Float64Array`, `Int32Array`)로 `cost`, `prevEdge`를 두어 더 빠르다.

### 3.4 출발·도착 연결

`router.js`의 `findRoute(G, from, to, opts)`가 끝점 종류를 노드 목록으로 바꾼다.

| 끝점 | 다익스트라에 넣는 것 |
|---|---|
| 역(`station`) | 그 역의 허브들, 시작 비용 0 |
| 지도 위 점(`point`) | 가까운 출입구(1.5km 안 3곳)와 터널 출입구·차량기지에 '가상 지상 간선'. 비용 = 거리 × 1.3 × 지상 가중치 |
| 선로 위 점(`edgept`) | 그 간선의 양 끝 노드. 비용 = 끝까지 걷는 거리 × 가중치 |
| 나갈 곳(`egress`) | 여기서 나가기 후보 |

- 지도 위 점은 걸어서 닿는 길이 정확히 있는 게 아니라서 직선 거리 × 1.3(`DETOUR`)으로 어림하고, 전부 지상 노출로 센다.
- 출발·도착이 둘 다 점이면 '지상으로 바로 걷기'도 후보에 넣는다. 지하로 가는 것보다 지상으로 걷는 비용이 더 싸면 바로 걷는 쪽이 이긴다.

### 3.5 막힌 간선과 지상 걷기 대비책

- 막힌 간선은 간선 번호의 `Set`이다. 탐색할 때 `blocked.has(ei)`면 건너뛴다.
- 앞이 막혀 지하로 갈 길이 아예 없으면 `findRoute`가 `null`을 돌려준다. 그때 `app.js`가 `{ surface: true }`로 다시 부른다.

```js
const route = RT.findRoute(state.G, f, t, { blocked: state.blocked })
           || RT.findRoute(state.G, f, t, { blocked: state.blocked, surface: true });
```

- `surface: true`이면 역 사이 '지상 걷기' 간선도 쓴다. 안내에는 '지상 걷기' 단계로 나온다.
- 참고: 막은 간선은 `state.blocked`(메모리의 `Set`)에만 있다. `app.js`에서 저장소(`localStorage`)에 쓰는 것은 레이어·속도·테마·화면 위치·안내문 확인 여부뿐이고(`SV.set` 호출 확인), 막은 구간을 저장하는 코드는 찾지 못했다. `plan.md`는 "차단한 구간은 기기에 저장"이라고 적었다. 새로고침하면 막은 구간이 사라지는지는 직접 돌려 확인하지 못했다.

### 3.6 대안 경로 (가중치 15)

기본 경로는 항상 지하 우선(1000)이다. 그 위에 한 번 더, 지상 가중치를 **15**로 낮춰 다시 찾는다.

```js
const ALT = { exposedW: 15, minSavedFrac: 0.2, minSavedMin: 30, maxExtraExposedM: 2000 };
...
const saved = main.total_m - r.total_m, extra = r.exposed_m - main.exposed_m;
if (!(saved > 0) || extra > ALT.maxExtraExposedM) return null;
if (saved / main.total_m < ALT.minSavedFrac && saved / mpm < ALT.minSavedMin) return null;
```

대안을 카드로 보여 주는 조건은 다음을 **모두** 만족할 때다.

1. 기본 경로와 다른 경로다(`sameRoute`가 아니다).
2. 걷는 거리가 줄어든다.
3. 줄어드는 양이 20% 이상이거나, 걷는 시간으로 30분 이상이다. (둘 중 하나)
4. 늘어나는 지상 노출이 2km 이하다.

- 조건을 만족하면 결과 카드에 '지상 1.2km 걸으면 22km 짧아요' 같은 한 줄이 뜨고, 누르면 그 경로로 바뀐다.
- 가장 가까운 지하로, 여기서 나가기, 바로 걷기에는 대안을 두지 않는다(`app.js`의 `findAlt`).
- 참고: `plan.md`의 초기 계획에는 '주 경로와 최대한 겹치지 않는 대체 경로'가 있었다. 구현은 그것이 아니라 이 '지상 가중치를 낮춰 다시 찾기'다. 사용자 결정(2026-11-11)으로 바뀐 것이다.

## 4. 안내 만들기

### 4.1 단계 만들기 (`steps.js`, 원본은 `route.py`)

경로(간선 목록)를 사람이 따라갈 단계로 바꾼다. `route.py`의 `build_steps`가 원본이고, `steps.js`는 이를 1:1로 옮겼다(반올림도 파이썬 `round()`와 같게).

1. **환승에서 나눈다** (`split_parts`): 환승 간선 하나가 `transfer` 단계 하나다. 그 사이의 선로·승강장 간선은 '타기(`ride`)' 부분이 된다.

```python
for i, (ei, u, v) in enumerate(path):
    kind = "transfer" if T["kinds"][E["k"][ei]] == "transfer" else "ride"
    if kind == "transfer" or not parts or parts[-1]["kind"] != "ride":
        parts.append({"kind": kind, "idx": []})
    parts[-1]["idx"].append(i)
```

2. **노선 단위로 다시 나눈다** (`pick_lines`, `assign_lines`): 간선마다 노선 후보가 여럿일 수 있다(예: 같은 선로를 두 노선이 달린다). 규칙은 이렇다.

```python
for j in range(len(sets)):
    if sets[j] and cur not in sets[j]:          # 지금 노선이 이 간선에 없으면
        best, best_run = None, -1.0
        for line in sets[j]:                      # 후보마다 그 자리에서 이어지는 길이(m)를 재어
            run, k = 0.0, j
            while k < len(sets) and (not sets[k] or line in sets[k]):
                run += lens[k]
                k += 1
            if run > best_run:
                best, best_run = line, run        # 가장 길게 이어지는 노선으로 바꾼다
        cur = best
    out.append(cur)
```

- 지금 타던 노선이 다음 간선에도 있으면 계속 탄다. 없을 때만 바꾼다. 바꿀 때는 가장 길게 이어지는 노선을 고른다.
- 노선이 없는 간선(승강장 간선, 이름 없는 선로)은 앞 노선을 이어 간다.
- 도시철도·광역전철 노선(`line_metro = 1`)만 먼저 본다. 경부선·기지선처럼 노선 relation이 없는 선로가 같은 노선 사이에 끼어 있으면 그 노선으로 메운다.

3. **방면** (`terminal_direction`): OSM 노선 relation의 정차역 순서(`line_routes`)에서 '출발역 바로 다음이 이 단계의 다음 역이고, 그 뒤에 도착역이 있는' relation을 모두 찾는다. 그중 종착역이 다른 relation이 앞으로 지날 역에 있는 것(중간 종착, 예: 5호선 상일동행)은 뺀다. 남은 방면이 하나면 '오금 방면'처럼 쓰고, 여럿이면 도착역 뒤에서 노선이 갈라지는 것이라 '하남검단산·마천 방면'처럼 종착역을 잇는다. 셋 이상(1호선)이면 정차역이 가장 많은 두 방면만 남긴다('인천·신창(순천향대) 방면'). 하나도 못 찾으면 도착역 방면('천호 방면')을 쓴다. 다음 역은 지나고 나면 반대쪽처럼 읽히기 때문이다. 순환선은 정차역 순서를 한 바퀴 더 이어 붙여 찾는다.
4. **지나는 역**: 단계 안에서 노드가 역에 속하면(`nodeStation`) 그 역과 단계 출발부터의 거리를 기록한다(`passing`). 진행 표시에 쓴다.
5. **선 이름**: 선로의 이름(`일산선`, `과천선`)은 노선 이름과 따로 담긴다. 화면 문구는 `3호선 · 일산선`처럼 만든다. 노선 이름과 같은 선 이름은 다시 쓰지 않는다.
6. **환승 카드** (`transfer.js`): 환승 단계에 두 승강장의 깊이(서울교통공사 1~8호선), 갈아탈 방향, 거리 출처(실측/추정), 시간(서울교통공사 값은 거리 ÷ 1.2m/s), 행동 안내 세 줄을 붙인다. 국토교통부 '빠른 환승' 자료(`extra.json`)가 있으면 계단이 승강장 앞·가운데·뒤 중 어디인지도 보여 준다. 환승 통로의 실제 모양은 모르면 지어내지 않는다.
7. **지상 노출 경고** (`exposure_warnings`): 지하에서 교량·지상으로 바뀌는 곳마다 경고를 하나 만들어, 노출이 시작되는 단계 바로 앞에 끼운다. 출발부터 지상이면 출발역에서 하나다. 경고에는 직전에 지난 역과 그 역에서 지난 거리, 터널 출입구에서 나가는지 여부(노드 표시 비트 1), 다시 지하로 들어갈 때까지의 노출 거리가 들어 있다.

걷는 시간은 거리 ÷ 걷는 속도다. 기본은 시속 3.5km이고 화면에서 바꿀 수 있다. 3~4km는 '어둠 속 선로 위'를 가정한 값이며 실측 근거는 없다(`plan.md` 가정).

### 4.2 갈림길 (`junctions.js`)

선로가 갈라지는 곳에서 엉뚱한 선로(다른 노선의 지선, 차량기지)로 들어가지 않게, 경로 위 갈림길을 찾아 왼쪽·오른쪽·직진을 알려 준다.

**갈림길 후보**: 경로가 선로 간선으로 들어와 선로 간선으로 나가는 노드에 다른 선로 간선이 더 붙어 있는 곳이다(`findJunctions`).

**왼쪽·오른쪽 계산**: 들어오는 선 모양의 마지막 약 80m와 갈래 선 모양의 처음 약 80m로 방위각을 잰다. 그 차이가 꺾인 각도다.

```js
function bearing(p, q) {   // 방위각(도, 북 0 · 동 90, 시계 방향)
  const dx = (q[1] - p[1]) * Math.cos(p[0] * Math.PI / 180), dy = q[0] - p[0];
  return (Math.atan2(dx, dy) * 180 / Math.PI + 360) % 360;
}
function turnAngle(from, to) {   // 꺾인 각도: -180 ~ 180 (오른쪽 +)
  let d = to - from; while (d > 180) d -= 360; while (d <= -180) d += 360; return d;
}
```

- `dx`에 `cos(위도)`를 곱하는 것은 위도가 높을수록 경도 1도가 짧아지는 것을 보정하는 것이다(짧은 거리라 평면으로 근사).
- 각도가 -20°~+20°면 직진, 음수면 왼쪽, 양수면 오른쪽이다. 갈래 둘이 같은 쪽이면 각도 순서로 '왼쪽 갈래', '오른쪽 갈래'(셋이면 '가운데 갈래')라고 한다.
- 두 갈래의 각도 차이가 3°보다 작으면 240m 앞 각도로 순서를 정한다.

**안내하지 않는 갈래(걸러내기)**: 아래에 해당하면 갈림길 목록에서 뺀다(순서대로).

1. 건넘선(`crossover`): 같은 방향의 옆 선로로 건너가는 선. 다만 다른 노선 본선으로 가서 다른 다음 역에 닿으면 갈림길로 본다.
2. 뒤쪽 선로: 꺾인 각도가 100°를 넘는 갈래(뒤에서 합류하는 선로).
3. 50m보다 짧은 막다른 선로.
4. 150m 안에서 같은 노선의 옆 선로에 다시 붙는 짧은 연결선.
5. 경로와 **같은 다음 역**에 닿는 나란한 선로. 단, 선 이름이 다르면(5호선 본선과 마천지선이 같은 강동역의 다른 승강장으로 갈라지는 경우) 안내한다.
6. 2km 안에서 경로의 앞쪽 노드로 다시 합쳐지는 대피선·통과선. 단, 지상으로 도는 선이면 안내한다.

- 갈래 이름은 갈래를 따라가며 만난 이름 있는 첫 선로로 정한다(`2호선 성수지선`). 선 이름에 '기지'가 들었거나 따라간 길 대부분이 차량기지·측선이면 '차량기지'라 부른다.
- 한계: 좌우는 OSM 선 모양으로만 정한다. 실제 분기기 위치와 다를 수 있고 현장에서 확인하지 못했다(`graph-format.md` 17.4절).

### 4.3 여기서 나가기 (`exithere.js`)

지금 위치에서 **지하로만 걸어서** 닿는 '지상으로 나가는 곳'을 가까운 순으로 보여 준다.

```js
while (heap.size()) {
  const top = heap.pop(), d = top[0], v = top[1];
  if (done[v]) continue;
  done[v] = 1;
  for (let k = G.adjStart[v]; k < G.adjStart[v + 1]; k++) {
    const e = G.adjEdge[k];
    if (e >= G.surfaceFrom || (blocked && blocked.has(e))) continue;
    if (G.weight[e] !== under && E.k[e] !== entrance) continue;     // 지하 간선만(출입구 간선은 예외)
    const w = G.adjNode[k], nd = d + E.len[e];
    if (nd <= maxM && nd < dist[w]) { dist[w] = nd; heap.push(nd, w); }
  }
}
```

- 같은 다익스트라인데 **지하 간선(가중치 1)만** 따라가고, 거리(m)가 `MAX_M = 5000`(5km)을 넘으면 멈춘다. 목적지가 없고 '5km 안의 모든 노드까지 거리'를 구한다.
- 이 거리표에서 후보를 고른다(`findExits`): 역 출구, 터널 출입구(`portal`), 터널 중간 수직구·비상 출구, 차량기지(`depot`). 터널 출입구 이하는 `egress.json`에서 온다.
- 지하 걷는 거리 순으로 정렬하고 10개까지 보여 준다. 같은 역의 출구는 가까운 2개만 둔다(큰 역은 출구가 10개 넘게 있다).
- 고르면 그곳까지 다시 안내한다(`router.js`의 `egress` 끝점). 출입 통제(울타리·문)는 따지지 않는다. 전시에는 뚫고 간다고 본 사용자 결정이다.
- 한계: 수직구·비상 출구에 지상으로 올라가는 계단이 실제로 있는지는 OSM에 없다. 그리고 OSM에서 이 항목은 거의 없다. 전국에서 수직구가 1개(8호선 몽촌토성 부근)뿐이다(`graph-format.md` 19.5절).

### 4.4 도달 범위 (`reach.js`)

도착한 역에서 지하만 따라 30분·1시간·2시간·4시간 안에 닿는 역을 지도에 시간대별로 칠한다.

```js
const bands = (opts.bandsMin || BANDS_MIN).map(function (min) { return { min: min, m: min * mpm }; });
const limit = bands[bands.length - 1].m;
...
for (let k = G.adjStart[v]; k < G.adjStart[v + 1]; k++) {
  const e = G.adjEdge[k];
  if (!isUnderEdge(G, e) || (blocked && blocked.has(e))) continue;
  const w = G.adjNode[k], nd = d + len[e];
  if (nd <= limit && nd < dist[w]) { dist[w] = nd; prev[w] = e; heap.push(nd, w); }
}
```

- 출발은 그 역의 지하 허브들이다. 쓰는 간선은 지하 간선뿐이다.
- 시간 띠는 걷는 속도로 거리로 바꾼다. 속도 3.5km/h면 분당 약 58.3m라서 30분 = 약 1.75km, 1시간 = 3.5km, 2시간 = 7km, 4시간 = 14km다. 4시간 띠(14km)까지만 계산한다.
- 지도에 칠할 때는 띠 경계에서 간선을 잘라, 범위 끝에 걸친 간선도 닿는 부분까지만 칠한다(`segments`).
- 문서 기록: 서울 시청은 30분 6곳, 1시간 22곳, 2시간 65곳, 4시간 150곳이다(2026-11-10 그래프, 시속 3.5km).

### 4.5 출구와 터널 출입구 연결

지도에서 누른 점이나 내 위치는 철도 그래프 위의 점이 아니다. 그래서 그래프에 '가상 지상 간선'으로 잇는다(`router.js`의 `connectPoint`, `egressConns`).

```js
const DETOUR = 1.3;          // 지상 걷기: 직선 거리 × 1.3 (길이 곧지 않은 것)
const NEAR_M = 1500;         // 점에서 출입구를 찾는 반경
const NEAR_COUNT = 3;        // 잇는 출입구(또는 역) 수
```

- 점에서 1.5km 안의 가까운 출입구 3곳에 잇는다. 출입구 자료가 없는 1.5km 안의 역은 그 허브에 잇는다. 둘 다 없으면 20km 안 가장 가까운 역 3곳이다.
- 길이는 직선 거리 × 1.3이고, 비용은 이 길이 × 지상 가중치(1000)다. 지상 걷기는 모두 노출로 센다.
- 터널 출입구(`portal`)와 차량기지(`depot`)도 1.5km 안의 가까운 3곳을 같은 방식으로 잇는다. 어디로 들어갈지는 다른 후보와 같이 **비용으로** 고른다. 예: 9호선 개화 부근 터널 출입구 옆에서 출발하면 지상 노출이 2,778m에서 68m로 준다(`check_connect.js` 시험 기록).
- 수직구·비상 출구와 '가장 가까운 지하로'에는 쓰지 않는다.

가장 가까운 지하로(`nearest.js`)는 지하 허브로 이어진 출구 중 직선 거리가 가까운 역 3곳을 고른다. 한 역에서는 가장 가까운 출구 하나만 남긴다. 20km 안에 없으면 '가까운 지하역 없음'이다.

### 4.6 실제 도보 길 (`walk.js`, 인터넷이 될 때만)

- 화면은 먼저 직선 × 1.3으로 그린다. 그다음 FOSSGIS OSRM 도보 경로(`routing.openstreetmap.de/routed-foot`)를 받아, 받으면 선 모양과 거리·시간·지상 노출을 실제 길로 바꾼다.
- 규칙: 경로 하나에 최대 5번 묻고, 4초 안에 안 오면 포기한다. 두 점이 15m 안이면 묻지 않는다. 실패하면 2분 동안 다시 묻지 않는다. 결과는 좌표를 소수 4자리(약 10m)로 반올림한 열쇠로 저장해 같은 구간을 다시 묻지 않는다.
- **경로를 고르는 계산은 바뀌지 않는다.** 직선 × 1.3으로 고른 경로 위에서 거리만 갱신한다.
- 오프라인이면 직선을 그대로 쓴다. 서버로 가는 것은 두 점의 좌표다(8절 보안 질문 참고).

## 5. 위치 추정

터널 안에서는 GPS가 안 잡힌다. 그래서 세 방법을 순서대로 쓴다(`guide.js`의 `GuideView`와 `app.js`).

```
1) GPS     쓸 만한 GPS 위치(6초 이내, 정확도 80m 이내)가 있고, 경로에서 150m 안이면 그 위치를 경로 위 거리로 바꿔 쓴다.
2) 걸음    GPS가 없고 걸음 센서가 켜져 있으면: 마지막 확인 지점 + 센 걸음 × 보폭
3) 시간    그것도 안 되면: 마지막 확인 지점 + 걸은 시간 × 걷는 속도
```

```js
function walkedM() {
  if (!st) return 0;
  if (opts.pdr && opts.pdr.usable()) return opts.pdr.distanceSinceCheckpoint();
  return (Date.now() - st.since) / 1000 * opts.getSpeed() / 3.6;
}
function hereAt(p) {
  const doneAt = st.cur >= 0 ? st.cps[st.cur].at : 0, nextAt = p.next ? p.next.at : doneAt;
  const g = opts.routePos ? opts.routePos() : null;
  if (g != null && isFinite(g)) return { m: Math.max(doneAt, Math.min(g, nextAt)), gps: true };
  return { m: Math.min(doneAt + Math.min(walkedM(), p.toNext_m), nextAt), gps: false };
}
```

- 위치는 항상 **경로 위의 거리(m)** 로 다룬다. 터널은 한 줄이라 '출발부터 몇 m'만 알면 지도 위치(`pointAt`)를 구할 수 있다.
- 추정 위치는 `[마지막 확인 지점, 다음 확인 지점]` 사이로 자른다(`Math.min`, `Math.max`). 추정이 다음 역을 넘어가 버리지 않게 하려는 것이다.
- **GPS를 믿는 규칙**(`guide.js`의 `GpsGate`, 2026-11-12). GPS가 잡히는 동안에는 늘 GPS를 쓰고, 경로 진행만 보고 추정으로 바꾸지 않는다(추정은 앞서거나 뒤처질 수 있다).
  - 잃음: 마지막 위치를 받은 때부터 6초 동안 새 위치가 없거나, 정확도가 80m보다 나쁜 위치가 오면 추정으로 바꾼다. GNSS는 대개 1초마다 위치를 주므로 6초는 5번 넘게 빠진 것이다. 길 안내 중에는 `maximumAge: 0`으로 브라우저가 저장해 둔 위치를 받지 않는다. 전에는 20초를 기다렸고 저장된 위치(10초)도 새 위치로 보여, 계단을 내려간 뒤에도 파란 점이 20~30초 지상에 남았다.
  - 시각: 끊김은 받은 시각(`Date.now()`)으로만 잰다. `pos.timestamp`는 `Date.now()`와 견주지 않는다. 안드로이드는 위성 시각을 줄 때가 있어, 기기 시계가 몇 초만 앞서도 모든 위치가 오래된 것으로 보여 GPS를 아예 못 쓸 수 있기 때문이다. `pos.timestamp`는 위치끼리 순서만 본다: 같거나 더 오래된 위치가 오면 버린다(`notNewer`, 점이 뒤로 가지 않게).
  - 다시 잡음: 보통은 쓸 만한 위치 하나로 바로 GPS로 돌아간다. 다만 GPS를 잃은 상태에서 추정 위치가 지하 구간이면, 역 안 와이파이·기지국 위치(정확도 20~60m)가 점을 끌고 가지 않게 엄하게 본다: 정확도 25m 안(고도가 없으면 15m 안) 위치가 3번 넘게, 3초 넘게 이어지고 서로 30m 안에 모여야 한다.
  - 지하 구간: 경로 조각마다 간선 구조가 지하(출입구 통로·터널·지하 승강장·지하 환승 통로)인지 적어 둔다(`routeTrack`의 `ug`). 경로 탐색의 '지하'와 같은 기준이다. 추정 위치가 어느 조각에 있는지는 `underNow`가 본다.

### 5.1 걸음 세기 (`pdr.js`)

가속도 센서(`devicemotion`)로 걸음을 센다. **나침반은 쓰지 않는다.** 선로·철골이 자기장을 흐트러뜨리기 때문이다. 터널은 한 줄이라 방향은 경로가 이미 알려 준다. 거리 = 걸음 수 × 보폭이다.

`StepDetector.push`의 핵심은 다섯 단계다.

```js
const m = Math.sqrt(x * x + y * y + z * z);      // 1) 세 축의 크기: 폰 방향과 무관
...
lp1 += aL * (m - lp1); lp2 += aL * (lp1 - lp2);  // 2) 3Hz 저역 통과 두 번(빠른 떨림 제거)
base += aH * (m - base);                          //    0.5Hz 느린 평균(중력·자세)
f = lp2 - base;                                   //    걸음마다 한 번 출렁이는 신호
const thr = Math.max(c.minPeak, c.peakFrac * amp);   // 3) 문턱: 최근 봉우리 높이를 따라 변함
if (!armed) { if (f > thr) { armed = true; peakV = f; peakT = t; } }
else if (f > peakV) { peakV = f; peakT = t; }
else if (f < 0) { armed = false; n = candidate(peakT, peakV); }   // 4) 문턱을 넘었다가 0 아래로 = 봉우리 하나
```

1. 가속도 세 축의 크기 `√(x²+y²+z²)`를 쓴다. 폰을 손에 들든 주머니에 넣든 같은 값이다.
2. 저역 통과(약 3Hz 이하만 남김)와 느린 평균 빼기(약 0.5Hz 이상만 남김)로 걸음 주파수(초당 1.4~2.2번)만 남긴다.
3. 문턱(`thr`)을 넘었다가 0 아래로 내려오면 봉우리 하나, 곧 걸음 후보 하나다. 문턱은 최근 봉우리 높이의 25%를 따라가서, 계단처럼 큰 봉우리와 천천히 걷는 작은 봉우리 모두 잡는다.
4. `candidate()`가 걸음으로 셀지 정한다. 0.25초 안의 두 번째 봉우리는 버리고, 후보 5개가 **고르게**(가장 긴 간격 ÷ 가장 짧은 간격 ≤ 1.5) 이어져야 '걷기'로 보고 모아 둔 5개를 한꺼번에 센다. 걷는 중에는 후보마다 한 걸음이다. 간격이 들쭉날쭉하면 걷기가 아닌 것으로 보고 다시 모은다(덜컹임·흔들기 거르기).
5. 서 있으면 걸음이 없으므로 거리가 늘지 않는다. 시간 추정과 가장 다른 점이다.

### 5.2 보폭 보정

기본 보폭은 0.70m(범위 0.45~1.0m)이다. 체크포인트를 확인하면 실제 거리를 알게 되므로 보폭을 고친다.

```js
out.measured = (knownM - (filledM || 0)) / steps;                       // 실제 거리 ÷ 센 걸음
...
out.rate = Math.min(c.calibMaxRate, steps / (steps + c.calibK));         // 많이 걸은 구간일수록 많이 믿는다
stride = clamp(stride + out.rate * (clamp(out.measured, c.strideMin, c.strideMax) - stride), c.strideMin, c.strideMax);
```

- 새 보폭 = 지금 보폭 + 비율 × (잰 보폭 − 지금 보폭). 비율은 `걸음 ÷ (걸음 + 300)`이고 최대 0.8이다. 한 번 잘못 눌러도 다 바뀌지 않는다.
- 쓰지 않는 구간: 50걸음 미만, 잰 보폭이 0.35m 미만이거나 1.3m 초과(다른 곳에서 눌렀거나 걸음을 크게 놓침), 시간으로 채운 거리가 10% 넘음.
- 보정에는 사용자가 이어서 두 번 확인한 체크포인트 사이의 **선로 구간**만 쓴다. 출입구·환승 통로·지상 걷기는 거리가 어림이라 쓰지 않는다(`guide.js`의 `arrive`).
- 센서가 1초 넘게 값을 못 보낸 시간(화면 꺼짐)이나 크게 흔들리는데 걸음이 안 잡히는 시간은 '시간 × 속도'로 채운다. 위치가 뒤로 튀지 않게 하려는 것이다.

> 정확도는 실제 폰과 터널에서 재지 않았다. 문서의 결과(걸음 오차 2% 안, 보정 뒤 보폭 오차 1% 안)는 시험 파일이 만든 **합성 신호**로 얻은 값이다. 합성 신호는 알고리즘을 만든 가정과 같은 모양이라 실제보다 쉽다. 폰을 팔과 함께 흔들면 두 걸음에 하나만 세는 경우(−50%)도 문서에 적혀 있다(`graph-format.md` 21.5·21.6절).

### 5.3 확인 버튼 (도착 / 통과)

`guide.js`의 `buildCheckpoints`가 경로를 체크포인트 목록으로 만든다.

- 종류: 들어갈 출구(`enter`), 역(`station`), 환승 완료(`transfer`), 갈림길(`junction`), 나갈 출구(`exit`), 도착(`end`).
- 각 체크포인트는 `at`(출발부터 거리 m)과 `pos`(경로 안 간선 위치)를 가진다.
- 사용자가 큰 단추(`도착`, `환승 완료`, `통과`)를 누르면 `arrive()`가 `st.cur++`로 확인 지점을 한 칸 옮기고, 걸은 시간·걸음을 0부터 다시 센다. 위치 오차가 그 자리에서 0이 된다. 걸음 추적기가 켜져 있으면 확인한 구간 거리로 보폭도 고친다.
- 진행 상황은 `progress()`가 계산한다: 다음 체크포인트까지 남은 거리, 이 단계 남은 거리, 전체 남은 거리.

### 5.4 앞이 막힘 (`guide.js`의 `planBlock`)

1. 마지막 확인 지점과 다음 체크포인트 사이의 선로 간선을 막는다.
2. 같은 터널의 반대 방향 선로도 함께 막는다. 막은 선 모양을 20m 간격으로 채우고, 다른 선로의 점 절반 이상이 40m 안에 있으면 나란한 선로로 본다(`blockSpan`, `PARALLEL_M = 40`).
3. 마지막 확인 지점에서 다시 찾는다. 되돌아갈 거리는 `마지막 확인 뒤 걸은 거리(다음 체크포인트까지를 넘지 않게) + 다시 출발할 곳까지 지나온 거리`다.

```js
const backtrack = Math.min(walked || 0, next.at - doneAt) + (doneAt - (rc >= 0 ? cps[rc].at : 0));
```

- 들어갈 출구가 막힌 경우는 그 출입구 간선만 막고 처음 출발점에서 다시 찾는다.
- 다시 찾아도 길이 없으면 막지 않은 것으로 되돌리고 알린다(`guideBlock`).
- 막힌 곳은 사용자가 직접 표시한다. 실시간 피해 정보는 없다.

## 6. 화면과 성능

### 6.1 지도 그리기 (`layers.js`)

- 지도는 Leaflet이다. 철도망은 선이 수만 개라서 **캔버스**로 그린다(`preferCanvas: true`, `L.canvas`). 선마다 DOM 요소를 만드는 SVG보다 훨씬 가볍다.
- 선을 하나씩 그리지 않고 **묶음**으로 그린다. 구조(지상·교량·지하) × 본선/측선으로 6개 묶음을 만들고, 묶음마다 `L.polyline` 하나에 선 여러 개(multi-polyline)를 넣는다.

```js
const renderer = L.canvas({ padding: 0.3 });
...
return { key: gr.key, tier: gr.tier, layer: L.polyline(gr.lines, { renderer: renderer, interactive: false, smoothFactor: 1.5 }) };
```

- 색: 지하 선로는 또렷하게, 지상·교량은 옅게 그린다. 경로를 볼 때는 철도망을 흐리게 하고 경로 선을 진하게 그린다. 노출 구간은 점선으로 끊어 그린다.
- 선 모양(폴리라인 풀기)은 비싸서 간선마다 한 번만 풀어 `shapes[e]`에 둔다.

### 6.2 불러오는 순서 (`graph-format.md` 14.1절)

처음 화면에 필요한 것을 먼저 받고 나머지는 뒤로 미룬다.

1. `index.html`을 읽자마자 `graph.json`을 받기 시작한다(`<link rel="preload" href="data/graph.json" as="fetch" crossorigin>`). 스크립트가 다 실행되길 기다리지 않는다.
2. 글꼴 CSS는 `graph.json`을 받은 뒤에 켠다. 글꼴이 같은 때 받히면 철도망이 늦어지기 때문이다.
3. `graph.json` → 검사·색인 → 역 검색·경로 찾기가 된다.
4. 철도망은 **지금 보이는 곳**(화면의 2배 넓이)의 선로만 먼저 그린다(`edgesInBox`). 나머지는 화면이 놀 때(`requestIdleCallback`) 한 번에 약 8ms씩 풀어 두고, 다 풀면 묶음을 하나씩 전국 선로로 바꾼다.
5. 그다음 차례로 `basemap.json`, `extra.json`, `egress.json`, `passage.json`, `places.json`을 받는다. 필요하면 그때 먼저 받는다.
6. 장소 검색 색인도 화면이 놀 때 8ms씩 나눠 만든다.

- 기록된 수치(헤드리스 Chrome, 폰 화면 390×844, 9Mbps, CPU 4배 느리게, 이 PC에서 잰 중앙값): 첫 화면 글자 0.75초, 역 검색·경로 찾기 가능 2.74초, 철도망 첫 그림 3.11초. **실제 휴대폰에서는 재지 않았다.**
- 앱을 연 뒤 인터넷이 끊겨도 장소 검색·여기서 나가기·환승 계단 위치를 쓰려고, 쓰지 않아도 결국 받아 둔다.

### 6.3 오프라인

서비스 워커(`web\sw.js`)가 앱과 데이터를 기기에 저장해, 한 번 연 뒤에는 인터넷 없이 다시 열어도 동작한다(`graph-format.md` 14.2절). 서비스 워커는 브라우저가 페이지와 인터넷 사이에 두는 작은 프로그램으로, 요청을 가로채 저장한 것으로 답할 수 있다.

- 등록: `web\js\offline.js`가 첫 화면이 뜬 뒤 등록한다. 배포본(스크립트 주소에 `?v=`가 붙은 것)에서만 켜고, claude.ai 미리보기나 iframe 안에서는 켜지 않는다.
- 설치: index 페이지와 그 안의 스크립트(Leaflet 포함)를 저장한다. 하나라도 못 받으면 설치하지 않는다(반쪽 앱을 저장하지 않게).
- 데이터: 앱이 뒤로 미룬 자료까지 다 받은 뒤 `data\*.json` 6개를 하나씩 저장한다(첫 로딩과 겨루지 않게). 다 되면 정보 탭에 '오프라인 사용 준비됨'과 크기(약 7.6MB)가 뜬다.
- 응답: 앱 파일은 저장한 것을 먼저 쓴다. 배경 지도 타일과 글꼴은 본 것만 저장하고(타일 400장, 글꼴 150개 한도, 오래된 것부터 지움), 인터넷이 안 되거나 4초 안에 안 오면 저장한 것을 쓴다. Photon·OSRM 요청은 건드리지 않는다.
- 새 판: 배포할 때 `pages.yml`이 `sw.js`의 `VERSION`을 커밋 번호로 바꾼다. 글자가 바뀐 `sw.js`를 브라우저가 뒤에서 설치하고, 다음에 열 때 적용한다(길 안내 중에는 적용하지 않는다). 안 바뀐 데이터는 다시 받지 않는다(304).
- 홈 화면에 추가: `manifest.webmanifest`와 아이콘으로 앱처럼 설치된다. 정보 탭의 '홈 화면에 추가' 버튼, iOS는 '공유 → 홈 화면에 추가'.
- 한계: 처음 연 화면의 지도 타일은 서비스 워커가 아직 맡기 전이라 저장되지 않는다. 타일이 없는 곳은 간이 배경 지도(`basemap.json`)와 철도망 선이 대신 나온다.

### 6.4 발표 무대: 앱과 3D 맞추기 (`web\stage\`, `demo.js` 6절, `web\3d\ride.js` 5절)

`web\stage\index.html`은 iframe 두 개(왼쪽 `../?stage=1&theme=dark#demo` 앱 시연(어두운 화면, 저장된 테마는 그대로), 오른쪽 `../3d/?follow` 3D)를 놓고 메시지를 넘겨 주기만 한다(같은 출처 `postMessage`).

- 시연으로 가는 길은 무대 하나다(2026-11-12): 정보 탭의 '발표 무대 열기'는 `stage/`로 가는 링크이고, 앱을 `#demo`(옛 `#demo2`·`#demo3` 포함)로 열면 `index.html` 머리의 짧은 스크립트가 철도망 자료를 받기 전에 `stage/`로 옮긴다(`location.replace`, 뒤로 가기로 돌아와도 다시 옮겨지지 않게). 연 뒤 주소가 `#demo`로 바뀌면 `demo.js`의 `hashchange`가 옮긴다. 시연은 주소에 `?stage=1`이 있고 iframe 안일 때만 열린다.
- 앱이 보내는 것: 장면이 시작될 때 `scene`(번호·이름, `scenario`는 늘 1), 걷는 구간이 바뀔 때 `leg`(entry 거리 → 승강장, first 처음 길, backtrack 되돌아가기, reroute 다시 찾은 길, south 남쪽), 걷는 동안 0.2초마다와 멈출 때 `pos`(그 구간 출발부터 길 안내 거리 m, 이번에 멈출 거리, 실제 1초에 늘어나는 m, 앱 추정 위치), 멈춤·속도 `state`(시연을 끝내면 `playing: false`), 끝 `end`. 장면 이름은 save · raid · nearest · enter · platform · plan · guide · junction(선로 갈림길, 2026-11-12 새로) · crossA(광나루까지 빨리 감기 + 첫 하저터널) · block · reroute · ff · crossB · arriveFf · arrive · south 순서다.
- 좁거나 세로인 화면(폰으로 무대를 연 경우): 위에 3D(높이 약 40%), 아래에 폰 칸을 남은 높이·너비에 맞게 줄여 쌓는다. 넓은 화면 배치는 그대로다. 오른쪽 아래 작은 '앱으로' 링크는 앱(`../`)으로 돌아간다.
- 같은 거리를 쓰는 이유: `build_3d.js`가 앱과 같은 길 찾기·안내 코드로 같은 경로를 계산하고, 3D 선의 m 을 안내 거리(`guide.routeTrack`)와 같게 만든다(다르면 빌드가 멈춘다). 그래서 3D 는 받은 m 을 그대로 쓴다.
- 3D 가 따라가는 법: 받은 m 에서 '속도 × 지난 시간(실제 시계)'만큼 앞을 예측하고(멈출 거리는 넘지 않고, 0.4초 넘게 메시지가 없으면 멈춤), 메시지가 올 때 생기는 어긋남은 0.1초 남짓에 걸쳐 줄인다. 속도는 앱이 알린 값과 실제로 늘어난 m 중 작은 쪽을 쓴다(앱 화면이 바빠 느려져도 3D 가 앞서 나가지 않게). 되돌아가기는 앱이 걷지 않으므로(앱 점은 바로 광나루역으로) 3D 가 그린다: 막힘 장면(약 4.8초)이 오면 0.8초에 걸쳐 터널 안으로 들어가고, 1.0초에 잔해가 떨어지고(0.6초 전부터 흔들림), 2.6초 뒤 밖으로 나와 빨간 막힌 구간을 보인 뒤, 무너지고 3.4초 뒤부터 2.4초 동안 광나루역으로 되돌아간다(다음 장면 앞 약 2초까지 이어지고, 다시 찾은 길은 그 뒤 나타난다). 카메라는 장면 이름마다 정해 둔 곳을 본다: 걷는 점이 갈림길 둘레(앞 260m ~ 뒤 160m)면 장면과 상관없이 터널 안 갈림길 35m 앞에서 두 갈래(고른 갈래 청록 + 앱 안내 문장, 다른 갈래 회색 + 선로 이름)를 보고, 첫 하저터널 장면의 빨리 감기는 멀리서 따라가며, 두 번째 하저터널은 가운데 ±500m 에서 잠깐 터널 안, 다시 찾은 길 장면에서는 첫 환승역(왕십리) 구조, 도착에서는 전체 보기, 끝 장면에서는 앱 화살표처럼 1초 뒤 2.6초 동안 수서 → 동탄 화살표가 이어진다. 터널 안 비율은 시간으로 부드럽게 바꾼다(빨리 감기로 갑자기 나오지 않게). 그림은 3판(평평한 지면 아래 단면, 깊이 10배) 그대로이고, 선로의 평면 모양·높이만 `build_3d.js`가 실제 자료로 계산한다(OSM 선에서 10m 안에서 편 곡선, 공식 역 레일 높이 + 35‰ 이하·종곡선 반지름 3,000m, 그리는 깊이 = 보정한 SRTM 지반 − 레일 높이). 깊이 숫자는 역(승강장 자료)에만 보여 주고, 역 사이·한강 아래는 추정이라 숫자를 쓰지 않는다.
- 조작: 발표자는 앱 시연 칸만 쓴다. 무대나 3D 위에서 누른 Space·→ 도 무대가 앱으로 넘긴다(`cmd`). 3D 가 늦게 열리면 `hello`를 보내 지금 장면·구간·위치를 다시 받는다.
- 맞춰 본 결과(명동 이야기, 헤드리스 Chrome, 1280×720, ×60, 3D 는 가벼운 그리기로 평균 20fps): 같은 m 에서 앱 추정 위치와 3D 위치의 수평 거리 차는 처음 길 최대 10m(갈림길 장면 최대 3m), 다시 찾은 길 최대 11m. 실제로 보이는 3D 점과 앱 추정 위치의 차는 걷는 장면(갈림길 초속 35~134m 최대 11m, 두 번째 하저터널 초속 350m 최대 22m)에서는 작고, 빨리 감기(초속 2,600~3,500m)에서는 평균 160~608m·최대 1,108m 까지 벌어졌다가 메시지마다 0.1초 남짓에 걸쳐 줄어든다. 입구(출구 → 승강장)는 3D 가 계단·대합실을 개략 모양으로 그려서 최대 33m 다르다.

## 7. 검증

### 7.1 JavaScript가 Python과 같은 결과를 내는가

`route.py`를 먼저 만들어 기준으로 삼고, 같은 로직을 `router.js`·`steps.js`로 옮겼다. `scripts\check_router.js`가 둘을 비교한다.

- 역 쌍 9개(서울역→강남, 여의도→광화문, 대화→백석, 부산역→서면, 반월당→동대구 등, 한강 5호선을 막은 경우 1개 포함)를 `python -I scripts\route.py ... --json`으로 풀고 같은 쌍을 JavaScript로 푼다.

### 7.3 OSM 데이터 검증

- **출처 대조 40곳**: 장대터널 7곳, 도시철도 지상·지하 구간 21곳, 서울 한강 철도 횡단 12곳을 위키백과·언론 자료와 대조했다. 틀린 구조 표시는 못 찾았다. 장대터널 길이는 7곳 중 5곳 일치, 2곳(율현 +3.3%, 솔안 +5.6%)은 대체로 일치다(`data-check.md` 4.5절).
- **발견한 불일치 1건**: `layer<0` 해석(경부선 금정~당정). 이것이 2.2절 판정 규칙의 근거다.
- **나무위키 64건 대조**: 지상·지하 구간 목록과 OSM을 맞춰 보니 일치 60, 애매 3, 못 찾음 1, 불일치 0이다. 엄격한 기계 판정에서는 2건(공항철도 인천공항1터미널~2터미널, 부산 1호선 노포)이 나왔지만, 다른 출처로 보니 나무위키 항목을 다르게 읽어야 했고 OSM이 틀렸다는 근거는 찾지 못했다(`namu-check.md`). 못 찾은 1건(3호선 동작)은 나무위키 수집 쪽 오류로 보인다.
- **서울교통공사 역 깊이 대조**: 277개 중 2개가 다르다(1호선 서울, 2호선 한양대). 12절 한계에 적혀 있다.
- **지역 신뢰도**: 좋음(서울·인천·경기·부산·대구·대전), 주의(전남광주·울산·세종·강원·경북·경남), 미검증(충북·충남·전북)으로 나눠 `graph.json`에 넣었고, 화면에서 주의·미검증 지역 구간은 '신뢰도 낮음'으로 표시한다.
- **범위 점검(확장 후보)**: 지하 보행로(`ped-check.md`), 폐선 터널(`abandoned-check.md`), 도로 터널·민방위 대피시설(`roads-shelters-check.md`)을 조사해 경로 탐색에는 넣지 않기로 했다(8절).

## 8. 예상 질문과 답

### Q1. 왜 다익스트라인가요? A*는 안 되나요?

가중치(길이 × 1 또는 1000)가 음수가 아니라 다익스트라로 정확한 최저 비용 경로를 얻습니다. 같은 알고리즘을 도달 범위(`reach.js`)와 여기서 나가기(`exithere.js`)에서도 '목적지 없이 일정 거리 안의 모든 노드까지의 거리'를 구하는 데 그대로 씁니다. A*는 목적지가 하나일 때 유리한데, 이 앱은 출발·도착이 여러 허브이거나 목적지가 없는 탐색이 많습니다. (A*를 시험해 비교하지는 않았습니다. 이 답은 코드 구조에 근거한 설명입니다.)

### Q2. 가중치 1000은 어떻게 정했나요?

'지상 1m를 지하 1km처럼 계산한다'는 규칙을 직접 정했습니다. 의도는 지하로만 가는 길이 있으면 아무리 돌아도 그 길이 뽑히게 하는 것입니다. 1000이라는 값을 실험으로 고른 기록은 문서에 없고, 값은 `graph.json`의 `weights`에 있어 코드 수정 없이 바꿀 수 있습니다. 한계는 지하 우회가 지상 1m당 1km를 넘으면 지상 구간을 택한다는 점입니다.

### Q3. 지하 판정은 왜 `layer<0`이 아니라 `tunnel` 태그만 쓰나요?

데이터를 검증하다가 `layer=-1`인데 실제로는 지상인 구간을 찾았습니다. 경부선 금정~수원 약 16km(선로 4줄)이고, 경인일보 기사에서 금정~군포~당정 4.84km가 지상 운행이라고 확인했습니다. 전국에서 `layer<0`만 있는 본선 90.1km 중 63.6km가 이 구간입니다. 그래서 `tunnel`이 있는 선로만 지하로 봅니다.

### Q4. OSM 데이터를 믿을 수 있나요?

완전히 믿는다고 하지 않고 검증했습니다. 장대터널·도시철도 구간·한강 횡단 40곳을 공개 자료와 대조해 틀린 표시를 못 찾았고, 나무위키 64건 대조에서도 불일치 0건이었습니다. 지역별 신뢰도를 좋음·주의·미검증으로 나눠 화면에 '신뢰도 낮음'으로 표시합니다. 알려진 오류도 있습니다(동대구처럼 역 건물 밑 선로가 터널로 그려진 곳).

### Q5. 서버 없이 경로를 어떻게 계산하나요?

전국 그래프를 파일 하나(`graph.json`, gzip 약 0.97MB)로 만들어 브라우저가 받고, 브라우저 안에서 다익스트라를 돌립니다. 인접 목록을 숫자 배열로 색인해 두기 때문에 한 번 탐색은 빠릅니다. 문서에 기록된 시간은 갈림길 찾기 1~10ms, 여기서 나가기 6~8ms(이 PC, Node)입니다. 폰에서는 재지 않았습니다.

### Q6. 왜 JavaScript와 Python 두 벌이 있나요?

Python `route.py`를 먼저 만들어 로직의 기준(참조 구현)으로 삼고, 브라우저용으로 JavaScript에 옮겼습니다. `check_router.js`가 둘의 결과(간선 목록, 거리, 단계, 문장)가 같은지 비교합니다. 옮긴 코드가 틀리면 바로 드러나게 하려는 장치입니다.

### Q7. 터널을 걷는 것이 현실적인가요?

현실에서 권장되는 행동이 아니라 **전시 상황을 가정한 설계**입니다. 열차 운행이 멈추고 전기가 끊겨 선로를 걸을 수 있다고 가정했고, 평시에는 철도 터널에 들어가면 안 된다는 안내를 처음 열 때와 정보 탭에 항상 보여 줍니다. 실제 터널 안 상태(조명, 감전, 수위)는 모르고, 현장에서 확인하지도 못했습니다.

### Q8. GPS 없이 위치를 어떻게 아나요?

세 단계입니다. GPS가 쓸 만하면 그것을 쓰고, 아니면 폰 가속도 센서로 걸음을 세어 '마지막 확인 지점 + 걸음 × 보폭'으로 추정하고, 센서도 안 되면 걸은 시간 × 속도로 추정합니다. 역이나 갈림길에서 '도착'·'통과'를 누르면 위치가 그 지점으로 바로잡힙니다. 걸음 세기는 아직 실제 폰으로 정확도를 재지 못했고, 합성 신호로만 시험했습니다.

### Q9. 걸음 세기가 실제로 정확한가요?

아직 모릅니다. 합성 신호 시험에서는 걸음 오차가 2% 안이었지만, 합성 신호는 알고리즘을 만든 가정과 같은 모양이라 실제 폰보다 쉽습니다. 폰을 팔과 함께 흔들면 절반만 세는 경우도 시험에서 나왔습니다. 그래서 기준은 여전히 사용자가 체크포인트에서 누르는 확인이고, 걸음 세기는 그 사이를 메우는 보조입니다.

### Q10. 막힌 곳 정보는 어떻게 아나요?

모릅니다. 실시간 피해 정보는 다루지 않습니다. 사용자가 '앞이 막힘'을 누르면 그 구간(같은 터널 반대 선로 포함)을 빼고 마지막 확인 지점에서 다시 찾습니다. 한강 교량 전부 파괴 같은 미리 만든 상황을 고르는 기능도 있습니다(`presets.han_crossings`). 막은 구간을 기기에 저장하는 코드는 확인하지 못했습니다.

### Q11. 환승 통로와 역 안 구조 데이터는 어디서 얻었나요?

서울은 서울교통공사 환승 거리(140행 중 139행 반영), 역 깊이(1~8호선), 서울시 지하도 공간정보(2021년 무렵, 출구 1,366개·환승 61쌍의 모양), 국토교통부 빠른 환승 정보(환승 계단 위치)를 씁니다. 그 밖의 환승 거리는 직선 거리 × 1.3 + 50m로 추정하며 그 계수에 실측 근거는 없습니다. 지하도 모양은 **그림만** 바꾸고 거리·시간은 그래프 값 그대로입니다.

### Q12. 서울 밖에서는 어떻게 되나요?

철도 그래프는 전국(제주 제외)입니다. 다만 자료의 깊이는 지역마다 다릅니다. 환승 실측 거리, 역 깊이, 지하도 모양은 서울만 있습니다. 부산·대구·대전은 신뢰도 '좋음'이고, 충북·충남·전북은 아직 검증하지 못해 '신뢰도 낮음'으로 표시합니다. 부산역→해운대 18.5km는 전 구간 지하로 나옵니다(앱에서 직접 찾아볼 수 있습니다. 시연은 서울 이야기 하나만 재생합니다).

### Q13. 오프라인은 어떻게 되나요?

계산은 전부 기기 안에서 하므로 서버가 필요 없습니다. 한 번 열면 서비스 워커가 앱 파일과 철도망 데이터(약 7.6MB)를 기기에 저장하고, 그 뒤에는 인터넷 없이 다시 열어도 경로 탐색·안내·재탐색·위치 추정·장소 검색이 됩니다. 정보 탭에 '오프라인 사용 준비됨'이 뜨면 준비가 끝난 것이고, 홈 화면에 추가하면 앱처럼 열립니다. 배경 지도 타일은 본 곳만 저장되고, 없는 곳은 간이 배경 지도로 대신합니다.

### Q14. 데이터는 어떻게 갱신하나요?

스크립트를 다시 돌립니다. `overpass_fetch.py`로 OSM을 받고, `merge_ways.py`와 `build_graph.py`를 실행하면 `graph.json`이 새로 만들어지고, 웹 폴더가 바뀌어 푸시되면 GitHub Pages가 자동 배포합니다. 현재 기준 시각은 2026-11-10입니다. 주기적 자동 갱신은 만들지 않았습니다.

### Q15. 왜 앱이 아니라 웹인가요?

설치와 계정이 필요 없고, 링크 하나로 열 수 있어야 급할 때 쓸 수 있기 때문입니다. 정적 파일이라 서버 없이 GitHub Pages(무료)로 배포합니다. 브라우저에서도 GPS와 가속도 센서를 쓸 수 있습니다. 대가는 화면이 켜져 있고 앱이 앞에 있을 때만 센서 값이 온다는 점입니다. 화면 꺼짐 방지(Wake Lock)로 줄이지만 배터리는 더 씁니다.

### Q16. AI를 어디에 썼나요?

코드 작성은 AI(Claude) 도움을 받았습니다. 직접 정한 것은 서비스 방향과 기능 범위, 판정 규칙('tunnel 태그만 지하'), 지상 가중치 같은 설계 결정, 그리고 어떤 자료로 어떻게 검증할지입니다. 이 문서는 그 코드를 읽고 설명할 수 있도록 정리한 것입니다. (발표 때는 본인이 실제로 한 일의 범위에 맞춰 이 답을 조정하세요.)

### Q17. 도로 터널이나 민방위 대피소는 왜 안 넣었나요?

조사한 뒤에 범위를 정했습니다. 도로 터널은 OSM에 3,487km가 있지만 한강을 건너는 도로 터널은 하나도 없고, 서로 떨어진 철도 지하 덩어리를 잇는 경우도 사실상 없었습니다(조건에 맞는 1쌍도 지상으로 걷는 것보다 나쁨). 민방위 대피시설은 좌표 자료가 인증키가 필요한 공공 API 하나뿐이었습니다. 그래서 경로에는 넣지 않고 확장안으로 소개합니다. 지하상가·폐선 터널도 같은 이유로 넣지 않았습니다.

### Q18. 보안이나 개인정보 문제는 없나요?

공개 데이터(OSM, 공공데이터)만 쓰고, 비공개 연결선이나 비상 통로 정보는 쓰지 않습니다. 서버와 계정이 없고 저장 장소·설정은 브라우저 `localStorage`에만 둡니다. 다만 인터넷이 될 때 외부로 나가는 것이 있습니다. 지상 도보 구간을 실제 길로 바꾸려고 OSRM에 두 점의 좌표를 보내고, 온라인 장소 검색(Photon)에는 검색어가 갑니다. 지도 타일과 Leaflet(CDN), 글꼴도 외부에서 받습니다. 오프라인이면 이 요청들은 쓰지 않습니다.

### Q19. 갈림길에서 왼쪽·오른쪽이 정확한가요?

OSM 선 모양으로만 계산하므로 실제 분기기 배치와 다를 수 있고 현장에서 확인하지 못했습니다. 갈래 사이 각도가 3°보다 작게 붙은 곳(예: 강동 서쪽)은 240m 앞 각도로 순서를 정해 특히 불확실합니다. 그래서 화면에는 좌우뿐 아니라 갈래의 노선 이름과 방면(`5호선 마천지선 · 둔촌동 방면`)을 함께 보여 줍니다.

### Q20. 시연 모드는 가짜 아닌가요?

앱의 실제 함수(경로 탐색, 길 안내, 도달 범위, 지도 따라가기)를 그대로 부르는 재생입니다. 다만 걸음을 실제로 걷지 않으므로 '마지막 확인 지점 + 걸은 시간 × 속도'의 시작 시각을 앞당겨 빨리 걸은 것처럼 만들고, 다음 확인 지점에 닿으면 큰 단추를 코드가 대신 누릅니다. 시연 중에는 GPS와 인터넷(OSRM)을 쓰지 않아 어디서든 같은 장면이 나옵니다. 시나리오는 한 사람의 이야기 하나입니다(명동 거리에서 공습경보 → 가장 가까운 출구(명동역 6번, 지상 257m) → 가족 약속 장소(수서역)까지 지하로 → 충무로 지나 선로 갈림길에서 '통과' → 광나루–천호 하저터널 막힘 → 마포–여의나루 하저터널로 다시 찾기 → 그 하저터널 건너기 → 수서역 도착 → 남쪽 동탄으로 이어지는 길). 거리·출구 번호는 자막에 박아 두지 않고 앱의 경로 탐색 결과에서 읽습니다. 발표 무대(`stage/`)에서만 재생하고, 앱 주소 `#demo`나 정보 탭의 단추는 무대로 옮깁니다. 공습 장면 처음의 위급재난문자는 흉내이고, 공개 페이지라 제목('위급재난문자 · 시연')과 본문('[시연] …')에 시연이라고 적고 실제 기관 이름·발신 번호를 쓰지 않습니다(`check_demo.js`가 확인). 시연 중 저장하는 '가족 약속 장소'는 메모리에만 두어(`saved.js`의 `useMemory`) 보는 사람이 저장해 둔 장소를 건드리지 않습니다.

## 9. 1분 설명 스크립트

지하로는 전쟁으로 지상이 위험할 때, 지하 철도망만 따라 이동하는 길을 찾아 주는 웹 앱입니다. 먼저 OpenStreetMap에서 전국 철도 선로를 받아, tunnel 태그가 있는 구간만 지하로 판정하고 역, 출구, 환승 통로를 이어 그래프 파일 하나로 만듭니다. 브라우저는 이 파일을 읽어 다익스트라 알고리즘으로 경로를 찾습니다. 지상 1미터를 지하 1킬로미터만큼 비싸게 계산하기 때문에, 지하로만 가는 길이 있으면 자동으로 그 길이 뽑힙니다. 결과는 노선, 방면, 지나는 역, 환승, 선로 갈림길 단위의 단계로 안내합니다. GPS가 안 잡히는 터널 안에서는 폰 가속도로 걸음을 세어 위치를 추정하고, 역에서 도착 버튼을 눌러 바로잡습니다. 앞이 막히면 그 구간을 빼고 다시 찾습니다. 경로 계산은 모두 기기 안에서 돌아가고, 지하 판정은 공개 자료 40곳과 대조해 검증했습니다. 코드는 AI 도움을 받아 작성했고, 판정 기준과 검증 방법은 제가 정했습니다.
